# Contracts between the parts of KubaOS

Every part of KubaOS is built against these interfaces. If you need to change one, update this file in the same commit.

Reference hardware: the TUXEDO InfinityBook Pro 14 Gen10 (AMD), the machine every release is tested on. Its drivers are the optional apt group `tuxedo`. Ubuntu Server 26.04 LTS minimal, Hyprland 0.56+ (from `ppa:cppiber/hyprland`, Lua config), Quickshell pinned to a tagged release via Nix, standalone home-manager (flake). Full context: `docs/PLAN.md`.

## Repo location and ownership

- On an installed machine, KubaOS is the root-owned checkout `/usr/share/kubaos`, on a local `release` branch that only a KubaOS update moves, with `origin` on GitHub. `/etc/gitconfig` lists it in `safe.directory`, so Nix reads it as the user. Nothing runs from a user-writable copy, and no Nix code names the checkout's path.
- Each user switches their own **user flake**, `~/.config/kubaos/home/` (`flake.nix`, `flake.lock`, `home.nix`), which the install writes from `user-flake/`. It has its own `nixpkgs` input and takes KubaOS as `git+file:///usr/share/kubaos?ref=refs/heads/release`, with no `follows`. The username and host are literals in it. After the install it's the user's: an update never writes it, except `flake.lock` when the user runs `nix flake update`, which `kubaos update` does, and a user migration ("Updates and migrations").
- KubaOS's flake exports `lib.mkHome { pkgs, username, modules }`, `homeModules.default` (`home/`) and `packages.<system>`, the curated set (`home/curated.nix`), built from KubaOS's own nixpkgs, plus `packages.<system>.cache`, a link to every output of the curated set but the debug ones, which the binary cache workflow builds ("The binary cache"). `mkHome` takes ordinary packages from `pkgs` (the user's nixpkgs) and gives the modules the curated set as the `kubaosPkgs` argument, plus KubaOS's whole package set as `kubaosPkgs.nixpkgs` for the GPU driver bundle. home-manager is KubaOS's pin. A package belongs in the curated set when it's built from source outside nixpkgs, loaded into a curated process, given privileges by `system/`, or driven by a curated program through an interface that changes between its releases (kdeconnect-kde); everything else comes from `pkgs`.
- **KubaOS's own crates in the curated set** (`kubaos`, `kobo`, `kotodama-kubaos`, `kubaos-files`, `-automount`, `-launches`, `-phone`, `-bluetooth`, `-clock`, `-sysmon`) build with crane (`crates/workspace.nix`, the `crane` flake input, which Kotodama's follows). Their dependencies build in two derivations, one for Kōbō (iced and wgpu, which nothing else uses) and one for the command-line tools, which change only with `Cargo.lock` and the crates' manifests; every package builds on its group's, compiling only KubaOS's code. A package's source is its crate, the workspace crates it depends on (read from the manifests) and the files they embed (`install/firstboot` for `kubaos-core`), plus every crate's `Cargo.toml`; so a release rebuilds only the packages whose crates changed. Their tests don't run in that build, on the user's machine: `cargo test --workspace` (`just test`) runs them. A new crate in the curated set goes in a group of `shipped` in `crates/workspace.nix`, so its dependencies are prebuilt. `/etc/nix/nix.conf` has `max-jobs = auto` (`system/60-nix.sh`, and the `parallel-builds` system migration on machines installed before it), so the daemon builds the packages side by side; `cores` keeps its default, every core for each build, which measured faster than a cap (`nix_parallel_builds` in `system/lib.sh`).
- **The binary cache** is the public Cachix cache `kuba-os` (`https://kuba-os.cachix.org`, key `kuba-os.cachix.org-1:BAhDPs8FW+W0SaOzsx7yS9sZmcb6ZjdLc09hBeKXIE0=`, signed by Cachix). On every push to `main`, `.github/workflows/cache.yml` builds `packages.<system>.cache` for `x86_64-linux` (`ubuntu-latest`) and `aarch64-linux` (`ubuntu-24.04-arm`) and runs `cachix push kuba-os` on it: its runtime closure, minus what cache.nixos.org has, which leaves KubaOS's crates, Kotodama, Quickshell's wrapper and the orange Colloid icon theme (about 240 MiB of NAR per architecture when all of it is new). Build-time paths, such as the crates' dependency builds, aren't pushed. Because `mkHome` takes the curated set from KubaOS's own lock whatever the user's nixpkgs, those are the exact store paths a machine's switch asks for. `/etc/nix/nix.conf` names the cache with `extra-substituters` and `extra-trusted-public-keys` (`nix_binary_cache` in `system/lib.sh`, run by `system/60-nix.sh` and by the `binary-cache` system migration on machines installed before it; `install/image/Dockerfile` and `test/Dockerfile` write the same lines). No user is in `trusted-users` and nothing runs `cachix use`: a trusted user is effectively root. A path the cache doesn't have yet, while CI is still building a push, builds on the machine as it would without the cache. The repo secret `CACHIX_AUTH_TOKEN` is the write token.
- KubaOS's flake also has `homeConfigurations."kuba@tuxedo"` and `"kuba@vm"`, both `x86_64-linux` and `mkHome` with KubaOS's own nixpkgs: the laptop's home from a checkout, and the test harness's (`test/run`, in Docker on the x86_64 development machine). The payloads build their user's home from the user flake (`user-flake/`, `@SYSTEM@` the payload's arch), not from these; an aarch64 machine switches its user flake too.
- Hostnames: `tuxedo` (the laptop, and the x86_64 payload's host) and `vm` (the aarch64 payload's host, and the test harness's container). Flake outputs are `<user>@<host>`, so plain `home-manager switch --flake ~/.config/kubaos/home` picks the right one.
- Flakes only see files git knows about: in a KubaOS clone, `git add` new files under `config/`, `scripts/`, `home/` before `home-manager switch` (no commit needed). `~/.config/kubaos/home` is a plain directory (a `path:` flake), unless you put it under git yourself.

## Defaults and the user layer (home/links.nix, scripts/dot-config)

KubaOS ships defaults. The user extends or overrides them in a layer of their own, and an update never overwrites it. An update can add new defaults and fix bugs in ours, and that's all.

- **Defaults** are `config/<app>/`. `links.nix` copies `config/` into the store once (`kubaos-defaults`) and links each file read-only into `~/.config/<app>/`, which is a real directory, so apps can still write their own files next to ours. `links.nix` finds the files with `builtins.readDir`, so a new file or app needs no Nix change. An update replaces this layer whole. Editing `config/` takes a `home-manager switch`. The shipped tree is also at `~/.local/share/kubaos/defaults`, for reading.
- **The user layer** is `~/.config/kubaos/<group>/<app>/`, grouped by area: `desktop/` (hypr, quickshell, cursor, clock, keyboard, sysmon, idle, power, files, wallpapers, phone, network, workspaces, update), `terminal/` (ghostty, foot, tmux, zsh, fastfetch), `editor/` (nvim), `tools/` (git, lazygit, yazi, bat, bacon, fuzzel) and `menu/` (kotodama), beside the user flake in `home/`. Inside an app's folder the file names are the app's own. The defaults load it last, so anything set there wins. Updates never write to a file in it. `dot-config apply`, which every `home-manager switch` runs (the install's included), creates each missing file from `user-layer/<group>/<app>/`. Each one opens with the settings people change most, commented out, each with its default and why you might change it, then a link to the app's full docs. Deleting a file brings it back on the next apply.
- **Where each app's folder is** is written once per language: `home/user-layer.nix` (Nix, and through the layer file's `app NAME PATH` lines, `dot-config` and the shell scripts, which ask `dot-config path APP`), `crates/kubaos-user-layer` (Rust), `config/hypr/user_layer.lua` (Hyprland), `config/quickshell/settings/UserLayer.qml` (Quickshell, the apps it reads) and `config/nvim/lua/config/user.lua` (Neovim's own folder). A file include in an app's config, which has no variables, names its grouped path literally; the harness checks each one exists after a switch. An eval-time assertion in `home/links.nix` and a test in `crates/kubaos-user-layer` keep `user-layer/` and the tables in step.
- **The maps.** `~/.config/kubaos/README.md` says where to go to change what, and each group's `README.md` lists its folders. They are links to the release's copies (`~/.local/share/kubaos/skel`), so they stay current; `dot-config apply` makes one only where there's nothing, and a README of the user's own is kept. The Command menu's "Settings folder" and "Settings: Desktop", "Terminal", "Editor", "Tools" and "Menu" open them in Files (`dot-config open [GROUP]`).
- **Moving from the flat layout.** Releases before the groups kept each app's folder at `~/.config/kubaos/<app>/`. `dot-config apply` moves those into their groups before it creates a missing file, so a new example never takes the place of the user's file (`dot-config relocate` does the move alone; the `grouped-user-layer` user migration runs it again). A folder whose group has none moves whole. Otherwise it moves file by file: the same file in both places is kept once, an untouched example gives way to the user's file, and when the user edited both, the grouped one stays and the flat one goes beside it as `<file>.old` (`.old.2` and so on), reported on stderr. Nothing is deleted but empty folders. In a user layer that is a git clone, the moves show as renames; nothing is committed. There's no fallback: nothing reads the flat paths after the move.
- When a default changes, users who never overrode it get the new value. Users who did keep theirs. In an entry file, the user layer's include stays the last line, below every default.
- A migration may change a user file only if it adds to the file and doesn't rewrite it, is safe to run more than once, backs the file up first, and skips any setting the user has changed. It may create a user file that doesn't exist.

A file that doesn't read (anything but those tables and keys, a screen in two groups) pins nothing, and says so in a critical toast, tried once a second for a minute until the shell shows it (at login Hyprland reads the file before the shell is up), then not shown again for the same problem across config reloads |
| lazy.nvim | `U/editor/nvim/lazy-lock.json` | `:Lazy update` rewrites it: copied from `config/nvim/lazy-lock.json` once (lazy.nvim's `lockfile`) |

The merged files (bat, git ignore, fastfetch) change when `dot-config apply` runs: after an update, or by hand after editing the user file. fastfetch's also change when `dot-theme` runs `dot-config merge` after a theme change. Every other user file applies the way the app reloads its config.

Not in the user layer yet: the rest of Quickshell's settings (`config/quickshell/settings/Settings.qml`), the matugen templates, and oh-my-posh (a matugen template). They ship as read-only defaults until they get their own design.

The `layer` table in `links.nix` lists the files that aren't plain links (seeded, `concat`, `json`); it's written to `~/.local/share/kubaos/layer` for `dot-config`, after one `app NAME GROUP/NAME` line for each app's folder in the user layer.

### The running session after a switch (home/session.nix, scripts/dot-session)

A switch writes no file: it points the links in `~/.config` at new store files. Programs that read their config once at start keep the old defaults, and Hyprland, which watches its files for writes, doesn't notice either. So every generation records, in `kubaos-session` next to its `activate`, the store paths each of these parts starts from: its directory or file in `config/`, plus the package where KubaOS pins one. Home activation (`reloadSession`, after the user units and `dot-config apply`) compares the old generation's record with the new one's and runs `dot-session apply` for the parts that changed:

| Part | Record | On a change |
|---|---|---|
| Hyprland | `config/hypr/` without `hypridle.conf`, `hyprlock.conf`, `README.md` | `hyprctl -i <instance> reload` |
| Quickshell | `config/quickshell/`, `kubaosPkgs.quickshell` (which carries Kotodama's QML module) | Hyprland execs `dot-session restart-shell`: it waits while `qs ipc call session locked` says `true`, then kills every Quickshell process (`pkill -x .quickshell-wra`, Quickshell's crash handler included, since it relaunches a shell it sees die and `qs kill` reaches one instance). `dot-session shell` ("The shell's supervisor") starts the new one; a shell started by hand, with no supervisor, is waited for until it has gone, and then `exec qs`. The Command menu's "Restart Quickshell" and `SUPER+CTRL+ALT+R` run the same. When no Quickshell runs, nothing starts. Two restarts waiting at once start one shell |
| hypridle | `config/hypr/hypridle.conf` | Hyprland execs `dot-session restart-idle`: when hypridle runs, it is stopped and started again. One stopped by hand stays stopped. Activation writes the idle settings' listeners (`kubaos-idle write`, `home/idle.nix`) before this runs |
| Ghostty | `config/ghostty/` | `SIGUSR2` to the user's Ghostty processes |
| tmux | `config/tmux/` | `tmux source-file` when a server runs |

- The Hyprland instances are `hyprctl instances` in `$XDG_RUNTIME_DIR` (`/run/user/<uid>` when unset), so it works from a terminal in the session, from `kubaos update`'s switch unit and over ssh, all as the desktop user. With no Hyprland running (a tty, ssh with nobody logged in), the Hyprland, Quickshell and hypridle parts do nothing.
- A first activation (the installer's, a new home) has no old generation and does nothing. A part a generation has no record of counts as changed when the other has one, so the first switch onto a generation with records restarts everything that runs once.
- It never fails a switch: `dot-session apply` exits 0, and a failed reload or restart is only a missing line in the output.
- Left alone: the Kotodama Daemon (it follows its config links into the store, and its systemd unit is restarted by the switch's sd-switch when the package changes), hyprlock (starts afresh at each lock), Hyprland's own package (the VM's, from Nix: a new one needs a new login), `dot-hypr-workspaces` (a running script keeps its old copy until the next login), and Neovim and the other terminal apps (they read their config when they start).

## The state directory, Suites and switch jobs (home/state.nix, home/suites.nix, kubaos-core)

What the `kubaos` CLI, the Command menu and Kōbō install is declared in files the tool owns, never in Nix code (`docs/adr/0002-suites.md`).

- **The state directory** is `~/.config/kubaos/home/kubaos.d/`, inside the user flake: `packages.toml`, `nixpkgs.toml` and `suites/<name>.toml`. Any of them may hold `packages = ["ripgrep", "python3Packages.black"]`, attribute paths into the user's `pkgs`; the home installs the union. A Suite file's other keys (options, version) belong to the Suite framework. `kubaos package add|remove` rewrites `packages.toml` whole, sorted, under the lock `~/.local/state/kubaos/kubaos.d.lock`, through a temporary file and a rename. A Suite's install writes its file and its removal deletes it.
- **Unfree packages.** `nixpkgs.toml` holds `allow_unfree`, true without the file or the key; `kubaos package unfree on|off` rewrites it whole under the same lock, and switches unless `--no-switch` (without `on` or `off` it prints `on` or `off`). While it is true, `home/state.nix` sets the home's `nixpkgs.config.allowUnfree = true`, so home-manager imports the user's nixpkgs with it, and every package of `pkgs`, `home.nix`'s included, may be unfree; while it is false it sets nothing, and nixpkgs' default refuses them. That definition takes the place of the config of the `pkgs` passed to `mkHome` (nixpkgs' defaults, for the user flake's `legacyPackages`); a `nixpkgs.config` of the user's own in `home.nix` merges with it key by key, so with the setting off their `allowUnfree` or `allowUnfreePredicate` still decides. The curated set keeps KubaOS's nixpkgs and its config. `kubaos try` follows the setting: while it is true it runs `env NIXPKGS_ALLOW_UNFREE=1 nix shell --impure …`, since the flake's `legacyPackages` refuses unfree packages. Whether a package is unfree is its `meta.unfree` in the user flake's nixpkgs: one `nix eval --json --inputs-from ~/.config/kubaos/home nixpkgs#legacyPackages.<system> --apply …` per command for every name at once, `null` for a name that is no derivation there or whose meta throws; a name that is no attribute path never reaches Nix and is unknown too (`kubaos_core::unfree::LicenseCheck`). `kubaos package add` runs it before writing anything: while `allow_unfree` is false it refuses an unfree name with exit 1 and a message naming `allow_unfree in kubaos.d/nixpkgs.toml` and `kubaos package unfree on`, and also when the check itself fails; while true it prints `added <name> (unfree)`, and a failed check only warns. `kubaos package list` prints `unfree` after an unfree package's files, and `--json` is `{ "<name>": { "from": ["packages.toml", "suites/<suite>.toml"], "unfree": true|false|null } }`, `null` when unknown or when the check failed, which it warns about on stderr. `kubaos package unfree off` refuses, exit 1, while a package the directory lists is unfree, naming the `kubaos package remove` or `kubaos suite remove` that takes it out, or while the check fails. It doesn't see `home.nix`'s packages: one of them unfree fails the switch, and `kubaos package unfree on` puts the setting back. `kubaos suite add` doesn't check the packages a Suite lists.
- **Git.** When the user flake is in a git work tree, Nix copies it from git's index, so a file git doesn't know isn't in the flake. Every write into `kubaos.d/` (`kubaos package`, `kubaos suite`, `kubaos package restore`) ends with `git add --intent-to-add -- kubaos.d`, which lists new files without staging their content, and `git rm --cached` of the files it deleted. Nothing is committed, and a changed file's staged content stays as the user left it (`kubaos_core::state::StateDir::sync_git`). A flake that isn't in a work tree is left alone.
- **Wiring.** `home.nix` sets `kubaos.stateDir = ./kubaos.d;` (`user-flake/home.nix` has it). `home/state.nix` reads the directory with `builtins.readDir` and `builtins.fromTOML` when the path exists, and does nothing otherwise. On an older `home.nix`, `kubaos package add|remove` and `kubaos suite add|configure|remove` add the line above its closing `}`, after copying the file to `~/.local/state/kubaos/backups/home.nix.bak` (or `.1`, `.2`, …). The backup lives outside the user flake, so it never becomes part of the flake's source in the Nix store. It skips a file that already sets it, and refuses one whose last line isn't a lone `}`, asking the user to add the line by hand (`kubaos_core::state::migrate`).
- **Rollback.** Each generation links its copy of the directory to `~/.local/share/kubaos/kubaos.d`, so `<generation>/home-files/.local/share/kubaos/kubaos.d` is the directory it was built from. `kubaos package restore <generation>` puts that copy back, and empties the directory for a generation that had none. `kubaos rollback` doesn't need it: an update never changes the directory, so a rollback puts back the `flake.lock` the update saved and switches.
- **Switch jobs.** Every switch is a job in `~/.local/state/kubaos/jobs/`: `<id>.json` (`id`; `state`, one of `queued`, `running`, `succeeded`, `failed`; `queued_at`, `started_at`, `finished_at` in Unix milliseconds; `error`; `target`, what it switches to: `{"kind": "current"}`, the default, `{"kind": "release"}` or `{"kind": "checkout", "path": …}`, below) and `<id>.log`, the switch's output. Ids sort by queue time. Submitting writes the job, then starts `systemd-run --user --unit=kubaos-switch-<id> --collect kubaos job work`, passing on `PATH`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `NIX_PATH`, `LANG` and `LOCALE_ARCHIVE`. A worker takes `switch.lock` (`flock`) in that folder and runs every queued job, oldest first, each a `home-manager switch -b hm-backup --flake ~/.config/kubaos/home` (for a preview with `--override-input kubaos git+file://<checkout> --no-write-lock-file`), until none is left. A job still `running` when a worker gets the lock lost its worker, and is marked `failed`. A job records its unit as `unit` (none for `--foreground`); a job still `queued` whose unit is no longer active (`systemctl --user show -p ActiveState`), while no worker holds the lock, will never run (its program failed to start, say), and following it or `kubaos job list` marks it `failed`. So two switches never run at once, none is lost, and none waits forever. A front end follows a job by reading the two files (`kubaos_core::switch::Queue::follow`); `kubaos job follow <id>` prints the log as it grows. `--foreground` runs the queue in the calling process instead, for a session without a user manager (the test harness).
- **Live previews** (`kubaos_core::preview`). `kubaos switch --from <path|branch>` switches the home to a KubaOS checkout: a folder, or else the worktree of `~/Projects/kubaos` (the Projects root's `kubaos`) whose branch it is, from `git worktree list --porcelain`. Before queueing, it refuses a folder git can't describe and a checkout the home doesn't evaluate with (`nix eval --json <flake>#homeConfigurations` with the same override, applied to every configuration's `activationPackage.drvPath`), exit 1, nothing switched. The job's target is `checkout`. The override is `git+file://`, so the build takes the checkout's tracked files with their uncommitted changes and never an untracked `target/`; `--no-write-lock-file` keeps `flake.lock` on the release. A `checkout` job that succeeds writes `~/.local/state/kubaos/preview.json`, under the switch lock: `{"path", "branch" (null on a detached head), "commit" (the full hash), "dirty" (uncommitted changes to tracked files), "since" (Unix milliseconds of the first switch to this path, kept while the path stays)}`. A `release` job that succeeds empties the file; empty or missing is no preview, and the file stays so its watchers keep it. A `current` job (`kubaos package`, `kubaos suite`) switches to the preview the file names when it runs, refreshing its commit, else the release; it fails naming `kubaos switch --release` when the file doesn't read or its checkout is gone. `release` and `checkout` jobs never read it, so a record that doesn't read never blocks them. A folder inside a checkout previews the checkout's top. A plain `kubaos switch` while the file names a preview, and no `release` job is queued, is refused, exit 2, naming `--release` and, while the checkout is there, `--from <path>`; a `--from` while one is on replaces it. `kubaos update`, `upgrade` and `rollback`, once confirmed and before their snapshot, run a `release` switch in a `live_preview` phase and stop if the file still names a preview after it ("Updates and migrations"). The bar's pill (`config/quickshell/services/Preview.qml`, `modules/bar/PreviewIndicator.qml`) and the Extension's `kubaos.preview` state read the file. Only the home is previewed: apt, `system/`, migrations and the boot stay the release's.

### Suites

A Suite (`docs/adr/0002-suites.md`, `docs/adr/0006-suites-on-mise.md`) has two halves. Its metadata is a `kubaos_core::suites::Suite` in `crates/kubaos-core/src/suites/catalog.rs`: name, title, description, versions (the default first), extras, its mise tools, toolchain source (`Nix`, `Mise`, or an upstream manager such as rustup), cache folders under the home, user-layer files it seeds, its scaffolders, and the words that mark a user-layer file as mentioning it. Its Nix module is `home/suites/<name>.nix`, which `home/suites.nix` imports and which does nothing until `kubaos.suites.<name>` is set. A new Suite is one catalog entry plus one module.

A Suite with mise tools has them installed by mise, as Go's, Node's, Python's, proto's and Rust's are; one without any is installed by its Nix module alone, as PHP's is until it moves to mise. A tool (`kubaos_core::suites::Tool`) is mise's name for it (a registry name such as `node`, or a backend's such as `aqua:astral-sh/uv`), its request (`Request::Suite`, the Suite's chosen version, for the main toolchain; `Request::Fixed("0.13")` at major.minor precision for the rest) and the extra that turns it on, if any. Every request in a fragment is at major.minor precision, so a plain `mise upgrade` moves a tool only to its patch releases: on `add`, and on a `configure` that moves the version, the main toolchain's chosen line is written as the major.minor of its newest release (`mise latest <tool>@<line>`: Node's `24` is written `24.22`), while the record keeps the line (`24`). A line whose newest release isn't numbered major.minor.something (`nightly`), or that mise knows no release of, is written as chosen.

- **The record.** `kubaos suite add` writes `kubaos.d/suites/<name>.toml`: a header comment, `version` and `extras`. `configure` rewrites it, `remove` deletes it, each under the state directory's edit lock, and each is followed by a switch. `home/state.nix` turns each file into `kubaos.suites.<name> = { version; extras; }`. A file with a name the catalog doesn't know still installs its `packages`.
- **The fragment.** A Suite's mise tools are one file, `~/.config/mise/conf.d/kubaos-<name>.toml` (under `MISE_CONFIG_DIR` when it is set): a header comment and a `[tools]` table of `tool = "request"`, written whole under the same lock, and nothing else, so every mise setting stays the user's. mise loads `conf.d/` in name order and the user's own `~/.config/mise/config.toml` after it, so a request or setting there wins. Every call to mise goes through `kubaos_core::mise::Mise` (`crates/kubaos-core/src/mise.rs`; the real one is `mise::Cli`, the `mise` on `PATH`), run from `/`, outside any project, with `MISE_YES=1` and never `--global`.
- **Install first, write after.** `add` runs `mise install <tool>@<request>…` with nothing written. When it fails, the versions that run added (listed by `mise ls --json` before and after) are uninstalled, nothing is written, and the command exits 1. Only after it succeeds are the fragment and the record written, then `mise lock --global --platform <this machine's> <the Suite's tools…>` locks those tools in `~/.config/mise/mise.lock` (one platform, as every other platform costs a lock-time provenance check, some a GitHub API call each, and the Suite's tools only, keeping every other entry), then `mise install` runs again under the lockfile (an npm tool's entry holds its dependency graph, which mise installs to a folder of its own: without it every shell warns `missing: npm:…`), then `mise prune --tools` deletes the install the lockfile doesn't select, the user layer is seeded and the switch runs. `configure` installs first too, when the tools change: a version or an extra moves the requests, and a request in the fragment that `mise upgrade` moved stays while it is on the Suite's line (`24.22` on `24`; any request of a tool other than the main toolchain). It then writes the fragment and the record, locks, unlocks the tools it dropped (below), installs again and prunes. When the lock or the install after it fails, the fragment, the record and the lockfile go back to what they were, the versions the run added are pruned, and the command exits 1 saying the Suite is back as it was: a Suite change ends fully done or not at all. When the switch after an `add` or a `configure` of a Suite with mise tools fails, and the command waited for it (not `--detach`), the record, the fragment and the lockfile go back to what they were, or out for an `add`, mise installs what they name and the versions they no longer ask for are pruned (`Suites::restore`). A Suite without mise tools keeps its record after a failed switch, for the next one.
- **GitHub's rate limit.** mise reads release lists, checksums and attestations from its own mirror (mise-versions) first and calls GitHub's API only when that fails or a release needs it; without a token GitHub allows 60 calls an hour for everything on the machine's address. A mise call that fails on that limit is `MiseError::RateLimited`, read from mise's own log (`MISE_LOG_FILE`, a file of its own for each call at `warn`), whose message names the call, when the limit resets (mise's `GitHub rate limit exceeded. Resets at <time>`) and that a token lifts it (`GITHUB_TOKEN=$(gh auth token) kubaos …`). KubaOS neither stores nor needs a token; mise takes one from the environment or gh (`docs/USING.md`, "Suites and GitHub's rate limit").
- **Versions.** `kubaos suite list` and `show` read each installed Suite's tools from its fragment and their versions from `mise ls --json`, the entry whose `source.path` is the fragment, and print `<tool> <request>: <version>` (or `not installed`); `--json` gives `tools: [{tool, request, version, installed}]`. mise runs only when a Suite has a fragment; when it fails, the listing warns on stderr and leaves the versions out.
- **Update and upgrade** (`crates/kubaos-core/src/suites/updates.rs`, `crates/kubaos-cli/src/suite/updates.rs`). `kubaos suite update [NAME…] [--all]` reads `mise outdated --json` and runs `mise upgrade <tool…>` for the named Suites' tools that have a newer release within their request: patch releases, every fragment and record left as they are. `kubaos suite upgrade [NAME…] [--all]` reads `mise outdated --bump --json` and runs `mise upgrade --bump <tool>@<request…>`, naming each target at the request's precision (`0.13`, so for a 0.x tool a minor release is an upgrade); mise rewrites the fragment, keeping its header. A Suite's main toolchain moves too, to its newest release on a line the Suite offers (when mise's bump is on no such line, `mise latest <tool>@<line>` of each line finds the newest one that is, or there is no upgrade), and when it lands on another line the record takes that line and the upgrade switches (`--no-switch`, `--detach`, `--foreground` as for `configure`); a failed switch it waited for puts each such Suite's record and fragment, and the lockfile, back (`Suites::restore`). Both list only tools whose `source.path` in mise's answer is a Suite's fragment, so a tool the user's own config asks for (it loads later and wins) is left out, run from `/`, and run `mise prune --tools` at once, after the moved Suites' `stop_servers` commands; neither reads, rewrites or bumps a project's `mise.toml`, whose pinned versions survive the prune. Without a name or `--all`, each prints the Suites with something newer, numbered, each tool `old → new` under its Suite, and asks which to move ("1 3", Enter for all, `n` for none); with no terminal it refuses and asks for names or `--all`. `--json` only prints that list, `[{name, title, tools: [{tool, request, current, latest, target}]}]` (`target` the upgrade's new request, `null` for an update), for the named Suites or all, and changes nothing.
- **What the module may declare:** packages, `home.sessionVariables`, `home.sessionPath`, files of the Defaults it links into the home (`home.file`, read-only like every other: the Rust Suite's `~/.cargo/kubaos.toml`), an activation step that creates a tool's own settings when they're missing and needs no network (the Rust Suite's `~/.rustup/settings.toml`, and `~/.cargo/config.toml`, which includes `kubaos.toml` and is the user's from then on), links to a mise tool for a name mise can't put on PATH itself, through the tool's `latest` link in mise's installs folder, which follows every install and prune (the Rust Suite's rustup proxies, `cargo`, `rustc` and the rest, which rustup answers to by the name it is called by, and codelldb, inside its VS Code extension), and editor settings in the Defaults through `kubaos.nvim.suiteSpecs`, a list of lazy.nvim specs as Lua expressions (a LazyVim language extra is `''{ import = "lazyvim.plugins.extras.lang.go" }''`). `home/suites.nix` writes them to `~/.config/nvim/lua/kubaos/suites.lua`, which `config/nvim/lua/config/lazy.lua` loads after KubaOS's extras and before the user layer's `plugins/*.lua`, so the user's settings win. A longer list is a Lua file beside the module that returns the specs, loaded as `dofile("${./<name>.lua}")` (`home/suites/node.lua`). A Suite whose language servers and tools come from mise or Nix adds `require("config.suite_tools").on_path({ servers = …, packages = … })` (`config/nvim/lua/config/suite_tools.lua`): LazyVim starts those servers from PATH instead of installing them with Mason, Mason leaves those packages out, and Mason's `bin/` goes after PATH, so the Suite's copy wins over one Mason installed before.
- **The user layer.** A Suite never writes to a user-layer file that exists, a dangling link included. On `add` and `configure` it creates each of its seeds that is missing, with a comment on how it's loaded and a commented example, as `dot-config apply` does.
- **Removal** takes away everything the module declared, at the next switch. It first runs the Suite's `stop_servers` commands through `mise exec --` (the Rust Suite's `sccache --stop-server`: prune never deletes a version a running process uses), then deletes the record and the fragment, deletes the lockfile entries of the fragment's tools that no config asks for any more (in `mise ls --json`, a version with a `source`), with the dependency graphs they name beside the lockfile, and at once runs `mise prune --tools` (in that order: while any global config is left, prune keeps what the lockfile lists), so the versions nothing else selects are deleted before the command returns, with no network: a `mise lock` would check every remaining entry again; a folder's own `mise.toml` keeps the versions it pins. Caches are sized first and kept; `--purge-caches` deletes them (a cache inside the Projects root, or holding it, is never one). The user-layer files that mention the Suite (as a whole word, ignoring case; not `kubaos.d/`, `.git/`, links, or files over 1 MiB) are listed and left alone. Projects are never touched.
- **Scaffolding.** `kubaos suite new <name> <project>` runs a scaffolder of an installed Suite in the Projects root, with `{path}` and `{name}` filled in. It refuses a project folder that exists, and a scaffolder whose command isn't on `PATH` (a Suite whose mise tools are missing) fails naming `kubaos suite configure <name>`. The Projects root is `~/Projects` by default; `KUBAOS_PROJECTS` moves it (an absolute path, or one relative to the home; `crates/kubaos-core/src/state.rs`, `PROJECTS_VAR`), best set in the user flake as `home.sessionVariables.KUBAOS_PROJECTS`. The Command menu's project folders are its own setting (`folders` in `menu/kotodama/user.toml`), so a moved root goes there too. `kubaos suite list --json` and `kubaos suite show <name> --json` give a menu the "New <Suite> project" actions of each installed Suite.
- **The Command menu.** The KubaOS Extension sends one Item a Suite of the catalog (`crates/kotodama-kubaos/src/suites.rs`, kind `kubaos.suite`, id `suite:<name>`), so a Suite needs no entry in `config/kotodama/kubaos.toml`. Not installed, it is "Install the <Title> Suite", the description its subtitle, and its one Action runs `kubaos suite add <name>`. Installed, it is "<Title> Suite", "Installed, version <version>" its subtitle, with "Configure…" first, whose optional Arguments are the version (when the Suite has versions) and each extra by name (`on` or `off`), running `kubaos suite configure <name>` with `--version`, `--extra` and `--no-extra` for what was typed; and "Remove the <Title> Suite", confirmed first, running `kubaos suite remove <name>`. While an installed Suite has mise tools, "Update Suites…" (`suites:update`) and "Upgrade Suites…" (`suites:upgrade`) run `kubaos suite update` and `kubaos suite upgrade` in the terminal, where their pick list asks which Suites to move. An installed Suite also has one Item a scaffolder, "<label>…" (`suite-new:<name>:<scaffolder>`), whose Argument `name` runs `kubaos suite new <name> <project> --with <scaffolder>`. Each runs in the Extension's `terminal`, which shows the switch, the caches a removal keeps and the user-layer files that mention the Suite; a version or an extra word the Suite doesn't take is refused in the menu. The Items are found by the Suite's name and title, "suite", the words of its `mentions`, and the verbs of the Actions they offer. Whether a Suite is installed is its file, read with the Extension's states and again when it changes; a file that doesn't read counts as installed, with Configure and Remove. `hide` takes out any of these ids.
- **Rust and Go.** `rust`'s toolchain is `Toolchain::Upstream` (rustup); it has no versions, since a project's `rust-toolchain.toml` is its pin, and one extra, `wild`. `go`'s is `Toolchain::Mise`: its versions, the default first, are Go lines (`1.27`, `1.26`, `1.25`), and its fragment asks for `go` at the chosen line and gopls and goimports (`go:` backend, built with that Go, since neither publishes binaries), gofumpt, golangci-lint and delve (`aqua:`, release binaries) each at its own major.minor request. Its module keeps the scaffolder, `~/go/bin` on PATH, LazyVim's Go extra and `~/.config/mise/conf.d/kubaos-go_defaults.toml`, `go_set_gobin = false`, so mise leaves `GOBIN` to Go (`~/go/bin`) instead of the activated Go's own `bin`, which a patch update prunes; the user's `config.toml` loads after it and wins. It sets no Go variable (`GOPATH`, `GOBIN`, `GOFLAGS`, `GOTOOLCHAIN`). Its main tool makes it pinnable: `kubaos pin go 1.26` ("Project pins"). `docs/USING.md`, "Rust" and "Go", says what each installs.
- **Node.** `node`'s toolchain is `Toolchain::Mise`: its versions, the default first, are Node lines (`26`, `24`, `22`), and its fragment asks for `node` at the chosen line, vtsls (`npm:@vtsls/language-server`, which ships only on npm, installed by mise's npm backend on the Node beside it) and, with the `bun` extra, `bun`, each at its own major.minor request. Its module keeps the scaffolder, which runs the `node` and `npm` on PATH, LazyVim's TypeScript and eslint extras, and the JavaScript debugger (`js-debug-adapter`, nixpkgs' `vscode-js-debug`: a VS Code extension, not a release mise installs). Global installs stay out of the activated Node's and Bun's folders, which a patch update prunes, through defaults the user's own files override: `NPM_CONFIG_GLOBALCONFIG` names `~/.config/npm/npmrc`, whose `prefix` is `~/.local/share/npm` and loses to `prefix` in `~/.npmrc` or a project's `.npmrc`; with `bun`, `BUN_INSTALL` is `~/.local/share/bun`, which `[install]` in the user's bunfig overrides. Both `bin/` folders are on PATH. It sets no `NPM_CONFIG_PREFIX` or `BUN_INSTALL_CACHE_DIR`, which would win over the user's files, and leaves mise's idiomatic version files off, so a project's `.nvmrc`, `.node-version` or `package.json` doesn't pick its Node unless the user turns them on. Its main tool makes it pinnable: `kubaos pin node 22`.
- **proto + moon.** `proto`'s toolchain is `Toolchain::Upstream` (proto); it has no versions, since a project's `.prototools` is its pin, and no extras. Its fragment asks for proto alone, `aqua:moonrepo/proto` (its release binary) at `0.63`; moon is proto's, installed per workspace by the scaffolder or `proto install`, not by the Suite. Its module keeps the scaffolder, `kubaos-moon-new`, which runs the `git` and `proto` on PATH (`proto install moon --pin local`, then `proto run moon -- init`), and puts proto's shims ahead of every Suite's tools: `~/.config/mise/conf.d/kubaos-proto_path.toml`, `[env]` `_.path`, which mise's hook puts ahead of its tools in an interactive zsh; a line after mise's shims in the session variables for a login shell; and `config/hypr/env.lua`, which puts `$PROTO_HOME/shims` ahead of mise's shims while `PROTO_HOME` is set. A shim that finds no version for the folder (`.prototools` up the tree, or proto's global config) runs the next command of its name on PATH, so a project's pins win in it and the Suites' tools elsewhere. `~/.local/share/proto/bin` stays behind mise's shims. It sets `PROTO_HOME` (`~/.local/share/proto`) and `PROTO_VERSION_CHECK=0` with `mkDefault`, so the user's `home.nix` overrides either, and every path the module writes follows `PROTO_HOME`. proto pins its own version only through `proto activate`, which KubaOS doesn't run, so a project's `proto` pin applies to `proto run proto`. `proto upgrade` replaces the binary it runs from, mise's, and copies itself into `$PROTO_HOME/bin`, which proto's shims run before any proto on PATH; the user migration `proto-on-mise` installs the fragment (`kubaos_suite_to_mise proto`) and deletes a `proto` and `proto-shim` file there.
- **The test Suite**, `test`, is in the catalog only in builds with the `test-suite` feature (the harness's); its module is `home/suites/test.nix`. Its toolchains (below) are declared only while it is installed, so a real home has no entries for it. Its mise tool, `kubaos-test-tool` at the Suite's version, comes from the asdf plugin in `test/mise/`, which the harness links with `mise plugins link` first, so it installs with no network.
- **mise** comes from the curated set (`home/curated/mise.nix`), at the version the release pins, built without the `self_update` feature, so `mise self-update` refuses and points to `kubaos update`. `home/shell.nix` installs it and runs `mise activate zsh` in every interactive zsh, so before each prompt mise puts the tools of the fragments and of the folder's `mise.toml` (Project pins, below) ahead of `~/.nix-profile/bin`, and sets the folder's `[env]`. The hook's first run, the one the shell starts with, is started at the top of `~/.zshrc` and runs beside the rest of the init, which takes its output where the activation would run it; when PATH or the folder changed in between, the hook runs again instead. It is the shell's only directory hook: direnv isn't installed, and a project with a flake devshell runs `nix develop`. Only an interactive zsh runs the hook, so mise's shims folder (`$MISE_DATA_DIR/shims`, by default `~/.local/share/mise/shims`) is on the session's PATH for everything else: the last line of the session variables (`home/shell.nix`, after Nix's `nix.sh`) puts it ahead of `~/.nix-profile/bin` in every login shell, `config/hypr/env.lua` keeps it there for what the graphical session starts (Neovim from the launcher, `kubaos suite new`), and in an interactive zsh the hook's entries come before it. A shim runs mise, which picks the version the folder's configs ask for. mise remakes the shims of what it installs and prunes; each switch runs `mise reshim` too (when the folder exists), since a shim links to the mise store path that made it.

### Project pins (kubaos-core pins)

A Project pin is the main tool of a Suite (`kubaos_core::pins::main_tool`: its mise tool with `Request::Suite`) in the `[tools]` table of a folder's `mise.toml`, `node = "22"` (`docs/adr/0006-suites-on-mise.md`). mise's shell hook puts the version it selects on PATH, ahead of the installed Suite's, in the folder and below it, and takes it away outside. Only a Suite with such a tool can be pinned; any other is refused (`PinError::NotOnMise`, or `Unversioned` for a Suite without versions). The version is any request mise takes, one word of letters, digits, `.`, `_` and `-`, not only the catalog's.

- **Which pin applies** is mise's resolution: every config of the folder and the folders above it loads, and the nearest one that names the tool wins (within one folder, mise's own order of `mise.toml`, `mise.local.toml` and the rest). `kubaos_core::pins::Pins::resolve` reads it from `mise ls --current --json`, run in the folder through `kubaos_core::mise::Mise::current`, and counts as a pin each entry whose `source.path` is neither under mise's config folder (the user's `config.toml`, KubaOS's fragments) nor under `/etc`, and whose tool is a Suite's main tool. That run is the one mise call KubaOS makes in a project's folder, and it is made without `MISE_YES`, which would answer mise's trust prompt and trust a cloned project's hooks and environment unasked; a folder whose config isn't trusted fails with mise's message.
- **`kubaos pin <suite> <version> [folder]`** runs `mise install <tool>@<version>` first, from `/`, and writes nothing when it fails. It then sets the tool in the folder's config that already names it, of `mise.toml`, `.mise.toml`, `mise.local.toml` and `.mise.local.toml` in that order, or in `mise.toml`, created when missing, through `toml_edit`: the file's other entries, comments and layout stay, and a changed entry keeps its trailing comment. A linked file is written where it points, and a file keeps its mode, set before the text goes in. An entry that isn't a plain version (a table with options, a list) or a `tools` that isn't a table is refused and left to the user (`PinError::Tangled`), as is a file that isn't TOML. Then `mise ls --current` runs in the folder, which makes mise track the config, and names a config of higher precedence in the folder that wins over the one written. A config with only `[tools]` of plain versions needs no trust.
- **`kubaos unpin <suite> [folder]`** removes the tool from the folder's config that names it, the `[tools]` table too when that empties it, and deletes a file left blank; then it runs `mise prune --tools`, so the version goes unless another tracked config or a Suite's fragment selects it. With no pin in the folder's own configs, it names the config whose pin applies there.
- **Pruning.** mise records each config it loads as tracked (`~/.local/state/mise/tracked-configs`), and `mise prune` keeps every version a tracked config that still exists selects. `kubaos pin` reads the folder, so a pinned version survives the prunes `kubaos suite` runs while its file exists, before anyone has entered the folder.
- **`kubaos pins [folder]`** lists the pins in effect, each with its config, the installed Suite's version, and the exact version mise selects and whether it is installed. `kubaos pins --all` lists every pin in a config under the Projects root, 4 folders deep at most, skipping hidden folders, links and `node_modules`, `target`, `vendor`, `dist`, `build`, with mise run once per folder for its versions; a folder mise fails in (a config there it doesn't trust) shows its pins as `unresolved: <mise's reason>`, and the rest are listed. Both name each `.envrc` line nothing reads, `use suite <name> <version>` or `use bwenv <project>…` (in the `.envrc` files of the folder and above it, or under the root), with what to run instead. Both take `--json`: `pins FOLDER --json` prints `folder`, `pins` and `leftovers`, `pins --all --json` `pins` and `leftovers`; a pin is `suite`, `tool`, `version`, `config`, `installed`, `installed_version`, `selected`, `fetched` and `unresolved` (mise's reason, or `null`), a leftover `envrc`, `line`, `kind` (`suite` or `bwenv`) and `suite` and `version`, or `projects`. A path that isn't UTF-8 has its bad bytes replaced. The folder is the current one by default and may start with `~` (the Command menu passes it on as typed); a relative one, `..` included, is taken from the shell's logical `$PWD`, links unresolved.
- **The migration.** `migrations/user/1794388664-project-pins-on-mise.sh` runs `kubaos pins --migrate` (`Pins::migrate`), which reads each `.envrc` under the Projects root, as deep as `--all`, split into words as the shell would. A lone, top-level `use suite` line of a Suite with a main tool moves to the folder's config as above, unless that config pins the tool already, which wins and drops the line; a `use bwenv <project>…` line becomes `KUBAOS_BWENV = "<project> …"` and `_.source = { path = "~/.local/share/kubaos/bwenv.sh", redact = true }` in the `[env]` of the folder's `mise.toml`, unless that `[env]` sources a script already, and the file is trusted with `mise trust`. A line that is indented, inside a block or repeats a Suite stays. Each file is copied to `~/.local/state/kubaos/backups/<seconds since 1970>/<its path>` before it changes; an `.envrc` left with nothing but blank lines, comments and `source_up` is deleted, and the GC roots `use suite` made in the folder's `.direnv/suites/` go. Running it again changes nothing.
- **Portable projects.** A pin needs KubaOS. A project shared with people who don't run it pins its toolchain in its own `flake.nix` and enters its devshell with `nix develop`.

## Updates and migrations (kubaos-core update, kubaos update)

- **Records.** `/etc/kubaos/channel` is `stable` or `edge`; `kubaos channel` writes it. `/var/lib/kubaos/release` is `key=value` lines: `version`, `codename`, `commit`, `channel`, `date` (UTC). The install writes both: edge unless `/usr/share/kubaos-keys/allowed_signers` exists and a `v*` tag verified by it points at the installed commit. Without a record, `kubaos update` reads `release`'s `VERSION` and `CODENAME` and takes edge unless a verified tag is there. `/var/lib/kubaos/update-history` has one line per update, tab-separated: date, from commit, from version, to commit, to version, the saved lock (`~/.local/state/kubaos/locks/<unix time>.lock`, or empty), the saved Suite entries of mise's lockfile (`~/.local/state/kubaos/locks/<unix time>.mise.lock`, or empty; a line without the field reads as empty). `kubaos rollback` undoes the last line and drops it.
- **The `kubaos` command** comes with the release: `home/curated.nix` builds it (`crates/kubaos-cli/package.nix`) and `home/updates.nix` installs it in every home, so each switch puts the release's build at `~/.nix-profile/bin/kubaos`. `/usr/bin/kubaos` is a launcher (`install/firstboot/kubaos-launcher`) that runs that one, and the install's own copy, `/usr/lib/kubaos/kubaos`, when the home has none (root, a home not switched yet). The daily check runs the generation's store path; the switch jobs' units run the binary that submitted them, which is the home's whenever it was started through the launcher or PATH. An update keeps running the binary it started with; the next one runs the new build. The system migration `kubaos-launcher` puts the launcher on machines installed before it.
- **Kōbō's setup mode** comes with the release the same way: `home/curated.nix` builds `kobo` (`crates/kubaos-kobo/package.nix`, its windowing and GPU libraries added to the runpath) and `home/setup.nix` installs it, at `~/.nix-profile/bin/kobo`. `/usr/bin/kubaos-setup` (`install/firstboot/kubaos-setup`), which the first-boot unit, the desktop entry and the Command menu's setup Items run, runs that one, and the install's own `/usr/bin/kobo` when the home has none. `/usr/bin/kobo` stays the build the live ISO carried: the installer runs it in `cage` before any Nix profile exists. The system migration `kobo-launcher` rewrites `/usr/bin/kubaos-setup` and `kubaos-setup.service` on machines installed before it, where they exist.
- **The release policy** (`kubaos_core::update::policy`): one seam, `Policy::pick(installed, refs)`, picks the update and the upgrade from a `Refs` (`GitRefs` after a fetch, `RemoteRefs` from `git ls-remote` for the daily check). Edge takes `origin/main`'s head, which `git verify-commit` must accept against `allowed_signers` when that file exists. Stable takes the newest `v<semver>` tag of the installed series that `git verify-tag` accepts, as the update, and the newest of the next series as the upgrade. Signatures are SSH (`gpg.ssh.allowedSignersFile`). A different release scheme replaces this module only.
- **Migrations.** `migrations/system/` and `migrations/user/` hold `<unix time>-<slug>.sh` (`just migration system|user <slug>` writes one). They change config, never only packages: an apt package goes in the package manifest ("The package manifest"), which every update applies. An update runs the new release's pending ones in name order, each under `bash -euo pipefail`, from the checkout, with `KUBAOS_DIR`: system ones as root after apt, the Hyprland pin and the package manifest, before the user flake's update; user ones as the user after the switch, with `KUBAOS_USER_FLAKE` and `KUBAOS_BACKUPS` too. `migrations/lib.sh` has `kubaos_backup FILE`, and `kubaos_suite_to_mise NAME` for the release that moves a Suite onto mise: on a home with the Suite's record it runs `kubaos suite configure NAME --no-switch`, which installs the Suite's mise tools at the record's version and extras and writes its fragment, leaving the record alone (Go's is `go-on-mise`). A migration that succeeds leaves a marker named after it in `/var/lib/kubaos/migrations/` or `~/.local/state/kubaos/migrations/`; one that fails stops the update and runs again on the next. The install writes markers for every migration of the installed release. A rollback keeps the markers: migrations only go forward. A change to a file under `system/files/` comes with a system migration that installs it again; `system/files.map` names what installs each file, and `just system-files-check` holds a branch to both.
- **Bitwarden and Nix within their series** (`kubaos_core::update::bitwarden`, `update::nix`, the phases in `update/updater/bitwarden.rs` and `nix.rs`). After the `home` phase, in every update, packages-only too: the `bitwarden` phase, when dpkg has `bitwarden` at a version, asks GitHub for `bitwarden/clients`' newest 100 releases, takes the newest published (not draft, not pre-release) `desktop-v<version>` of the installed major series that is newer, downloads its `Bitwarden-<version>-amd64.deb` with curl (`--proto =https --tlsv1.2 -f`) into `~/.local/state/kubaos/downloads/`, and installs it with `apt-get install` only when its `sha256sum` is the asset's `digest` in GitHub's answer (`sha256:<hex>`); a mismatch or no digest installs nothing; the file is removed either way. The `nix` phase, when `/nix/var/nix/profiles/default/bin/nix` is there, reads its version, lists the releases of its minor from the `nix-releases` S3 bucket behind `releases.nixos.org`, and for the newest newer patch reads `releases.nixos.org/nix/nix-<version>/fallback-paths.nix`, which must give this machine's system (`x86_64-linux`, `aarch64-linux`) a `/nix/store/<hash>-nix-<version>` path; then, as root, `nix upgrade-nix --profile /nix/var/nix/profiles/default --nix-store-paths-url` that file (Nix substitutes the path from its binary cache and checks the cache's signature), checks the version again, copies the new profile's `nix-daemon.service` and `.socket` over `/etc/systemd/system`'s where they differ (as `system/60-nix.sh` keeps them: copies, never links into `/nix`), `systemctl daemon-reload` when it copied, and `systemctl restart nix-daemon.service`. A newer major series of Bitwarden, or the next minor of Nix, is a note and waits for a KubaOS release. Each phase ends `skipped` while its flag file, `U/desktop/update/no-bitwarden` or `no-nix`, exists (`kubaos update --turn-on|--turn-off bitwarden|nix` removes or makes it, as it does `no-firmware` for `firmware`; `kubaos_core::update::programs` reads and writes all three); a failure ends it `failed` with a warning, and the update goes on. `system/70-bitwarden.sh` leaves a newer release of its pin's series installed. The bw CLI stays pinned in the script; the `home` phase's check reports its new releases.
- **The Suites in an update** (the updater's `suites.rs`, `kubaos_core::suites`). In the `snapshot` phase, beside `flake.lock`, an update copies the lockfile entries (`~/.config/mise/mise.lock`, which `mise lock --global` and `mise upgrade` write) of every tool a Suite's fragment asks for to `locks/<unix time>.mise.lock`, and names it in the history; a failed copy is a warning, and the Suites' tools then stay where they are. After the `home` phase, in every update, packages-only too, the `suites` phase runs what `kubaos suite update --all` does, then reads `mise outdated --bump --json` and notes each upgrade waiting as `<suite>: <tool> <request> → <new request>` and "Upgrade them with kubaos suite upgrade". It runs only while an installed Suite has a fragment, its failure is a warning, and the summary carries `suites: {updated, upgrades, restored, error}`, each tool `{suite, tool, from, to}`. `kubaos rollback`, after its `home` phase, puts back each saved entry whose tool a fragment still asks for, at a request one of the entry's versions is on (mise keeps an entry after the last request for it goes, and selects a locked version even past its request), then runs `mise install --locked` and `mise prune --tools`; fragments and records stay as they are, so a `suite add`, `configure` or `upgrade` run after the update is kept. A version pruned since is downloaded again, checked against the entry.
- **The Hyprland pin.** On amd64, when the release's `system/files/apt/preferences.d/kubaos-hyprland` differs from `/etc/apt/preferences.d/kubaos-hyprland`, an update unholds the held stack (`system/lib.sh`'s `HYPR_HOLD_RE`), installs the pinned versions, holds the stack again, and only then writes the pin.
- **What a run reports** (`kubaos_core::update::event`). `kubaos update`, `upgrade`, `rollback`, `update --check` and `packages enable|disable` send `UpdateEvent`s to a `Sink`, and the CLI only shows them: a live view of the phases on a terminal, plain lines without escape codes elsewhere (`NO_COLOR` drops the colours of the live view), and with `--json` one event per line on stdout, an object tagged by `type` (`started`, `phase_started`, `step`, `progress`, `output`, `note`, `warning`, `preview`, `prompt`, `answered`, `phase_finished`, `available`, `summary`, `declined`, `failed`). A front end shows the same events. A `prompt` of kind `confirm` is answered with a line on stdin (empty or `y` is yes, end of input is no); one of kind `password` is `sudo -v` reading the terminal, so a front end without one passes `-y` and keeps sudo's credentials fresh itself. The phases are `checking`, `fetching`, `verifying`, `reviewing`, `live_preview` (only while the home is a live preview), `snapshot`, `system_packages`, `release`, `hyprland`, `manifest`, `system_migrations`, `inputs`, `home`, `bitwarden`, `nix`, `user_migrations`, `firmware`; each ends `done`, `skipped` or `failed`, and only those that run are sent. The `summary` is the run's last event and carries everything the terminal's summary shows, so a front end shows the same: `from` and `to` (the KubaOS release before and after, each `{version, codename, commit}`; equal when it stayed), the channel, the release's changes (below; a rollback lists none), `packages` (how many apt packages `apt-get upgrade` upgraded or newly installed), `upgraded` (those packages, one `{name, from, to}` each, as apt's simulated upgrade listed them; `from` is missing for a package new to the machine), `apt` (what the `manifest` phase installed and removed, one `{group, installed, removed}` a group), `inputs` (the user flake's inputs `nix flake update` moved), `nix_packages` (the home's Nix packages the switch changed: `nix store diff-closures` of the home-manager generation before the switch and after it, both read from home-manager's GC root `$XDG_STATE_HOME/home-manager/gcroots/current-home`, one `{name, from, to}` a package whose version changed, came in (no `from`) or went (no `to`), several versions joined with `, `, a rebuild at the same version left out; `[]` when the switch kept the generation, and missing when there was no switch, no generation to compare or the diff failed, which the log says), the migrations run, `programs` (what the `bitwarden` and `nix` phases did, one `{program, result, waiting}` each in the order they ran: `program` is `bitwarden` or `nix`; `result` is `updated` with `from` and `to`, `current` with `version`, `off`, or `failed` with `error`; `waiting` is a newer series that waits, when there is one; a phase that didn't run has none), what the session reloaded (the switch's `dot-session:` lines), `firmware` (what the `firmware` phase did, one `{device, id, from, to, reboot, outcome}` a device, the outcome `applied`, `staged`, `waiting` or `failed`; left out when it did nothing), `restart` (`none`, `relogin` or `reboot`) with `restart_reason`, the command that undoes it and the log; lists left empty and fields left unknown are left out, and a reader takes a missing list as empty. `crates/kubaos-core/src/update/event/summary.json` is a `summary` with every field set. A run that changed nothing (the release stayed; no apt, Nix, program, migration or firmware change; nothing waiting or failed; no restart) ends its terminal output on one line saying so. When nobody reads the run where it runs (no `--json`, and neither stdout nor stderr a terminal: a systemd unit, a timer, a script writing to a file), `kubaos update`, `upgrade` and `rollback` also send the summary as one notification (`notify-send --app-name=KubaOS`, `kubaos_core::update::summary`): the title names the release it ended on, or says nothing changed; the body has the reboot or re-login line and its reason first, then one line a part (apt packages upgraded, installed and removed, Nix packages changed, Bitwarden and Nix moved, failed or waiting for a release, the firmware phase's result, the migrations); urgency `normal` with a restart or a failed part, else `low`. The Command menu and the bar run updates in a terminal that stays open after the run, so they show the terminal's summary and send none. The `preview`, before anything changes, holds the same `apt` with what the `manifest` phase will install (no removals: those are known only once apt has simulated them), and `upgrades`, the apt packages `apt-get upgrade` will move, as `{name, from, to}`. Both carry the release's changes (`kubaos_core::update::changelog`), read from `git log --topo-order` of the installed commit to the target's: `main`'s first-parent history is one entry per merge or direct commit, a merge stands for the commits it brought in that aren't merges, each carrying the pull request its subject ("Merge pull request #N from …") names, and a merge's own subject is never a change; a squash-merged subject's trailing `(#N)` names its pull request too. `changes` lists them newest first as `{kind, scope, subject, breaking, pr, commit}` (`kind` is the Conventional Commit type, `feat`, `fix`, `perf`, `build`, `refactor`, `revert`, `style`, `docs`, `test`, `ci` or `chore`, or `other` with the whole subject for one that isn't; `breaking` from a `!` or a `BREAKING CHANGE:` footer; `pr` missing for a commit made on `main`; `commit` the full hash): every breaking change, then the others of kinds people read about, the first 20; `more_changes` counts those past 20 and `internal_changes` the `docs`, `test`, `ci` and `chore` ones, which aren't listed; `repository` is `origin`'s GitHub web address (from an HTTPS or SSH remote; missing for one elsewhere), and a pull request is `<repository>/pull/<pr>`. The terminal's preview lists them under Breaking (highlighted), New, Fixed, Faster, Build and Other (dimmed), each with its scope and `#N`, an OSC 8 link to the pull request while it shows colours; its summary names the first 5 in the same order.
- **Firmware** (`kubaos_core::update::firmware`, the updater's `firmware.rs`). The last phase of `kubaos update`, packages-only too, after the user migrations: `sudo fwupdmgr refresh` (the LVFS metadata; exit 2, already fresh, is fine, and a failure warns and lists from what fwupd has), `fwupdmgr get-updates --json` as the user, then `sudo fwupdmgr update <device id>` for each device whose update needs no reboot. A device fwupd flags `needs-reboot` or `needs-shutdown` installs only at the next boot: the update names it and, when it asks (in a terminal, without `-y` or `--json`), asks "Stage it now?"; a yes hands it to fwupd, which installs it at the next reboot, and the summary's restart is a reboot. Without a yes, or with nobody to ask, it only reports it, as `waiting`. Every call takes `--json --no-unreported-check --no-metadata-check --no-reboot-check`, so fwupdmgr asks nothing, uploads no report and never reboots; the update never reboots either. The phase never fails the update: a failure is a warning, and a list fwupd can't give or that doesn't read ends the phase `skipped`. Without `/usr/bin/fwupdmgr` (fwupd is in the manifest's `graphics` group) the phase doesn't run and the update warns. The flag file `U/desktop/update/no-firmware` turns it off; `kubaos update --turn-off firmware` writes it and `--turn-on firmware` removes it, as the Command menu's "Firmware updates off" and "Firmware updates on" do.
- **The run's log.** Every program's output goes to `~/.local/state/kubaos/update/<UTC date>T<time>-<command>.log`, each line with its seconds since the start, each command as a `$` line; the last 10 logs are kept. The check writes none. A failed step's event carries its last 20 lines of output and the log's path.
- **No terminal input.** Programs run with stdin closed, migrations included: a migration can't ask. apt runs with `DEBIAN_FRONTEND=noninteractive` and `--force-confdef --force-confold`, so a changed config file under `/etc` is kept and the package's new one is left beside it as `.dpkg-dist`. sudo's password is asked before a step that needs root (or runs sudo itself, as `system/relink.sh` does) only when sudo's cached credentials have run out, with the live view cleared.
- **The daily check.** The user timer `kubaos-update-check.timer` (`home/updates.nix`) runs `kubaos update --check`, which writes `~/.local/state/kubaos/update-available`: `update=`, `update-commit=`, `upgrade=`, `upgrade-commit=`, `upgrade-codename=`, `apt-security=` and `apt-security-packages=` lines, the file empty when nothing waits. Each version or commit is notified once (`~/.local/state/kubaos/notified`); each pending apt security package is notified once too, as `apt-security name=version`, and a check notifies only when the pending set gains a package not notified yet. The apt keys of packages no longer pending are dropped on every check, so the file stays as small as the pending set. The bar (`config/quickshell/services/Updates.qml`, `modules/bar/UpdateIndicator.qml`) and the KubaOS Extension (`crates/kotodama-kubaos/src/updates.rs`) watch the file: the bar's marker shows for `update`, `upgrade` or `apt-security`, and a click runs `kubaos update` unless only `upgrade` waits; the Extension's "Update KubaOS" Item adds the pending security count to its subtitle. An update empties it. The check takes the update's lock (`update.lock`) from counting to writing, and leaves the file alone when an update holds it, so a finished update's cleared count is never written back.
- **Pending apt security updates.** The check counts them without root. Ubuntu's own list refresh is retired (below), so the system's lists change only when `kubaos update` runs; the check therefore keeps lists of its own in `~/.local/state/kubaos/apt` (`kubaos_core::update::security`): `apt-get update` as the user with `Dir::State` and `Dir::Cache` moved there (sources, dpkg's status and the auto-installed marks stay the system's), then `apt-get -s upgrade --with-new-pkgs`, the same simulation the update's preview runs, counting each `Inst` line whose origins include a `-security` pocket. A candidate that comes from `-updates` alone is checked with `apt-cache policy` (one call for all of them): when a `-security` version newer than the installed one exists, the candidate carries that fix and counts. The package caches are off (`Dir::Cache::pkgcache=` and `srcpkgcache=` empty) and only English descriptions are fetched (`Acquire::Languages=none`); measured on the laptop, the folder is about 100 MiB (all of it lists, against about 250 MiB with the caches), and the simulation takes about 1 s. It never takes the dpkg lock or runs apt as root, and the folder can be deleted. `apt-get update` runs with `--error-on=any`, so a list that failed to download fails the refresh (plain `apt-get update` exits 0 with a `W: Failed to fetch`); when the refresh or apt fails the check warns and keeps the last count. The check costs one list download a day, as `apt-daily` did. What installs them is `kubaos update`: `apt-get upgrade --with-new-pkgs` takes every pocket in the sources, `-security` and `-updates` alike, and `--with-new-pkgs` brings a new kernel image and its metapackage; the summary says when a reboot is needed.
- **Ubuntu's own updaters are retired** (`retire_ubuntu_updaters` in `system/lib.sh`, run by `system/10-strip.sh` and the `retire-ubuntu-updaters` system migration): nothing starts apt unless `kubaos update` runs it. `apt-daily.timer`, `apt-daily-upgrade.timer`, `unattended-upgrades.service` and the `apt-daily` and `apt-daily-upgrade` services are stopped, disabled and masked (`unattended-upgrades.service` is not stopped while `/var/run/unattended-upgrades.lock` is held, since the stop would SIGTERM the running upgrade and wait for it, up to 30 minutes; it is still disabled and masked; the `apt-daily` services are never stopped, a running one finishes), so a package upgrade can't enable them again; `/etc/apt/apt.conf.d/99kubaos-no-periodic` (`system/files/apt/apt.conf.d/`) sets `APT::Periodic::{Enable,Update-Package-Lists,Download-Upgradeable-Packages,Unattended-Upgrade,AutocleanInterval,CleanInterval}` to 0, and sorts after Ubuntu's `20auto-upgrades`. The `unattended-upgrades` package is out of the package manifest (the `upgrades` group is gone), so an update removes it once it is recorded as installed and nothing depends on it. Ubuntu's other leftovers, checked on the laptop and decided one by one:
  - **Kept**: `fwupd` and `fwupd-refresh.timer` (it downloads LVFS metadata and installs nothing; firmware updates need it), `fstrim.timer` (SSD), `dpkg-db-backup.timer` (a daily copy of dpkg's database, cheap and useful after a crash).
  - **Already off or absent**: `motd-news.timer` and the `apt-news` and `esm-cache` services (`system/10-strip.sh` disables or masks them; the ESM line of the login motd has its exec bit off), `man-db.timer` and `update-notifier` (not installed).
  - **Left alone**: the Ubuntu Pro client's `ua-timer.timer`, `ubuntu-advantage.service` and `ua-reboot-cmds.service`, which are enabled but inert on a machine with no Pro subscription (their conditions fail, no timer is scheduled), `e2scrub_all.timer` (it finds no ext4 volume on a btrfs machine and exits at once), and the `85-fwupd` and `50-motd-news` login-motd scripts, which print a line at a console login and fetch nothing now.


## The package manifest (system/packages.toml, kubaos-core apt)

- **The manifest.** `system/packages.toml` lists every apt package KubaOS installs, in `[group.<name>]` tables: `summary`, `packages`, and optionally `arch` (the one architecture it is for), `repo` (a `[repo.<name>]`: `key_url`, `fingerprint`, `keyring`, with the sources file in `system/files/apt/sources.list.d/<name>.sources`, `@ARCH@` filled in), `hold = true` (apt-mark hold), `if_available = true` (a package with no install candidate is skipped quietly), `optional = "on"|"off"` (the user may turn it off or on; the value is its default) and `when_on`/`when_off` (the script, with its arguments, that sets up or takes down what the group needs beyond packages). The file keeps to tables, strings without escapes, booleans and string arrays: `system/manifest.sh` reads it with awk, `kubaos_core::apt::manifest` with serde, and a test holds the two to the same reading of the release's file. A group is **active** when it is for this architecture and on.
- **The choices.** `/etc/kubaos/apt-groups`, `<group>=on|off` lines, holds what the user decided; a group without a line follows its default. The scripts' flags write it (`40-apps.sh --no-docker`/`--no-chrome`, `70-bitwarden.sh --no-u2f`/`--remove-u2f`, `75-yubikey.sh --piv`/`--no-piv`, `30-hardware.sh`'s tuxedo part), and so does `kubaos packages enable|disable <group>`. The scripts take their defaults from it.
- **The record.** `/var/lib/kubaos/apt-installed`, `<package><TAB><group>` lines: each package an install script or an update installed because a group listed it and the machine lacked it. A package that was there first is never in it.
- **Install.** The system scripts install their groups with `group_install` (`system/manifest.sh`, sourced by `lib.sh`), which sets up a group's vendor repo, installs with `--no-install-recommends`, holds a held group and records what it installed. Their non-package work stays in the scripts. Outside the manifest: the kernel headers of the running kernel (`30-hardware.sh`), `make` and grub-btrfs when it isn't packaged (`20-base.sh`), and the Bitwarden desktop `.deb` (`70-bitwarden.sh`, moved on within its series by `kubaos update`, above).
- **Update.** Every `kubaos update`, packages-only too, runs the `manifest` phase against the checked-out release's manifest, after the Hyprland pin and before the system migrations: `system/apt-repo.sh` (as root) for the vendor repos of the groups with packages to install; `apt-get install` of the active groups' missing packages that have a candidate (one without is a warning, or nothing for an `if_available` group); `apt-mark hold` of the held groups' packages; and `apt-get remove` of each recorded package no group lists any more, after `apt-get -s remove` shows it takes nothing else along; one that would is kept, with a warning. A group that is off loses nothing in an update.
- **The base list.** What the system scripts install is the manifest's active groups: every group that isn't `optional`, for this architecture, and the optional ones that are on; an optional group that is off stays off. The update reads the list from the checked-out release, `/usr/share/kubaos/system/packages.toml`, the same file the scripts read, so every run installs what a release added to a script's list on a machine installed before it, with no migration. A test (`kubaos_core::apt`'s, over `system/*.sh`) fails a system script that installs an apt package outside the manifest other than the lines "Install" names, so a list outside it can't come back.
- **Turning a group on or off.** `kubaos packages enable <group>` records `on`, installs the group's packages and runs its `when_on` script; `disable` records `off`, runs `when_off` (for `u2f`, `70-bitwarden.sh --remove-u2f`, so PAM never names a module that is gone), then removes the group's recorded packages that no active group lists; one it didn't install (a machine from before the record) stays, named in a warning with the `apt remove` that takes it. A failed script puts the old choice back. Both run as a run of `UpdateEvent`s (command `packages`), under the update lock, with a log.
- **Status.** `kubaos packages status` lists each group, active or not and why, with each package's state (`installed`, `held`, `missing`, `unavailable`, `skipped` for an inactive group's missing one) and version, and the `extra` packages: recorded, installed, and listed by no group. `--json` writes the same as one object: `arch`, `groups` (`name`, `summary`, `active`, `inactive`, `optional`, `packages`: `name`, `group`, `state`, `version`, `kubaos`), `extra`.
- **Adding a package.** Put it in its group of `system/packages.toml`; the install and the next update install it. No migration.

## Other links (home/links.nix)

- Every file in `scripts/` is linked from the store (`kubaos-scripts`) to `~/.local/bin/<name>`, like the defaults. `~/.zprofile` sources the tty1 autostart snippet (`system/files/hyprland-autostart.zsh`) from the store. Scripts are executable, start with `#!/usr/bin/env bash` (or another env shebang), use `set -euo pipefail`, and are prefixed `dot-`.
- **Never** manage a path under `config/` with a `programs.<x>` option that writes the same file (for example `programs.tmux.extraConfig` or `programs.ghostty.settings`). Install the package with `home.packages` or `programs.<x>.enable` only if that option writes nothing under the linked path. If Nix needs to hand a store path to a config (tmux plugins, for example), write it to a generated file outside the app's dir, such as `~/.config/tmux-nix/plugins.conf` via `xdg.configFile."tmux-nix/plugins.conf"`, and have the config `source` it if it exists.

## The file manager (home/files.nix, crates/kubaos-files)

- The file manager is Files, apt's Nautilus (`system/20-base.sh`, with Sushi, gvfs, the thumbnailers, File Roller with 7zip and unar, and python3-nautilus). The SUPER + SHIFT + F bind and the Command menu's "Files" run `nautilus --new-window`; "Recent files" runs it on `recent:///`. Kotodama's Apps Extension hides Nautilus's own entry (`config/kotodama/kubaos.toml`); the KubaOS Extension's "Files" stands in for it.
- **Defaults.** `~/.local/share/applications/mimeapps.list` is KubaOS's and names only apps KubaOS ships: `inode/directory` → `org.gnome.Nautilus.desktop` then `kubaos-files.desktop`; the archive types Nautilus's entry lists (zip, 7z, RAR, tar and its compressed forms) → Nautilus, which extracts an archive next to itself on double-click when it is the archive's default app (Nautilus 50 has no setting for it); images → Loupe, videos (MP4, MKV, WebM, MOV, AVI, MPEG, Ogg, MPEG-TS, M4V, WMV, ASF, FLV, 3GP) → Showtime, PDF → Papers. Audio types have no default. `~/.config/mimeapps.list` is the user's and comes first in the lookup, so `xdg-mime default` and apps that make themselves default write there and win. Nothing manages it (no `xdg.mimeApps`).
- **Show in folder.** `org.freedesktop.FileManager1` is Nautilus's, from its `/usr/share/dbus-1/services` file (`nautilus --gapplication-service`). KubaOS puts no service file in `~/.local/share/dbus-1/services`, which would come first; home activation reloads the session bus's config, so a running bus forgets one an older generation linked. `kubaos-files serve` still answers the name for yazi, and is registered by nothing.
- **Settings** (dconf, `home/files.nix`): `org.gnome.nautilus.preferences show-image-thumbnails` is `always`, so phones and network shares get thumbnails; `org.gtk.gtk4.Settings.FileChooser sort-directories-first` is true. The matugen colours reach Files through `~/.config/gtk-4.0/gtk.css` (`home/theme.nix`), which libadwaita reads at start.
- **Right-click.** nautilus-python loads `~/.local/share/nautilus-python/extensions/`: `ghostty.py`, linked from the Ghostty package ("Open in Ghostty"), and `kubaos.py`, `home/files/kubaos-nautilus.py`: "Copy Path" (`wl-copy`), "Convert Image" (JPG, PNG, WebP) and "Resize Image" (50%, 25%, at most 1920 px; `magick … -auto-orient -resize`), each writing a new file next to the original and never overwriting, "Open as Administrator" on a folder (`nautilus --new-window admin://<path>`, gvfs's admin backend through polkit), and "Import Photos" on a folder that is or holds `DCIM` (`kubaos-automount import`). A command that fails says so through `notify-send`. Bulk rename is Nautilus's own (`F2` on a selection).
- **Windows.** Hyprland floats Sushi (`org.gnome.NautilusPreviewer`) large (`config/hypr/rules.lua`); Nautilus's Properties and Preferences are libadwaita dialogs inside its window.
- **yazi.** `kubaos-files open [PATH|URI]...` runs `ghostty -e yazi -- <entries>`, in a systemd scope of its own (`kotodama_extension::launch`). A path, `~`, or a `file://` URI on this machine (no host, `localhost` or the host name), percent-escapes undone; a path that doesn't exist becomes its nearest folder that does. No entry is the home folder. yazi opens a folder inside it and a file in its folder with the file hovered; several entries are tabs. The SUPER + CTRL + F bind, the Command menu's "Yazi" and "Open folder in yazi…", and the user folder Items' second Action run it. `~/.local/share/applications/kubaos-files.desktop` (Name "Yazi", `MimeType=inode/directory;`) puts it under "Open With"; the Apps Extension hides it.
- **Tidy Downloads.** `kubaos-files tidy` moves the regular, non-hidden files of `~/Downloads` (the XDG download folder) whose extension it knows into `Images`, `Documents`, `Archives`, `Installers`, `Video` and `Audio`, leaving files that arrived in the last 24 h (the later of mtime and ctime); a taken name gets ` (1)`, ` (2)`. It prints `<n> moved` and notifies. The setting is the file `~/.config/kubaos/desktop/files/tidy-downloads`: `tidy on` writes it, `tidy off` removes it, off by default. The user timer `kubaos-tidy-downloads.timer` (daily, `Persistent`) runs `tidy --scheduled`, which does nothing without the file.
- **Dragging out.** ripdrag (Nix) is the drag source; yazi's key for it is in the user layer ("Defaults and the user layer", yazi). Hyprland floats its window (`config/hypr/rules.lua`).
- **Image previews** need nothing in yazi's config: Ghostty speaks the kitty graphics protocol, which yazi detects. tmux passes it through (`allow-passthrough`, `config/tmux/tmux.conf`). nixpkgs' `yazi` brings its preview tools (ffmpeg, poppler, ImageMagick and the rest).

## Where launched apps open (home/launches.nix, crates/kubaos-launches, config/hypr/launches.lua)

- An app's window opens on the workspace it was launched from, not on the one focused when it shows. Hyprland's `misc:initial_workspace_tracking` follows only what Hyprland starts; launchers have systemd start each app as a service of its own.
- The user unit `kubaos-launches.service` (`PartOf` and `WantedBy=graphical-session.target`) runs `kubaos-launches watch`: on the session bus it calls the systemd user manager's `Subscribe` and follows `UnitNew`. A unit named as systemd's desktop conventions name an app's launch, `app-[<launcher>-]<app id>@<unique>.service` or `app-[<launcher>-]<app id>-<unique>.scope`, is an app's launch; each such unit is told once (the manager sends `UnitNew` again when it loads one again). For each, it sends `/eval dot.launches.started("<unit>", "<app id>")` to Hyprland's request socket, `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket.sock`.
- `config/hypr/launches.lua` notes the focused workspace (none for a special workspace) and makes a window rule, `workspace <id> silent` for a class equal to the app id, ignoring case. The rule is on only while that workspace exists and isn't the focused one. The window is drawn first on that workspace and the focus doesn't move; a window from an app that was already running, which hands the launch to its own process (Chrome), is caught the same way. A window whose class isn't the app id but whose process runs in the launch's unit (`/proc/<pid>/cgroup`) is moved as it maps (`window.open_early`), and the focus goes back to the window that had it. A launch ends at its first window or after 20 s. Rules take the names `launch-1` to `launch-8` in turn.
- **Setting.** `~/.config/kubaos/desktop/workspaces/no-open-where-launched` turns it off (`kubaos-launches off` writes it, `on` removes it); the service reads it at each launch, so it takes effect at once.

## Removable drives (home/automount.nix, crates/kubaos-automount)

- The user unit `kubaos-automount.service` (`WantedBy=default.target`) runs `kubaos-automount watch`, a udisks2 client on the system bus (zbus). It reads udisks2's objects at start and follows `InterfacesAdded`, `InterfacesRemoved` and `PropertiesChanged`. A block device is mounted (`Filesystem.Mount`, `auth.no_user_interaction`, so udisks2's polkit rules for the active session decide) when it has a filesystem, isn't mounted, isn't `HintIgnore`, isn't in fstab or crypttab, and its drive is `Removable` and not `HintSystem`. A LUKS device isn't unlocked: a notification, "<name> is encrypted", opens Files, whose sidebar asks for the passphrase, and the cleartext device that gives is never mounted by the service. Drives present at start are mounted too.
- **Setting.** `~/.config/kubaos/desktop/files/no-automount` turns mounting off (`kubaos-automount off` writes it, `on` removes it); the service reads it on each new device, so it takes effect at once. Eject keeps working.
- **Notifications** (`org.freedesktop.Notifications`, the shell's server): "<name> is ready" with the actions Open (also the default action, the card's main button; `nautilus --new-window <mount point>`), Import photos when the mount point holds a `DCIM` folder (case-insensitive), and Eject.
- **Drives file.** `$XDG_RUNTIME_DIR/kubaos-drives`, rewritten atomically on each change: a line per mounted removable drive, its udisks2 drive object path, its name (the label, else vendor and model, else the device file) and its mount points, separated by tabs (a tab or newline in a name becomes a space; a mount point with one is left out). The unit deletes it when the service stops. The KubaOS Extension watches it and sends an "Eject <name>" Item a line, id `drive:<last part of the object path>`, which runs `kubaos-automount eject <object path>`.
- **Eject.** `kubaos-automount eject TARGET` (a drive object path, a block device path, a device file or a mount point) unmounts every filesystem on the drive, locks its unlocked LUKS devices, then powers the drive off (`Drive.PowerOff`), or ejects it (`Drive.Eject`) when it can't be powered off. A busy filesystem leaves the drive mounted with "<name> is still in use". It notifies how it went; exit 1 puts the reason on stderr.
- **Import.** `kubaos-automount import FOLDER` copies the photos and videos under FOLDER's `DCIM` (or FOLDER itself without one; hidden entries and symlinks skipped) into `<XDG pictures folder>/<year>/<month>/`, by EXIF `DateTimeOriginal`, else `DateTime`, else the file's mtime in UTC. A file whose name and size are already in that month's folder is skipped; another file of the same name is copied as `<name> (n).<ext>`. Each copy is written under a temporary name, given the source's mtime, then renamed. The source is only read. It prints and notifies `<copied> copied, <already> already there, <failed> failed`; exit 1 when any failed.
- Exit 2 is a usage error for every command.

## Bluetooth pairing (home/bluetooth.nix, crates/kubaos-bluetooth)

- bluetoothd asks a pairing agent (`org.bluez.Agent1`) for every code a pairing needs. With none registered it pairs as `NoInputNoOutput`, so a keyboard that wants its passkey typed never pairs, and while a `Pair` hangs, bluetoothd keeps discovery suspended. The user unit `kubaos-bluetooth.service` (`Type=dbus`, `WantedBy=default.target`) runs `kubaos-bluetooth agent`, which registers `/org/kubaos/bluetooth/agent` with capability `KeyboardDisplay` and makes it the default agent (`RequestDefaultAgent`), again each time `org.bluez` reappears on the system bus. Ubuntu's `/etc/dbus-1/system.d/bluetooth.conf` (BlueZ's own) already lets any user call `org.bluez` and lets bluetoothd call `org.bluez.Agent1`; nothing in `system/` changes it.
- **Requests.** `DisplayPasskey` and `DisplayPinCode` show the code ("Type this on <device>, then Enter", with the digits typed so far) until bluetoothd's `Cancel` or the end of the pairing. `RequestConfirmation` and `RequestAuthorization` ask Pair or Cancel; `RequestAuthorization` for the device being paired from the shell is allowed without asking. `RequestPasskey` (six digits) and `RequestPinCode` (1 to 16 letters or digits) ask for input; anything else is `org.bluez.Error.Rejected`. `AuthorizeService` is allowed for a trusted device and the one being paired, rejected otherwise. A prompt nobody answers in 50 s is `org.bluez.Error.Canceled`, under bluetoothd's own 60 s limit. A new request replaces the open prompt.
- **State.** The agent writes `$XDG_RUNTIME_DIR/kubaos-bluetooth.json`, replaced atomically on every change: `{"agent": <registered with bluetoothd>, "prompt": {"id", "kind": "display-passkey"|"display-pin-code"|"confirm"|"authorize"|"passkey"|"pin-code", "device": <object path>, "name", "code": <six digits or the PIN>|null, "entered": <digits typed>|null}|null, "pairing": [<object paths>], "errors": {<object path>: <short reason>}, "rssi": {<object path>: <dBm>}}`. `rssi` is how strongly each device was last heard (`Device1.RSSI`, followed through `PropertiesChanged` and the object manager's `InterfacesAdded` and `InterfacesRemoved`); bluetoothd drops `RSSI` when a scan ends, and the agent keeps the last value until the device itself goes. A change under 6 dBm is the signal's jitter and isn't written. The unit deletes it when the agent stops. `config/quickshell/services/Bt.qml` watches it (`FileView` + `watchChanges`); no file means no agent.
- **Commands.** The shell calls the agent's session-bus service `org.kubaos.Bluetooth` (`/org/kubaos/Bluetooth`, `org.kubaos.Bluetooth1`) through `kubaos-bluetooth pair DEVICE`, `cancel DEVICE`, `answer ID yes|no [VALUE]` and `scan on|off ADAPTER` (BlueZ object paths). Exit 2 is a usage error; exit 1 puts the reason on stderr as one line, which the tab shows.
- **Pairing.** `pair` calls `Device1.Pair` and returns at once. After 90 s it calls `CancelPairing` and fails as "Timed out". A pairing that succeeds (or finds the device already paired) sets `Trusted` and calls `Connect`. One that fails keeps its reason under the device for 30 s (BlueZ's `TemporaryTimeout`), then the agent removes the device unless it got paired meanwhile, since `Pair` makes a device permanent in BlueZ before it tries. `cancel` calls `CancelPairing`; when bluetoothd has no pairing to cancel, the agent ends its own as "Cancelled". Every call to bluetoothd times out after 2 minutes.
- **Scanning.** bluetoothd keeps one discovery session per D-Bus connection and answers a second `StartDiscovery` from it with `InProgress`, even while it has that session suspended and shows `Discovering` false. `scan on` therefore calls `StopDiscovery` then `StartDiscovery`, on the agent's connection; `scan off` stops it. The Bluetooth tab scans for 20 s every 45 s while it shows, its connection form included (`config/quickshell/components/ScanPulse.qml`): bluetoothd forgets an unpaired device 30 s after it last heard it (`TemporaryTimeout`), so a longer gap would empty the list before each scan. The Wi-Fi tab keeps Quickshell's scanner on while it shows, its connection form included, and Quickshell asks NetworkManager for a scan at most every 10 s: Quickshell lists a network that isn't saved only while the scanner is on, so turning it off would drop the network the form is for. `NotReady` from bluetoothd reads "Bluetooth isn't responding. Restart it: sudo systemctl restart bluetooth"; KubaOS doesn't restart bluetoothd itself, as that needs root.
- **The tab.** Known lists the paired devices, named or not, and Nearby the rest, nearest first by their last `rssi` (from -60 dBm "Very close", from -75 "Nearby", else "Far"). A device that sends no name (BlueZ's `Alias` is then its address, dashes for the colons) is unnamed: Nearby lists the named ones, then a line counting the unnamed ones ("12 unnamed devices") with a Show or Hide button and a chevron, then the unnamed ones by their address in a drawer under the line, closed unless `bluetoothUnnamed` is true in `~/.local/state/quickshell/kubaos.json` (`config/quickshell/services/ShellState.qml`, false by default). The button flips the setting, as `qs ipc call bluetooth unnamed show|hide` and the Command menu's pair do. Show slides the drawer's edge down from the line over `medium` (`standard_decel`), uncovering rows that stay where they are, which fade in together a `micro` after it starts, over `short`; the chevron turns 180° with the edge. Hide slides the edge back up to the line over `medium` (`standard_accel`) as the rows fade out together over `short`. With reduced motion it opens and closes at once. Neither moves the line, its button or anything above it, even with the list scrolled into the drawer, and a device that comes or goes in the open drawer arrives or leaves as any row does. Neither radio list scrolls by itself: a scan that adds, drops or re-sorts rows leaves the view where it was (a `LiveList` doesn't follow its current row, and the keys bring the row they select into view), and the control center opens both lists at their top. Enter or a click on a paired device connects or disconnects it through Quickshell.Bluetooth; on a nearby one it opens the connection form, whose Pair calls `pair`, whose prompt follows the agent's for that device, and whose Cancel answers no or calls `cancel`. A new prompt opens the control center on the Bluetooth tab, with the form for its device. An adapter that is off shows a Turn on button (`Adapter1.Powered`, as the quick tile); if it is still off 4 s later, the tab says to restart bluetoothd. An rfkill-blocked adapter (`BluetoothAdapterState.Blocked`) says `rfkill unblock bluetooth`.

## Phone link (home/phone.nix, crates/kubaos-phone)

- **Opt-in.** KDE Connect (`kdeconnect-kde`, curated) ships with KubaOS, but kdeconnectd runs only while `~/.config/kubaos/desktop/phone/phone-link` exists. The user unit `kubaos-phone.service` (`Type=dbus`, `BusName=org.kde.kdeconnect`, `PartOf` and `WantedBy=graphical-session.target`) runs kdeconnectd from the store with `ConditionPathExists` on that file, so a login starts it exactly when the link was left on. KDE Connect's package isn't in the profile: its D-Bus activation file and its XDG autostart entry are nowhere the bus or a session looks, so nothing starts kdeconnectd behind the flag. The flag is in the user layer and not in `kubaos.d`: it takes effect at once, needs no switch, and the user layer is where the other on/off switches live (`files/no-automount`, `files/tidy-downloads`).
- **Commands.** `kubaos-phone on` writes the flag, then `systemctl --user start kubaos-phone.service`, and waits up to 10 s for `org.kde.kdeconnect` on the session bus; `off` removes the flag, then stops the unit. `status [--json]` prints `{"on", "running", "name", "addresses", "devices": [{"id", "name", "kind", "paired", "reachable", "wants_to_pair", "verification_key", "battery": {"charge", "charging"}|null}]}`; while the link is off it reads nothing from the bus and `name` is the host name. `accept DEVICE` accepts a pairing request, and only from a device asking (`isPairRequestedByPeer`). `send-clipboard`, `send-file PATH` (`~` expanded; a `file://` URL with everything outside the unreserved set escaped), `ring` and `unpair` take an optional phone, by id or name in any case, else the paired one in reach. Exit 2 is a usage error; exit 1 puts the reason and what to do on stderr. Every command but `status` notifies how it went (`notify-send`, app name Phone), since the menu runs them with no terminal.
- **The bus.** `kubaos-phone` and Kōbō call kdeconnectd through `busctl --user --auto-start=no --json=short`: `org.kde.kdeconnect.daemon` on `/modules/kdeconnect` (`announcedName`, `devices(false, false)`), the properties of `org.kde.kdeconnect.device` on `/modules/kdeconnect/devices/<id>` (`acceptPairing`, `unpair`), and the plugins below it (`/clipboard` `sendClipboard`, `/share` `shareUrl`, `/findmyphone` `ring`, `/battery` `charge` and `isCharging`). A device id is letters, digits and underscores, or it is refused. The laptop's addresses come from `ip -j -4 addr show scope global`, leaving out `docker*`, `br-*`, `veth*` and `virbr*`. Checked against kdeconnectd 26.04 (the curated one) and 26.08.
- **Plugins.** A device keeps only `kdeconnect_clipboard`, `_share`, `_ping`, `_battery`, `_findmyphone`, `_findthisdevice` and `_connectivity_report` (`kubaos_phone::phone::LINK_PLUGINS`), plus the names listed one a line in `~/.config/kubaos/desktop/phone/plugins` (blank lines and `#` comments skipped). `kubaos-phone restrict` turns every other plugin a device supports off (`isPluginEnabled`, `setPluginEnabled`, which kdeconnectd keeps in the device's config), for every device it knows, paired or asking; it never turns one on, so a plugin the user switched off stays off. It runs in `on`, before and after `accept`, and as the unit's `ExecStartPost`, so plugins a later KDE Connect adds are off from its first start; a failure there stops the unit. A pairing accepted from KDE Connect's own notification instead of the card is restricted at the next start.
- **The card.** Kōbō's "Your phone" card (docs/INSTALL-INTERNALS.md, "First boot") goes through the same library in process (`kubaos_core::setup::Sys::phone`).
- **Firewall.** KubaOS turns no firewall on. With one, KDE Connect needs TCP and UDP 1714-1764 and mDNS (UDP 5353) open on the local network.

## Counters (home/counters.nix, crates/kubaos-counters)

- **Files.** `~/.local/state/kubaos/counters.toml` (`$XDG_STATE_HOME/kubaos/` when set): `last` (the id of the counter changed last), `next_id`, and a `[[counters]]` table each, in their order, with `id`, `name`, `value` and either `rule` (a recurrence in its own words, `"every day at 9:00"`) with `next_reset` (RFC 3339, UTC) or `stop`. Ids are never used twice. Names are unique whatever the case and hold no tab or line break. Beside it, `counters.log`: a line a change, appended and never edited, `<time, RFC 3339 UTC>\t<id>\t<kind>\t<value after>` and a fifth field, the name, for `created`, `renamed` and `removed`; the kinds are `add`, `sub`, `set`, `reset`, `auto-reset`, `created`, `renamed` and `removed`. Removing a counter rewrites the log without its lines (a temporary file and a rename), then appends its `removed` line. A line that doesn't read is skipped. `counters.lock` is held (`flock`) by every command while it reads and writes the two.
- **Changes.** Every command takes the lock, does the resets that came due, makes its change, then appends to the log, writes `counters.toml` and the shell's state file (each through a temporary file and a rename). A value never goes below 0: −1 at 0 is refused. A counter with a stop refuses +1 at it, and a value set past it, or a stop set below the value, is the stop. Setting the value a counter has, or resetting one at 0, logs nothing.
- **Rules.** `kubaos_clock::recurrence` reads them: a day, a weekday or a day of the month with a time (midnight without one), or every so many minutes up to a day, on the clock from each midnight. The next reset is the first time on the wall clock strictly after now; a time summer time skips comes an hour later, one autumn repeats counts once, and a day past a month's end is its last day. A reset that came due is logged at the time it came due (`auto-reset`), once however many came due, and only when the value wasn't 0 already.
- **Timer.** After a change that moves the earliest next reset, the command stops `kubaos-counters-reset.timer` and starts it again at that time (`systemd-run --user --on-calendar="<UTC time> UTC"`, `AccuracySec=1s`), running `kubaos-counters tick`; without a rule it is only stopped. The timer is on the calendar, so one that came due asleep fires on resume. `kubaos-counters.service` (oneshot, `default.target`) runs `tick` at login: it does the resets missed while switched off, writes the shell's state file and arms the timer.
- **The shell's state file.** `$XDG_RUNTIME_DIR/kubaos-counters.json`, written whole after every change (a due reset included) and by `tick`: `{"last": "<name the key adds to, or empty>", "counters": [{"id", "name", "value", "stop" (0 for none), "rule" (empty for none), "next" (seconds since the epoch, 0 for none), "detail" ("Resets every day at 9:00", "Stops at 4", or empty)}]}`. The words follow the clock's time format (`U/desktop/clock/clock.toml`). A shell watches the file, as `config/quickshell/services/Idle.qml` does Keep awake's, and changes counters through the command.
- **Commands.** `kubaos-counters list|new|add|sub|set|reset|rename|rule|stop|move|remove|log|check|tick`: a NAME is one argument, matched exactly or else whatever the case. `--json` makes `list` print the state file's JSON, `log NAME [--group change|day|week|month] [--sort newest|oldest|highest]` an array of `{"at", "kind" (empty for a group), "label" ("+1", "−1", "Set", "Reset", "Auto reset"), "value" (after it, or after the group's last), "added" (+1s less −1s), "changes"}`, groups starting at local midnight, weeks on Monday, and `check RULE` `{"ok": true, "rule", "words", "next", "when": "Next tomorrow at 9:00"}` or `{"ok": false, "error", "examples"}`. `--notify` says the outcome in a toast too. A refusal exits 1 with the reason on stderr, a usage error 2.
- **The menu and the key.** The KubaOS Extension reads `counters.toml` (watched with the update check's file, settled for 200 ms) for "New counter" (`counter-new`) and an Item a counter (`counter:<id>`, kind `kubaos.counter`). It tries each change on a copy first, so a refusal reads in the menu, then launches `kubaos-counters … --notify`. "Auto reset…" pushes a list View that filters itself (`counter-reset:<id>`), answered at each keystroke. `SUPER + CTRL + code:21` runs `kubaos-counters add --last --notify` (`config/hypr/keybinds.lua`).

## System monitor (home/sysmon.nix, crates/kubaos-sysmon)

- **Engine.** `kubaos-sysmon serve`, started by the shell (`config/quickshell/services/Sysmon.qml`) for its life and restarted with a backoff, reads `/proc` and `/sys` itself; no process is spawned per sample. It writes a line of JSON a sample on stdout, `{"type":"sample","t":<ms>,"detail":<bool>,"cpu","memory","gpus","disks","io","snapshots","net","battery","fans","fanCount","hasSnapshots","quotas","top","uptime","kernel"}` (camelCase keys, `null` or `[]` where the machine has no such sensor; `fanCount`, `hasSnapshots` and `quotas` say in every sample how many fans and whether snapshots a detailed one has, and whether Btrfs quotas are on for their size, so the panel lays out their lines from its first frame), and `{"type":"alert","id","title","body","action","actionLabel"}` when an alert fires.
- **Pace.** The shell sends `{"id":n,"op":"mode","mode":"pill"|"quiet"|"popup"|"paused"}`: a light sample every 2 s for the pill (every 10 s, `quiet`, while a power stop holds background work back), a detailed one (per core, clock, fans, address, disk traffic, the top 40 processes by CPU and by memory, where a light one scanning for an alert holds five) every second while the panel is open, none while the session is locked or with the pill hidden and alerts off. Out of a pause the counters start afresh. The engine keeps its last detailed sample in memory, never on disk, and right after its reply to `popup` sends it with the newest light sample's numbers in it, marked `"cached":true` (not written to the stream file, not added to the shell's history), so the panel opens on its last readings; only the first opening after the engine starts shows placeholders. Requests on stdin, each answered with its `id`: `process` (`pid`: name, command, user, state, parent, threads, memory, start), `signal` (`pid`, `signal` `term` or `kill`; init and the monitor itself refused), `settings`, `set` (`key`, `value`). A failed one gets `{"id","error"}`.
- **Stream file.** Each sample also goes to `$XDG_RUNTIME_DIR/kubaos-sysmon.json`, replaced atomically. The KubaOS Extension answers `cpu`, `ram`/`memory` and `battery` from it while it is under 10 s old, else reads `/proc` and `/sys` itself, so the pill, the panel and the menu show one reading.
- **Alerts** (on by default): CPU over its temperature for 30 s, memory over its threshold for 10 s (naming the process holding the most), a watched disk over its threshold, the battery drawing over its threshold for 30 s while discharging. Each fires once while its condition holds, and again only once it has cleared and 10 min have passed; the shell shows it as a notification whose button runs `qs ipc call sysmon act <action>`. In the pill's pace the processes are scanned only while a CPU, memory or battery condition holds, so the alert can name the busiest. A heat or drain alert names the busiest process only when it carries a third or more of the CPU's load, and otherwise says how busy the CPU is across many processes. The drain alert offers the Power Saver stop, or opens the monitor when the power service (its `kubaos-power.json`, the `pid`'s `comm` checked) is already on Power Saver or Super Saver.
- **Sources.** CPU temperature from hwmon (`k10temp` Tctl, `zenpower`, `coretemp` package, else a thermal zone); fans from every hwmon `fan*_input`, so TUXEDO's drivers show where they expose them; amdgpu's `gpu_busy_percent`, `mem_info_vram_*` and hwmon; a discrete GPU that is runtime-suspended is listed as asleep and not read, since reading it would wake it. NVIDIA's usage needs `nvidia-smi`, so only its presence and power state show. Disks are `/`, `/home` on its own device and anything under `/media` or `/run/media`; Btrfs snapshot space comes from qgroups in sysfs and is unknown without quotas.
- **Processes from the menu.** `kill NAME` and `end NAME` list the processes whose name holds NAME, one result a name; End and Kill both ask first, then signal every process of that exact name, scanned again.
- **Commands.** `kubaos-sysmon sample` (one detailed sample as JSON), `settings` (JSON), `set KEY VALUE` (`pill`/`alerts` `on|off|toggle`, `style`, `metrics` as words, `cpu-temp`, `ram`, `disk`, `battery-draw`). Exit 2 is a usage error.

## Power stops (home/power.nix, crates/kubaos-power)

- **The stops.** Super Saver, Power Saver, Balanced, Performance and Max Performance, in that order on the slider. power-profiles-daemon stays the one profile switch other tools see: Super Saver and Power Saver sit on its `power-saver`, Balanced on `balanced`, Performance and Max Performance on `performance`. `kubaos_power::plan::Plan::for_stop` is the one place a stop becomes its settings, the CPU scheduler among them (`Scheduler::Kernel`, or `Scheduler::Lavd` in the stop's mode when `scheduler = "lavd"`; "The CPU scheduler" below); `docs/USING.md`, "Power", has the table. ppd owns the rows it sets on its profile and sets again on every power change (EPP, `balance_power` on battery and `balance_performance` plugged in for Balanced; per-policy boost; the minimum clock; the platform profile); the service writes the rest after it, so its values are the last word: every policy's `scaling_max_freq`, amdgpu's `power_dpm_force_performance_level`, `panel_power_savings` of each connected `eDP` connector, `/sys/module/pcie_aspm/parameters/policy`, each USB device's `power/control`, `iw` power saving on each Wi-Fi interface, and the charge limit (TUXEDO's `charging_profile`, else `charge_control_end_threshold`). A knob the machine lacks is skipped, and `status` says so.
- **Service.** `kubaos-power serve`, the user unit `kubaos-power.service` (WantedBy and PartOf `graphical-session.target`), follows ppd's `ActiveProfile`, UPower's `OnBattery` and display device `Percentage`, and logind's `PrepareForSleep` on the system bus, and answers one line a connection on `$XDG_RUNTIME_DIR/kubaos-power.sock` (`set STOP`, `undo`, `reload`, and `retry-scheduler`, a `reload` that also lets a LAVD systemd gave up on start again; `ok …` or `error …` back). `kubaos-power set STOP` (and `kubaos power set`) speak it; with no service, `set` changes ppd's profile alone. It replaces `$XDG_RUNTIME_DIR/kubaos-power.json` whole on every change, `{"stop","index","title","source","dropped_from","quiet","pid","refused"}`, which the shell watches (`services/Power.qml`: the slider, the bar's icon, the system monitor's `quiet` pace). Both files go when the unit stops.
- **Which stop.** Each power source remembers the stop last picked on it, battery and plugged in apart, in `~/.local/state/kubaos/power/stops.json` (`{"battery","ac","last":{"source","stop"},"dropped_from","undone"}`); before any pick, battery is Power Saver and plugged in Balanced. A plug or unplug counts once `OnBattery` has held for 3 s (a bouncing dock switches nothing), and moves to the new source's stop with a low-urgency toast. A ppd profile set from outside lands on the stop named like it, as the current source's pick, or on the source's own stop when the profile is that stop's (Super Saver's `power-saver`). A profile a program holds (ppd's `ActiveProfileHolds`, GameMode's) is followed but never remembered, and its end, ppd going back to the profile before it, returns to the source's own stop. At its start the service keeps the stop it left, when the source is the same and ppd's profile still fits it, follows ppd when it no longer does (changed while nothing watched), and takes the source's stop on the other source. The low-battery drop: at `low_battery` % or under, on battery, above the drop's stop, the stop drops there with a toast whose Undo (`kubaos-power undo`) goes back to the remembered stop; the drop is never the battery's pick, plugging in ends it, and after an Undo, or a pick made under the level, no drop comes until the next unplug. `kubaos_power::control` decides all of it, tested with fakes. The service also follows udev's GPU, screen and USB events (`udevadm monitor`) and ppd's profile changes, and once they have been quiet for a second (5 s at most after the first) writes whatever the stop lacks again: Max Performance's GPU `high`, which ppd's `amdgpu_dpm` action puts back to `auto` on a screen's arrival, and a newly plugged device's autosuspend. While a power source is on its way to counting, that check waits for it: the new source's stop writes everything. `kubaos_power::control::Recheck` decides when. The runtime file names the service's `pid`; the shell checks `/proc/<pid>/comm`, so the file of a service killed outright isn't taken for a running one.
- **Root.** The writes go through `/usr/local/libexec/kubaos-power-write` (`system/files/power/`), run as `pkexec --disable-internal-agent` with only the knobs that differ, as `knob=value` arguments: `cpu-max=KHZ|max`, `gpu-dpm=CARD:LEVEL`, `panel-power=CONNECTOR:0-4`, `aspm=POLICY`, `usb=DEVICE:auto|on`, `wifi=INTERFACE:on|off`, `charge-profile=PROFILE`, `charge-end=BATTERY:PERCENT`, `scheduler=powersave[:CPUS]|autopilot|performance|off|reset` ("The CPU scheduler" below), `yields=on|off` and `unyield=PID[,PID…]` ("Background work yields" below). It checks each name and value against its own patterns and that the device exists, writes only what differs, never sets `auto` on a device with a HID, smart card or audio interface or Yubico's vendor id, and goes on past a knob that fails, an unreadable file included, naming it on stdout as `failed KNOB=VALUE` (exit 1 then, 2 for a usage error). The service leaves a refused knob alone until the stop or the settings change, and `kubaos power status` says which the kernel refused. The stops keep printers, CDC network adapters and Realtek's USB Ethernet (docks' r8152) awake too. pkexec is `/usr/bin/pkexec`. polkit action `org.kubaos.power.write` (`org.kubaos.power.policy`, `auth_admin_keep`); `50-kubaos-power.rules` lets a local, active member of `sudo` or `admin` through without a password, as the keyboard's rule does: polkit counts the user manager's processes in the user's display session (`sd_uid_get_display`), and with no agent to ask, pkexec would refuse without one. `install_power_helper` (`system/lib.sh`) installs them from `system/30-hardware.sh` and the `power-helper` system migration, with `/etc/modprobe.d/kubaos-amdgpu.conf` (`amdgpu freesync_video=1`; `update-initramfs -u -k all` while the initramfs of any kernel in `/lib/modules` lacks it, so a failed rebuild is tried again), and on the first install and in the migration only (`install_power_helper --actions`), ppd's `amdgpu_dpm` action on and its `amdgpu_panel_power` action off: that one rewrites `panel_power_savings` at every battery percent, and the stops own it.
- **The CPU scheduler.** On by default (`scheduler = "lavd"`); `scheduler = "kernel"` leaves Linux's EEVDF. scx_lavd (nixpkgs' `scx.rustscheds` 1.1.4, only its `scx_lavd` copied out as the curated `scx-lavd`, `home/curated.nix`) runs as root from the system unit `kubaos-scx.service` (`system/files/systemd/`), `ExecStart=/usr/local/libexec/kubaos-scx-lavd $LAVD_ARGS` with `EnvironmentFile=/var/lib/kubaos/scx-lavd.env`, `Restart=on-failure`, `RestartSec=2`, `StartLimitBurst=3` in `StartLimitIntervalSec=5min`, conditioned on `/sys/kernel/sched_ext` and the env file. No `scx_loader`. Modes by stop: Super Saver `--powersave --cpu-pref-order …` (the CPUs from slowest core to fastest by `amd_pstate_highest_perf`, else ACPI CPPC's `highest_perf`, each core's threads side by side: `4,16,5,17,…,11,23,0,12,…,3,15` on the HX 370; plain `--powersave` where the cores are all alike), Power Saver `--powersave`, Balanced `--autopilot`, Performance and Max Performance `--performance`. LAVD's own powersave order sorts by last-level cache before capacity without an energy model, which would start on the Zen 5 cores; its `--autopower` follows ppd's three profiles, with no autopilot and no core order, so a mode change is a restart, EEVDF running for that moment. The helper's `scheduler=MODE[:CPUS]` checks the mode, that CPUS (powersave only) are distinct CPUs that exist, that `/sys/kernel/sched_ext` and the binary are there; writes the env file (`KUBAOS_SCHEDULER=` the value, `LAVD_ARGS=` the command line; mode 0644, the service reads it back) when it differs; enables the unit; and starts it, or restarts it when the mode changed, after `reset-failed` so that starts asked for never count towards the start limit; a unit waiting to restart after a crash (`SubState=auto-restart`) is left alone when the mode is the same, so stops during a crash loop never grant it fresh restarts. A unit systemd gave up on (`failed`) is never started: its new mode is kept and the knob fails until `scheduler=reset` (`reset-failed`). `scheduler=off` removes the env file, then `disable --now`s the unit and resets a failure. The service sends `scheduler=` only at a stop or a settings change, last, never on a recheck: `off` while the env file names a mode or LAVD runs, the stop's mode when sched_ext and the binary are there and LAVD doesn't run or runs another mode, preceded by `reset` after `retry-scheduler`. "LAVD runs" is `/sys/kernel/sched_ext/state` `enabled` with `root/ops` starting `lavd`. The kernel ejects a BPF scheduler that errors or stalls and goes back to EEVDF by itself; scx_lavd then exits with an error (or a signal kills it) and the unit restarts it. The service `Subscribe`s to systemd on the system bus and follows the unit's `PropertiesChanged` (`LoadState`, `ActiveState`, `SubState`, `Result`, `NRestarts`), and while LAVD is on toasts the moment the unit enters `auto-restart` (normal urgency; it promises no restart, since the crash that reaches the start limit enters `auto-restart` too) or `failed` (critical), and logs it; a unit found that way at the service's start is said too. A clean exit (SysRq-S) is no fallback and stays stopped until the next stop. `install_scx` (`system/lib.sh`, from `system/60-nix.sh` and `system/relink.sh`, so every update and rollback) builds `.#scx-lavd`, pins it with the GC root `/nix/var/nix/gcroots/dotfiles-scx-lavd`, links `/usr/local/libexec/kubaos-scx-lavd` to it, installs the unit (`daemon-reload` when it changed) and restarts a running LAVD on a new build or unit file, after `reset-failed`; it never enables the unit. The `sched-ext-lavd` system migration reinstalls the helper. Secure Boot: Ubuntu's kernel has `CONFIG_SCHED_CLASS_EXT=y` and BTF, and lockdown `integrity` restricts no BPF feature scx_lavd uses, so nothing is signed.
- **Background work yields.** On by default (`background_yields = true`), under either scheduler: nice is the lever, as scx_lavd weighs a task by its nice and ignores cgroup `cpu.weight`; nothing goes to `SCHED_IDLE` or the idle I/O class, whose starved holder of a lock (the Nix store's) would stall whatever waits on it. Two parts (`kubaos_power::yields`). The user's build tools: the service's watch, a thread of `kubaos-power serve`, reads `/proc/loadavg`'s last PID every 2 s and, when a process started since, the new processes' `/proc/PID/stat`; each of the user's processes whose `comm` is a rule (`cargo`, `rustc`, `rust-lld`, `make`, `gmake`, `ninja`, `cc`, `c++`, `gcc`, `g++`, `cc1`, `cc1plus`, `as`, `clang`, `clang++`, `ld`, `ld.bfd`, `ld.gold`, `ld.lld`, `ld.mold`, `lld`, `mold`, `collect2`, `go`) and runs below nice 19 has every thread put at nice 19 (`setpriority`, which needs no root), and what it starts after inherits it. Nix's builds: the helper's `yields=on` writes `/etc/systemd/system/nix-daemon.service.d/kubaos-yields.conf` (`Nice=19`, `IOSchedulingClass=best-effort`, `IOSchedulingPriority=7`, `CPUWeight=10`; mode 0644), `daemon-reload`s so the weight reaches the running unit, and puts each thread of the unit's cgroups below nice 19 at 10 with that I/O priority; `yields=off` removes the drop-in, reloads, and puts the unit's threads at nice 19 back to 0 with their I/O priority following nice. The service sends `yields=` at a stop, a settings change and a recheck when the drop-in's presence differs from the setting, on a machine with `/etc/systemd/system/nix-daemon.service`. Turning it off: the watch stops, then sends `unyield=` with the user's processes at nice 19 that are a rule's or nix-daemon, or descend from one (the same set the report counts); lowering a nice takes root, as `RLIMIT_NICE` is 0, so the helper puts each thread of each at nice 19 back to 0 after checking the process is `PKEXEC_UID`'s. A thread at another nice was set by someone else and is left. Audio (PipeWire's data loops, real-time through rtkit) and the kernel's display threads (FIFO 50) already outrank any nice, and Hyprland and Quickshell stay at nice 0. `kubaos power scheduler` and "CPU scheduler: status" add the rows "Background work yields", "Build tools" (the rules), "Nix's builds" (whether the drop-in is in place) and "Yielding now" (the processes at nice 19 under a rule, by name and count).
- **Suspend.** Whatever the stop, a suspend (or hibernation) starts from sleep-safe values: Performance's and Max Performance's ASPM `performance`, GPU `high` and USB devices kept `on` keep an AMD laptop out of s0i3, and the one after a failed s0i3 tends to fail too. systemd-sleep runs `/usr/lib/systemd/system-sleep/kubaos-power` (`system/files/power/kubaos-power-sleep`, installed by `install_power_helper`, the one folder systemd-sleep reads) with `pre` as root, after systemd has frozen the user sessions, so the service can't write in between; it runs `kubaos-power-write --sleep-safe`, which writes `/sys/module/pcie_aspm/parameters/policy` `default` where it is `[performance]` (the firmware's own setup, L1 substates included, the policy Balanced reaches s0i3 from; `powersave` would turn off substates the firmware set), `auto` to each amdgpu card's `power_dpm_force_performance_level` that is `high` or a `profile_*` level, and `auto` to `power/control` of each USB device that is `on`, except those the helper never autosuspends (HID, smart card, audio, Yubico); the saver stops' `powersave`, `powersupersave` and `low` stay. Wi-Fi power saving isn't touched: mac80211 stops the card for a suspend without Wake-on-WLAN. It prints one line, `kubaos-power-write: sleep-safe: KNOB=VALUE…` or `… nothing to change`, in the journal of `systemd-suspend.service`; a missing knob is skipped, a refused write is said on stderr, and the hook always exits 0, so nothing fails the suspend. `post` does nothing. The service, on `PrepareForSleep(true)`, writes nothing until `PrepareForSleep(false)` (a stop's writes asked in between wait), then checks the stop's writes as after a device event, a second after the wake's last device event and 5 s at most, waiting for a power source on its way to counting: the stop of the source it woke on puts back everything the hook changed. Without logind the stop's values come back at the next device event or stop.
- **The laptop panel.** The service writes `refresh=60|native` and `vrr=0|1` to `$XDG_RUNTIME_DIR/kubaos-power/panel` and runs `hyprctl -i <instance> eval 'dot.power_panel()'`; `hyprland.lua` runs it after the user layer at every config load, so a reload keeps the stop. **VRR** goes through the global `misc:vrr` (`hl.config`), never the panel's rule: Hyprland 0.56 leaves a running screen alone when its new rule differs only in `vrr` (`CMonitorRule::compare` doesn't read it), while `misc:vrr`'s refresh runs `ensureVRR` on every screen, an adaptive-sync commit with no modeset. So `config/hypr/monitors.lua` gives the panel (`eDP-1`) a rule of its own with no `vrr`, and wraps `hl.monitor` to give every other output's rule `vrr = 0` unless the user's names one: the stops never reach an external screen, and `misc:vrr` belongs to them. Without the service's file the panel starts with VRR. A Hyprland whose screens were set up before these rules keeps `misc:vrr` off until it starts again (its first config load, before any screen, leaves `$XDG_RUNTIME_DIR/kubaos-power-vrr-<instance>`). **The rate** goes through the panel's own rule, which `hl.monitor` merges into by output name: `dot.power_panel()` sets only `mode`, the rule's size at 60 or the config's own mode back, so position, scale and the rest stay. 60 Hz is asked for only when `/sys/module/amdgpu/parameters/freesync_video` is on, where amdgpu's FreeSync video mode keeps the native timing and stretches the vertical blank, so the switch is seamless; without it Super Saver keeps the native rate with VRR, and `status` says the 60 Hz waits for a reboot. A panel the lid turned off stays off.
- **Battery history.** The service keeps `~/.local/state/kubaos/power/history.jsonl` (`kubaos_power::history`), mode 0600, one JSON object a line, oldest first; no process name leaves the machine. A line that doesn't read is skipped, and a service start ends a line a crash cut. Three types, each with `at` in seconds since the epoch; a field with nothing to say is left out:
  - `{"type":"sample","at","percent","wh","watts","stop","lid_closed","panel_on","brightness","keep_awake","docked","cpu","wakers":{"secs","irqs":[[name,rate]],"procs":[[name,rate]]}}`: a minute on battery. `wh` is `energy_now`, else `charge_now` at `voltage_min_design`, since the gauge's percent can jump at low charge. `panel_on` is the eDP connector's `dpms`, `brightness` the backlight in percent, `docked` a connected screen other than the panel, `cpu` the percent of all threads busy since the sample before. `wakers` is on each tenth sample only: the top five interrupt lines and processes (by name, their pids summed) in wakeups a second over `secs`, from `/proc/interrupts` and every thread's context switches.
  - `{"type":"sleep","at","end","trigger","percent_before","percent_after","wh_before","wh_after","charger","watts","percent_per_hour","hw_sleep_us","last_hw_sleep_us","hw_share"}`: a suspend, from logind's `PrepareForSleep(true)` to `(false)`. `trigger` is `lid` when the lid was closed, else left out: logind doesn't say why. The first reading is taken on the signal's own thread, before systemd-sleep freezes the session; the second 5 s after the wake, past the 3 s a power source takes to count, so a charger plugged in during the sleep shows. `charger` is true when the battery wasn't discharging at either end or its charge rose, and `watts` and `percent_per_hour` are left out then. `hw_sleep_us` is the difference of `/sys/power/suspend_stats/total_hw_sleep` across it, in microseconds, `last_hw_sleep_us` that file's `last_hw_sleep` (the most recent suspend's), and `hw_share` the first over the sleep's length, from 0 to 1. All but `last_hw_sleep_us` are left out, meaning unknown and never 0 %, when the files are missing (the kernel shows them with S0 low-power idle only), `max_hw_sleep` is 0 (no driver reports here) or the sleep outlasted `max_hw_sleep`, which the reference laptop has at 2^64 - 1.
  - `{"type":"event","at","what","detail","percent"}`: `what` is `service-start` (a boot or a restart; `detail` the stop), `plug`, `unplug`, `stop` (`detail` the stop), `low-battery` (`detail` the stop it left), `lid-open`, `lid-closed` (UPower's `LidIsClosed`), `keep-awake-on` or `keep-awake-off` (`$XDG_RUNTIME_DIR/kubaos-keep-awake.json`, read at each sample, lid move and plug, so on battery within a minute).
  - **Cost.** A timer runs only while on battery and awake, once a minute. A sample spawns nothing and asks nothing on the bus: it reads about 30 small files under `/sys`, `/proc/stat` and the Keep awake file (120 µs on the reference laptop) and appends one line without `fsync`. Each tenth also reads `/proc/interrupts` and every thread's `status` (33 ms over 2,900 threads). Past a day the service reads the file's first line; only when the oldest entry is over 97 days old does it stream the file to a new one, keeping the last 90 days, so a rewrite comes about weekly. A write that fails is logged once and otherwise ignored.
  - **The toasts** (`kubaos_power::recorder`, off with `battery_notes = false`, `kubaos power battery-notes off`), `notify-send` with a "Battery report" button, which runs `ghostty --class=dot.float --wait-after-command=true -e kubaos power report` through `hyprctl -i <instance> dispatch`: a sleep over 30 min with under half of it in hardware sleep, a known share and no charger, 5 s after the wake; a stretch over 1 h awake with the lid closed on battery, when the lid opens or on the next resume, naming Keep awake only if it was on during the stretch. A plug ends the stretch, and its toast waits for the lid.
  - **The report.** `kubaos power report [--days N] [--json]` (`kubaos_power::report`, default 7 days, at most 90): stretches of 30 min or more, from the sleep entries and the runs of samples with the same lid and under 3 min apart, what went wrong first, each newest first; the average watts by stop and lid; and the top eight interrupt lines and processes, each count weighted by its `secs`. `--json` prints `{"days","since","until","stretches":[{"kind","start","end","percent_before","percent_after","lost_percent","lost_wh","watts","percent_per_hour","deep_percent","keep_awake","charger","went_wrong"}],"averages":[{"stop","lid_closed","watts","minutes"}],"irqs":[{"name","rate"}],"procs":[{"name","rate"}]}`, `kind` being `asleep-deep`, `asleep-shallow`, `asleep-unknown`, `awake-lid-closed` or `awake-lid-open`.
- **Background work.** The system monitor samples the pill every 10 s in the saver stops, and the file indexer is held paused through `localsearch inhibit sleep infinity` in the transient user unit `kubaos-power-quiet` (stopped to resume, and with the service). Nothing starts the indexer in this session: Ubuntu's autostart entry names other desktops and `localsearch-3.service` is `static`, so it runs from the first time a program activates `org.freedesktop.LocalSearch3` on the session bus, and `localsearch inhibit` fails at once while that name has no owner, without activating it. So the service follows the name (`NameOwnerChanged`, `kubaos_power::indexer`): the hold starts when the name appears on a saver stop, is looked at again 1 s later in case the indexer wasn't ready for it, and stops when the name goes, since the pause lives in the indexer and a hold outliving it would pause nothing. `status`'s "Background work" row asks the indexer itself: no owner is `indexer not running`, which agrees with every stop; otherwise `GetPauseDetails` (never auto-starting it) says `indexer paused` or `indexer running`, and `✗` marks one the stop doesn't want. `localsearch status` does activate it.
- **The critical battery.** UPower decides the power-off, as Ubuntu's `/etc/UPower/UPower.conf` has it, unchanged by KubaOS (`UsePercentageForPolicy=true`, `PercentageAction=2`, `CriticalPowerAction=HybridSleep`). At 2 % or under while discharging, UPower's display device turns to its action level and 20 s later (`UP_DAEMON_ACTION_DELAY`) UPower calls logind's first available of HybridSleep, Hibernate and PowerOff; leaving discharging within the 20 s calls it off, and a boot already there starts the 20 s when UPower starts. Under Secure Boot's kernel lockdown hibernation is restricted, so logind's `CanHybridSleep` and `CanHibernate` answer `na`, UPower's `GetCriticalAction` says `PowerOff`, and the machine powers off, an orderly shutdown with no state saved. `kubaos-power` warns before that: at `critical_warning` % or under on battery (default 5, 3 to 20, or `"off"`; `kubaos_power::control`), a critical toast (`kubaos_power::warning`, "Battery at N %", naming the 2 %, or "within seconds" at 2 % or under) and `~/.local/share/kubaos/power/critical.oga` through `pw-play` (`home/power.nix`, the freedesktop theme's `dialog-warning`). It fires once a discharge: a plug-in that holds for the 3 s resets it, so the next unplug under the level warns again, and starting under the level warns at the first reading. What it has fired is held in the service's memory, not `stops.json`: a new boot or a restart of the service on an empty battery warns anew. The service doesn't pause while the session is locked, so the sound plays; the lock surface shows no toasts, so the toast is there at the unlock, a critical one staying until dismissed. A toast the shell isn't up to take yet (a boot) is offered every 2 s for a minute. The toast's words say power off whatever `GetCriticalAction` says.
- **Commands.** `kubaos power` runs `kubaos-power`: `set STOP`, `undo`, `status` (every row, what the stop wants and what the machine says now, `✗` where they differ, and what this machine lacks), `measure [--seconds N]` (default 120: the battery's average draw sampled every second from `/sys/class/power_supply`, and the top ten interrupt lines and processes by wakeups per second, from `/proc/interrupts` and each process's context switches; saved in `~/.local/state/kubaos/power/measure/<time>-<stop>.txt`), `report [--days N] [--json]` and `battery-notes on|off` ("Battery history" above), `panel-power-saving on|off`, `charge-limit 80|90|100`, `low-battery power-saver|super-saver|off|PERCENT`, `critical-warning PERCENT|off`, `panel STOP 60hz|vrr|native`, `apply`, `scheduler [status]` (which CPU scheduler runs and why, the mode in this stop, the unit's state and scx_lavd's last `Error:` line this boot from its journal, read with the `adm` or `systemd-journal` group, then what background work yields), `scheduler on|off` (writes `scheduler`, then `retry-scheduler` or `reload`), `background-yields on|off` (writes `background_yields`, then `reload`). `status` has a "CPU scheduler" row with the same why. Exit 1 is a refusal, 2 a usage error.
- **Command menu.** An Item a stop (`super-saver`, `power-saver`, `balanced`, `performance`, `max-performance`, the middle three the old toggles' ids), the Extension's own "Power: what this stop does" (`power-status`, the rows as a List View), "Undo the low-battery drop", the low-battery drop's three stops and level, the critical-battery warning on, off and at a level (`critical-warning-on`, `critical-warning-off`, `critical-warning-level`), panel power saving on and off, the charge limit at 80, 90 and 100 %, "Measure power draw" (for 2 minutes, or as long as typed), "Battery report" (`battery-report`, `kubaos power report` in a terminal), "Battery toasts off" and "Battery toasts on" (`battery-notes-off`, `battery-notes-on`), "CPU scheduler: LAVD on" and "CPU scheduler: LAVD off" (`cpu-scheduler-lavd-on`, `cpu-scheduler-lavd-off`), and "Background work yields: on" and "Background work yields: off" (`background-yields-on`, `background-yields-off`, shown by `power.background-yields`), in `config/kotodama/kubaos.toml`; the Extension's "CPU scheduler: status" (`cpu-scheduler-status`, the report as a List View: what runs with why under it, then a row a detail, background work's rows among them); and its "What's draining the battery" (`battery-drain`, a List View: the draw now with the stop under it, then the top three processes and interrupt lines, from the history's last count when it is under 20 min old, else measured for a second; plugged in, it says so and measures nothing).

## Proxy (home/proxy.nix, crates/kubaos-proxy)

- **The profile.** `~/.config/kubaos/desktop/network/proxy.toml` (seeded from `user-layer/desktop/network/proxy.toml`, every part commented out): `[tunnel]` `type` (`wireguard` or `openvpn`; a profile without it is `wireguard`, so a profile from before the key reads as it did), `conf` (the VPN's config beside it without its secrets; `kubaos-proxy import` writes it and these two keys), `kill_switch` (default true), `allow_local_network` (default true; `kubaos-proxy lan on|off` sets it, `toml_edit`, comments kept) and `vault_item` (default `kubaos-proxy`); `[dns]` `servers` and `domains`; `[http]` `proxy` (`http://` or `https://`, a host and a port, nothing else: no user, password or path), `pac` (`http(s)://`, no quotes, backslashes or spaces) and `no_proxy` (always led by `localhost`, `127.0.0.1`, `::1`); `[ca]` `file` (PEM, at most 64 KiB). An unknown key or type, a value outside its pattern, or `[dns]` without a VPN refuses the whole profile; no file is no part. The config's own DNS (WireGuard's `DNS =` addresses and names, OpenVPN's `dhcp-option DNS` and `DOMAIN`) counts as `[dns]` servers and domains. A WireGuard VPN is a full tunnel when any peer's `AllowedIPs` has `0.0.0.0/0` or `::/0`; an OpenVPN one when the config has `redirect-gateway` or a `route`/`route-ipv6` to every address.
- **On and off.** `kubaos-proxy on` puts the parts up in this order and `off` takes them down in the other: the VPN; the root helper's parts; the session's variables; GNOME's proxy; Docker's client proxy; git's. A part that fails takes every part before it (and itself) away again, so the Proxy is wholly on or off; `off` that fails to take a part away puts the ones it took down back. What is up is `~/.local/state/kubaos-proxy/applied` (a part a line), written after each part, so it outlives a crash or a reboot. A part is written there before it goes up. Taking a part away removes whatever of it KubaOS put there, whatever the profile says now, and puts back what the user had ("The session" below). The session lock is `$XDG_RUNTIME_DIR/kubaos-proxy/lock`; `$XDG_RUNTIME_DIR/kubaos-proxy/wanted` exists while the user wants it on.
- **The VPN.** A NetworkManager connection made at every `on` through `AddAndActivateConnection2` with `persist=volatile`, id `kubaos-proxy`, `autoconnect=false`, `permissions=user:$USER`, of the profile's type (`kubaos_proxy::tunnel`):
  - **WireGuard**: a `wireguard` connection on interface `wg-kubaos`, `wireguard.fwmark=0x6b6f`, the `.conf`'s addresses (`manual`), MTU, listen port and peers (endpoint, allowed IPs, keepalive); the private key and each preshared key are in the call with flags `1` (agent-owned).
  - **OpenVPN**: a `vpn` connection of NetworkManager's OpenVPN plugin (`network-manager-openvpn`, `service-type` `org.freedesktop.NetworkManager.openvpn`), over NetworkManager's primary connection, else the first active one that isn't the loopback's or a VPN, which it needs to base a VPN on. `vpn.data` has `dev=tun-kubaos`, `dev-type=tun`, `connection-type` (`tls` with a certificate and key, `password` with `auth-user-pass` alone, `password-tls` with both), `remote` (each server as `ADDRESS:PORT:PROTO`, joined by `, `), and what the config sets of `remote-random`, `cipher`, `data-ciphers`, `data-ciphers-fallback`, `auth`, `tls-cipher`, `tls-version-min` (with `tls-version-min-or-highest`), `tls-version-max`, `remote-cert-tls`, `ns-cert-type`, `verify-x509-name` (`TYPE:NAME`, `subject` when the config names no type), `comp-lzo`, `compress`, `allow-compression`, `float`, `tunnel-mtu`, `mssfix`, `fragment-size`, `reneg-seconds`, `ping`, `ping-restart`, `ping-exit` (`keepalive A B` is `ping=A`, `ping-restart=B`) and `connect-timeout`; with `auth-user-pass`, `username` and `password-flags=1`, the password in `vpn.secrets`; for an encrypted key, `cert-pass-flags=1` and its passphrase in `vpn.secrets`. The plugin takes the CA, the certificate, the key and the `tls-auth`, `tls-crypt` and `tls-crypt-v2` keys as files alone (`ca`, `cert`, `key`, `ta` with `ta-dir` from `key-direction`, `tls-crypt`, `tls-crypt-v2`): `on` writes them from the keyring into `$XDG_RUNTIME_DIR/kubaos-proxy/vpn/` (mode 0700, each file 0600, in memory), the plugin copies each, read as the connection's user, into a file of its own only root reads, and `kubaos-proxy` removes the folder as soon as the activation ends, up or failed, and at `off`. `ipv4` and `ipv6` are `auto`, with the config's `route` and `route-ipv6` lines as `route-data`; a split tunnel has `never-default=true`, so it carries the server's pushed routes and its own but never the default route, even one the server pushes.
  - **Servers by address.** Each server's name (a WireGuard endpoint, an OpenVPN remote) is resolved by `kubaos-proxy`, and NetworkManager is given the address, kept in `~/.local/state/kubaos-proxy/endpoints` (`HOST PORT ADDRESS` lines): with the kill switch up (a VPN coming back, a second `on`) the kept address goes first, with no lookup; a name that doesn't resolve uses it too. A WireGuard VPN prefers the family of its own addresses, an OpenVPN one IPv4 unless every remote is `udp6`/`tcp6`.
  - **The secret agent.** NetworkManager saves the agent-owned secrets nowhere, not even in its profile under `/run`, and asks a secret agent for them as it activates the VPN. `kubaos-proxy` is that agent for as long as it brings the VPN up, and only then: it serves `org.freedesktop.NetworkManager.SecretAgent` at `/org/freedesktop/NetworkManager/SecretAgent` on a bus connection of its own, registered with `AgentManager.Register("org.kubaos.proxy")` before the call and unregistered once the VPN is up or has failed. Each `on` gives the connection a fresh `connection.uuid` (`/proc/sys/kernel/random/uuid`), and the agent answers `GetSecrets` only when NetworkManager's bus name sent it, for that uuid and id `kubaos-proxy`, and for the setting the secrets are in: `wireguard` (`private-key`, and `peers` with each `public-key` and its `preshared-key`) or `vpn` (`secrets`: `password`, `cert-pass`). Any other request gets `org.freedesktop.NetworkManager.SecretAgent.NoSecrets`, and `SaveSecrets` and `DeleteSecrets` do nothing (`kubaos_proxy::agent`). That is every time NetworkManager asks: WireGuard re-keys in the kernel with no secret asked, OpenVPN's renegotiation takes what the plugin was given, and the connection is volatile and never starts by itself, so every activation, at `on` or when `serve` brings it back, is one `kubaos-proxy` makes. NetworkManager waits at most 20 s for a WireGuard VPN and 60 s for an OpenVPN one, and deletes the connection when it goes down.
  - **DNS.** The work DNS rides on it: `dns-data` per family and `dns-search` as routing domains (`~corp.example.com`) on the first family with both an address and a server (an OpenVPN VPN's addresses come from its server, so the first with a server), which NetworkManager hands to systemd-resolved for the VPN's link alone; a full tunnel with servers adds `~.` and `dns-priority=-50`, so every name goes to the work servers. NetworkManager drops it when the machine sleeps.
- **Secrets.** `kubaos-proxy import FILE` reads the type from the file (`kubaos_proxy::vpn::detect`: WireGuard's `[Interface]` or `[Peer]`, else OpenVPN's `client`, `remote`, `tls-client` or `<ca>`; neither is refused) and checks the whole config before it touches the vault. WireGuard's secrets are `PrivateKey` and each `PresharedKey`; OpenVPN's are the client's `cert` and `key`, `tls-auth`, `tls-crypt` and `tls-crypt-v2`, each an inline block (`<key>…</key>`, from its `-----BEGIN` line; the comment lines `openvpn --genkey` writes above a static key are left out) or a file the config names beside it, at most 64 KiB, and the `username` and `password` of `auth-user-pass` (from the file it names, its first two lines, or `<auth-user-pass>`, else asked once at the terminal, the password unechoed) and an encrypted key's passphrase (`cert-pass`, from `askpass`'s file or asked once). An OpenVPN config needs `client` (or `tls-client` and `pull`), a `remote` (at most 16, `port` and `proto` filling in what a line leaves out, 1194 and `udp` by default), a `ca`, and a certificate with its key or `auth-user-pass`; TAP (`dev tap`), PKCS#12 (`pkcs12`), static keys (`secret`) and `<connection>` blocks are refused. The secrets go to the vault (a secure note named by `vault_item`, hidden fields: WireGuard's `private-key` and `preshared-key <peer public key>`, OpenVPN's by their names, `cert`, `key`, `tls-auth`, `tls-crypt`, `tls-crypt-v2`, `username`, `password`, `cert-pass`; created or edited through `bw create|edit item` with the item on stdin, the other type's fields replaced, the item's own kept) and to the GNOME keyring (`secret-tool`, attributes `service=kubaos-proxy key=<name>`, and for a preshared key `peer=<public key>`). The import then writes the config without them beside `proxy.toml`, as `vpn.conf` (WireGuard, wg-quick's format) or `vpn.ovpn` (OpenVPN: what the plugin takes, the CA inline, the rest left out and named), removes the other type's file when the profile named it, and sets `type` and `conf` in `proxy.toml` (`toml_edit`, comments kept). `on` reads the secrets from the keyring, and refuses a VPN the keyring can't bring up; `kubaos-proxy pull` copies them from the vault to the keyring again, WireGuard's when the item has a private key, else OpenVPN's. A secret is on stdin, never in argv; the session goes in bw's environment alone.
- **Root.** `/usr/local/libexec/kubaos-proxy-write` (`system/files/proxy/`), as `pkexec --disable-internal-agent` (action `org.kubaos.proxy.write`, rule `50-kubaos-proxy.rules`: an admin at the machine, local and active, needs no password), installed by `install_proxy_helper` (`system/lib.sh`) from `20-base.sh` and the `proxy-helper`, `proxy-helper-lan` and `proxy-vpn` migrations. Its arguments, in the order `on` gives them: `killswitch=on` (nftables `table inet kubaos_proxy`: output and forward reject everything but `lo`, the VPN's interfaces `wg-kubaos` and `tun-kubaos`, packets marked `0x6b6f` (WireGuard's own), DHCP, IPv6 neighbour discovery, and the container bridges `docker0`, `virbr0`, `br-*`, `veth*`; no DNS lookup goes out beside the VPN; only for a full tunnel with `kill_switch`) or `killswitch=lan|RANGES` (the same, and on output the local network: TCP and UDP to ports 53 and 853 refused first, then `169.254.0.0/16`, `224.0.0.0/24`, `239.255.255.250`, `255.255.255.255`, `fe80::/10`, `ff02::/16` and each of RANGES accepted, at most 32 joined by commas, each by its first address with a prefix of at least 1, none at all allowed; with `allow_local_network`), either after `server:SERVERS|` for an OpenVPN VPN (its own packets carry no mark: SERVERS, 1 to 16 joined by commas, each `udp` or `tcp`, an IPv4 address or a lower-case IPv6 one, and a port from 1 to 65535 joined by slashes, `udp/198.51.100.7/1194`, are accepted on output as `ip daddr ADDRESS PROTO dport PORT`, before the lookups are refused: the addresses NetworkManager was given), `ca=-` (one PEM certificate on stdin, read and written back by `openssl x509`: `/usr/local/share/ca-certificates/kubaos-proxy/company.crt` and `update-ca-certificates`, which Nix's `/etc/ssl/certs/ca-certificates.crt` follows, Chrome's `CACertificates` in `/etc/opt/chrome/policies/managed/kubaos-proxy-ca.json`, and a running Docker daemon restarted, as it reads its roots once), `apt=URL` (`/etc/apt/apt.conf.d/80kubaos-proxy`), `docker=URL|NO_PROXY` and `nix=URL|NO_PROXY` (`/etc/systemd/system/{docker,nix-daemon}.service.d/kubaos-proxy.conf`, then `daemon-reload` and `try-restart`; a unit that isn't installed is left alone), `chrome=proxy|URL|NO_PROXY` or `chrome=pac|URL` (`ProxySettings` in `kubaos-proxy.json` beside the CA's), each `PART=off`, and `off` (every part, past one that fails). It checks every value against its own pattern before any part goes, writes only its own files whole, and stops at the first part that fails; `done PART=VALUE` on stdout names each one done. A file whose part failed after it was written (a daemon that wouldn't restart, a trust store that wouldn't update) goes again, so the next run writes it anew. It ignores SIGPIPE, so a caller that stops reading never stops it half way. `stats` prints `wg show wg-kubaos latest-handshakes`. Exit 1 when a part failed, 2 for a usage error, 3 when a value isn't pinned. `KUBAOS_PROXY_ROOT` points it at a fake `/` for the tests (`crates/kubaos-proxy/tests/helper.rs`); pkexec clears it.
- **Pins.** A trusted root and a proxy see all of the machine's traffic, so the passwordless helper puts in place only what an admin pinned in `/etc/kubaos/proxy-pins` (root's, 0644: `ca=` the CA's SHA-256 fingerprint or `none`, `proxy=` URL or `none`, `no_proxy=`, `pac=` URL or `none`); a CA, proxy, `no_proxy` or PAC file that differs exits 3 and changes nothing. The killswitch, every `PART=off`, `off` and `stats` need no pin. `/usr/local/libexec/kubaos-proxy-pin`, the same script by another name, writes the pins (`ca=-|none proxy=URL|none no-proxy=LIST pac=URL|none`, all four, the CA on stdin) under the action `org.kubaos.proxy.pin`, `auth_admin` with no rule: the password every time. `on` pins when the write helper says exit 3, which asks for the password once, then applies again; a profile that keeps its values never asks again.
- **Local network.** With `allow_local_network`, the kill switch lets through the ranges of the interfaces that are up (`ip -json address show up`), but `lo`, `wg-kubaos`, `tun-kubaos` and the container bridges, each by its first address: the widest of ranges inside each other, no whole family, loopback, link-local, multicast or IPv6 range of IPv4 addresses, at most 32 (`kubaos_proxy::local_network`). A range that overlaps one the VPN routes is left out, so work traffic never leaves beside the VPN: a WireGuard peer's allowed IPs but `0.0.0.0/0` and `::/0`, and its own addresses; an OpenVPN config's `route` lines, and the unicast routes on `tun-kubaos` (`ip -json route show table all dev tun-kubaos`, the default left out), which hold what the server pushed. The kill switch's argument is read as the root part goes up, after the VPN, so an OpenVPN server's address and its pushed routes are known; it is kept, as it went up, in `~/.local/state/kubaos-proxy/kill-switch` (gone with the root part), and a reconcile with every part up, and `kubaos-proxy lan on|off` while the root part is up, put `killswitch=` up again alone when what it would let through differs from that record. One that fails leaves what the kill switch let through before, and says so in the log.
- **The session.** `systemctl --user set-environment` (and `unset-environment` at `off`) of `http_proxy`, `https_proxy`, `no_proxy` and their capitals, for units started after; the values the user manager had before (`show-environment`) are kept in `$XDG_RUNTIME_DIR/kubaos-proxy/env-before` and set again at `off`. The same as `export` lines in `$XDG_RUNTIME_DIR/kubaos-proxy/env`, which zsh sources at start (`home/shell.nix`, order 1890). GNOME: `org.gnome.system.proxy` `mode` `manual` with `http` and `https` `host`/`port` and `ignore-hosts`, or `auto` with `autoconfig-url` for a PAC file; the seven keys as `gsettings get` had them first are kept in `~/.local/state/kubaos-proxy/gnome-before` and set back at `off`, the mode last. Docker's client: `proxies.default` (`httpProxy`, `httpsProxy`, `noProxy`) merged into `$DOCKER_CONFIG/config.json` (else `~/.docker/config.json`), its mode kept; `~/.local/state/kubaos-proxy/docker-proxies.json` keeps `{"ours","before"}`, and `off` puts `before` back (or removes the key) only while the one there is still `ours`. git: `[http] proxy` in `~/.local/state/kubaos-proxy/proxy.gitconfig`, which `config/git/config` includes.
- **Service.** `kubaos-proxy serve`, the user unit `kubaos-proxy.service` (WantedBy and PartOf `graphical-session.target`), reconciles at its start, after logind's `PrepareForSleep(false)` once NetworkManager is connected again (at most 60 s), and when NetworkManager's `ActiveConnections` or `State` change (a burst settles 2 s first), so a VPN dropped while the machine is awake comes back too, and a network joined is let through the kill switch once it has its address: not wanted (a login starts so), whatever `applied` lists and an active VPN go; wanted, a part not up or a dropped VPN goes up again with the rest, and with every part up the kill switch goes up again when the local networks changed ("Local network"). A VPN that can't come back takes everything down but the kill switch, when it was up: the Proxy stays wanted, a notification says that "Proxy off" lifts it, and a change of network tries again, at most once in 30 s after a failure (`kubaos_proxy::watch`). Without a kill switch, everything goes and so does the wish. It logs through `log` on stderr, with the journal's priority prefixes.
- **Status.** `kubaos-proxy status [--json] [--live]`; `--json` is `{"configured","wanted","on","busy","parts","tunnel":{"type","typeName","interface","full","killSwitch","allowLocalNetwork","localNetworks","endpoint","up","handshake","rxBytes","txBytes"}|null,"dnsServers","dnsDomains","proxy","pac","ca","warnings","problem"}`: `type` is `wireguard` or `openvpn`, `typeName` `WireGuard` or `OpenVPN`, `interface` the VPN's, `endpoint` its first server as the config names it. The rows say `VPN: up|down: TYPE, full|split tunnel to SERVER[, kill switch]`. `--live` adds a WireGuard VPN's handshake (through the helper's `stats`; an OpenVPN one has none) and the bytes moved from `/sys/class/net/<interface>/statistics`. Every `on`, `off` and reconcile replaces `$XDG_RUNTIME_DIR/kubaos-proxy.json` whole with the status not live, `busy` true while it works; `services/Proxy.qml` watches it. `kubaos proxy` runs `kubaos-proxy`. Exit 2 is a usage error; exit 1 says why on stderr, and `on` and `off` notify it (`notify-send`, app name Proxy).
- **Command menu.** "Proxy on", "Proxy off", "Allow local network through the Proxy" and "Block local network behind the Proxy" (`kubaos-proxy lan on|off`, shown by `proxy.local-network`), "Import VPN config…" (keyword `import-vpn`; in a terminal, for bw's prompt and an OpenVPN login's) and "Open proxy settings" (`proxy-on`, `proxy-off`, `proxy-local-network-on`, `proxy-local-network-off`, `proxy-import`, `proxy-settings`) in `config/kotodama/kubaos.toml`, and the Extension's own "Proxy status" (`proxy-status`, the rows as a List View, read live).
- **Shell.** The control center's Proxy tile (shown once the profile has a part) switches it; its arrow opens the detail: the state, "VPN" (the type and the kind, `WireGuard, full tunnel, kill switch`), "Server", and an "Allow local network" switch, shown with a kill switch, which runs `kubaos-proxy lan on|off`. While it shows and the VPN is up, it reads `/sys/class/net/<the status's interface>/statistics` every 5 s (the bytes moved, and when the VPN last received), and a WireGuard handshake through `status --json --live` (pkexec) as it opens and then once a minute. The bar's `ProxyIndicator` shows while it is on.

## Wallpaper depth (crates/kubaos-depth)

What a wallpaper's depth is (ADR 0004): a foreground cut-out the lock draws over its rest clock, and the clock's place and tint on the picture. The same files come from two places: a shipped wallpaper carries them beside its picture, and the wallpaper-depth Suite writes them for the user's own pictures into a folder per picture under `~/.cache/kubaos/wallpapers/`. A picture without them gets the clock in front of it.

- **The folder.** `depth.toml`, always, and `cutout.png` when a cut-out was kept. Each is written to a temporary name in the folder and renamed into place, so a reader never finds half of one; a run that keeps no cut-out removes an earlier `cutout.png`.
- **`cutout.png`.** The picture's foreground: an 8-bit RGBA PNG at the picture's own size, the picture's colours where it stands in front and alpha 0 (colour black) where it doesn't. Drawn over the picture with the same crop and scale, it lines up pixel for pixel.
- **`depth.toml`.** All keys required, no others:

  ```toml
  format = 1            # this layout; a reader refuses another
  tool = "0.1.0"        # the kubaos-depth version that wrote it
  method = "sky"        # the cut-out kept: "sky", "object", or "none" (no cutout.png)
  score = 0.941         # the best candidate's score, kept or not (kept from 0.7)

  [clock]
  x = 0.5               # the middle of the rest digits' baseline, a share of the picture's width
  y = 0.56              # the same, a share of its height from the top
  tint = "#ffa9f1"      # the rest digits' and the kicker's colour, #rrggbb
  ```

  The place holds on any crop of the picture (the lock covers the screen with it, as `object-fit: cover` does). With a cut-out, the cut-out covers between 1 % and 45 % of the digits in `type.clock_rest` on a 1536 × 960 screen, and none of the kicker or its halo on 1536 × 960, 1920 × 1200, 1536 × 864, 1920 × 1080 and 2560 × 1440 screens; with none, the place is `x = 0.5`, `y = 0.56`. The tint is the Lock page's rule (`crates/kubaos-depth/src/tint.rs`) over the picture under the digits.
- **The command.** `kubaos-depth run PICTURE --out DIR --models DIR` writes PICTURE's folder into DIR, at niceness 19, on the CPU. `--models` holds `depth-anything-v2-small.onnx`, `birefnet-lite.onnx`, `sam-vit-b-encoder.onnx` and `sam-vit-b-decoder.onnx` (their sources and licences: the crate's doc). It prints the method and score on stdout and logs each step on stderr (`KUBAOS_DEPTH_LOG=debug` for each candidate's numbers). Exit 2 is a usage error, 1 a failed run, with the reason on stderr. ONNX Runtime is loaded from `ORT_DYLIB_PATH`, else the nixpkgs one the package was built with. The choice of cut-out and its confidence rule are in the crate's doc (`crates/kubaos-depth/src/lib.rs`).
- **A picture of the user's own.** Its folder is `~/.cache/kubaos/wallpapers/<key>/`, where `<key>` is the md5 of the picture's path as `dot-theme` records the wallpaper (`realpath -s`, the path in `colors.json`'s `wallpaper`), in lowercase hex: `Qt.md5(path)` in QML, as the posters' folder is keyed (`config/quickshell/services/Wallpapers.qml`). Beside the tool's files the folder holds `source`, one line, `<size> <mtime> <tool version>`: the picture's size in bytes and mtime in seconds when the run started, and the `kubaos-depth` version that ran, written after each run whether it succeeded or not. A folder whose `source` names another size or mtime was made from an older picture at the same path; the queue empties it at once, so a reader finds nothing until the new run is in.
- **The hook.** With the wallpaper-depth Suite installed, `kubaos-depth-queue PICTURE` is on PATH (`home/suites/wallpaper-depth.nix`, `home/suites/wallpaper-depth-queue.sh`). `dot-theme set` calls it after matugen and the reloads, and `dot-theme apply` calls it when the theme is up to date, for a still that isn't in the sets' folder; without it on PATH, nothing happens. It does nothing when the settings give the picture no cut-out (it asks `kubaos depth wants PICTURE`, which exits 1 and says why while depth is off or the picture is skipped, a video or in the sets' folder; without `kubaos` it takes the defaults), when `source` matches the picture and the installed tool, or when the picture's unit is active. Otherwise it starts the transient user unit `kubaos-depth-<key>.service` (`systemd-run --user --collect`, in `background.slice`, `CPUWeight=idle`, `IOWeight=1`, `Nice=19`, `IOSchedulingClass=idle`), whose command, `kubaos-depth-queue job PICTURE`, waits while `systemd-ac-power` says the machine is on battery (it asks every 60 s), runs `kubaos-depth run PICTURE --out <folder> --models <the Suite's models>` and writes `source`. Its output goes to the journal. `kubaos-depth-queue redo PICTURE` stops the picture's unit (`systemctl --user stop`, which waits for it to end), empties its folder and queues it, so it runs even when it was up to date; `forget PICTURE` stops the unit and deletes the folder; `stop` stops every `kubaos-depth-*.service`. Removing the Suite takes the command off PATH at the next switch, and `kubaos suite remove wallpaper-depth --purge-caches` deletes `~/.cache/kubaos/wallpapers/`, never the settings.
- **The settings.** `U/desktop/wallpapers/depth.toml`, seeded commented out from `user-layer/desktop/wallpapers/depth.toml`; every key optional, no others (`crates/kubaos-core/src/wallpaper_depth.rs`):

  ```toml
  enabled = true        # depth for the user's own pictures
  push = 0.025          # how far the wallpaper comes toward you in the lock motion, 0 to 0.05
  skip = [              # pictures that never get a cut-out, by the path `dot-theme` records
    "/home/kuba/Pictures/wallpapers/harbour.jpg",
  ]
  ```

  - `enabled` (default `true`): while it is `false` the hook queues none of the user's own pictures, and the lock draws none of their cut-outs, though their folders stay, so turning it on again is instant for what was done. KubaOS's sets keep their shipped depth either way.
  - `push` (default `0.025`, from `0` to `0.05`): the share the picture grows by in the lock motion, round the middle of the screen's bottom edge, and shrinks back by as it gives way; the Lock page's `scale.push` is `1 + push`. Over a background plate the cut-out grows by twice it (the Lock page's `scale.near`, 1.05 at the default), and without one it grows with the picture. `0` holds the wallpaper still.
  - `skip`: the lock draws no cut-out on a picture listed here, shipped or the user's own, and the hook never queues one. A path is compared as written, the way `dot-theme` records the wallpaper.
  - The lock reads the file when it locks. An unreadable file is a warning from `kubaos depth` and the defaults, for the hook and the lock alike.
- **`kubaos depth`** (`crates/kubaos-cli/src/depth.rs`) changes the file, rewriting only the key it changes (comments, the other keys and their order stay; a new key goes at the end, the skip list one path a line), through a temporary file and a rename, and applies at once. PICTURE, left out, is the current wallpaper, the first line of `~/.local/state/theme/wallpaper` (`dot-theme current`).
  - `on` and `off` set `enabled`; `on` queues the current wallpaper, `off` runs `kubaos-depth-queue stop`.
  - `skip [PICTURE]` lists the picture and runs `kubaos-depth-queue forget PICTURE`, so the lock stops drawing its cut-out; `unskip [PICTURE]` takes it off the list and queues it.
  - `redo [PICTURE]` runs `kubaos-depth-queue redo PICTURE`. It refuses (exit 1, the reason on stderr) a picture the settings give no cut-out, and without the Suite.
  - `push SHARE` sets `push`; a share out of bounds is a usage error (exit 2).
  - `show` prints `enabled=<true|false> push=<share>`, then each skipped picture on its own line.
  - Without the Suite, every command but `redo` changes the file alone. A file that isn't TOML is refused and left as it is (exit 1).
- **The Command menu.** While `kubaos.suites.wallpaper-depth` is on, the KubaOS Extension lists "Turn wallpaper depth on" or "off" (by `wallpapers.depth`), "Redo this wallpaper's cut-out" (while depth is on and the wallpaper isn't skipped), "No cut-out on this wallpaper" or "Cut this wallpaper out again" (by `wallpapers.depth-skipped`) and "Set the lock's push" (`lock-push`), each running `kubaos depth` (`config/kotodama/kubaos.toml`).

## The Command menu's KubaOS Extension (crates/kotodama-kubaos, config/kotodama/kubaos.toml)

- **The registry.** `[extensions.kubaos.actions.<id>]` tables, KubaOS's in `config/kotodama/kubaos.toml` and the user's in `U/menu/kotodama/user.toml`, which the Daemon merges key by key; `hide` leaves ids out. An action is `title` and `run`, and optionally `subtitle`, `icon`, `keywords`, `names`, `arguments`, `terminal`, `confirm`, `delay_ms` and `shown_when` (`docs/USING.md`). A table the Extension can't use is left out and logged.
- **States.** `shown_when = { state, is }` sends an action only while its state reads as `is`, and `{ state, is_not }` only while it doesn't; a list of them, `shown_when = [{ state, is }, ...]`, sends it only while each holds, and an empty list is a problem. Every on/off pair of KubaOS's actions has one, so only the half that applies is listed, and so do the three low-battery choices (the one in use is left out), "Stop keeping awake" and "Turn the phone link off". The Extension reads every state at start and with each config, and again whenever one of their files changes (a watch on their folders, settled for 200 ms), never per query and never through a command. A state whose file can't be read has no reading, and its actions show, both halves of a pair alike. A `shown_when` naming no state, or a value its state never reads as, is a problem, and the action is left out. The states and where they come from (`crates/kotodama-kubaos/src/states.rs`):
  - `packages.<group>`, each optional group of the package manifest: on by the group's line in `/etc/kubaos/apt-groups`, else by the manifest's `optional` default (`/usr/share/kubaos/system/packages.toml`), as `kubaos packages enable|disable` turn it. Without the manifest only the groups with a line are known.
  - `files.tidy-daily`: `U/desktop/files/tidy-downloads` exists. `files.automount`: `U/desktop/files/no-automount` doesn't. `workspaces.open-where-launched`: `U/desktop/workspaces/no-open-where-launched` doesn't. `terminal.greeting`: `U/terminal/zsh/no-greeting` doesn't. `phone.link`: `U/desktop/phone/phone-link` exists. `update.firmware`: `U/desktop/update/no-firmware` doesn't.
  - `keyboard.mac-accents`: `mac_accents` in `U/desktop/keyboard/keyboard.toml`, its default without the file.
  - `power.panel-power-saving`, `power.critical-warning`, `power.battery-notes` and `power.background-yields` (true or false), `power.scheduler` (`kernel` or `lavd`) and `power.low-battery` (`power-saver`, `super-saver` or `off`): `U/desktop/power/power.toml`, with its defaults.
  - `nix.unfree`: `allow_unfree` in `U/home/kubaos.d/nixpkgs.toml`, the user flake's state directory, on without the file or the key ("The state directory, Suites and switch jobs", "Unfree packages").
  - `idle.keep-awake`: `active` in `$XDG_RUNTIME_DIR/kubaos-keep-awake.json`, off without it. `proxy`: `wanted` in `$XDG_RUNTIME_DIR/kubaos-proxy.json`. `proxy.local-network`: `allow_local_network` in `[tunnel]` of `U/desktop/network/proxy.toml`, on without the file or the key.
  - `notifications.dnd`: `on` in `$XDG_RUNTIME_DIR/kubaos-dnd.json`, which the shell writes at its start and on every change (`config/quickshell/services/Notifs.qml`), unknown without it.
  - `kubaos.preview`: `~/.local/state/kubaos/preview.json` names a live preview; off while it is empty or missing ("Live previews"). "Back to the release" shows only while it is on.
  - `kubaos.suites.<name>`, each Suite of the catalog: `U/home/kubaos.d/suites/<name>.toml` exists; unknown while it doesn't read ("Suites").
  - `update.bitwarden`: `U/desktop/update/no-bitwarden` doesn't exist. `update.nix`: `U/desktop/update/no-nix` doesn't exist. "Bitwarden updates on/off" and "Nix updates on/off" are their pairs.
  - `bluetooth.unnamed`: `bluetoothUnnamed` in `~/.local/state/quickshell/kubaos.json`, which the shell writes (`config/quickshell/services/ShellState.qml`); off without the file or the key. "Show unnamed Bluetooth devices" and "Hide unnamed Bluetooth devices" are its pair.
  - `wallpapers.depth`: `enabled` in `U/desktop/wallpapers/depth.toml`, on without the file or the key; unknown while it doesn't read. `wallpapers.depth-skipped`: its `skip` names the current wallpaper (the first line of `~/.local/state/theme/wallpaper`), off without a wallpaper; unknown while either doesn't read ("Wallpaper depth").
- **Ranking.** Kotodama ranks an Item whose keyword equals the query with the exact titles, above an Item whose title has the query as a word, as an installed app's does; on an equal match an app ranks before an action. So an action about an app (installing or removing it) leaves the app's name out of its keywords, and a `confirm` action never has words of its own title as a keyword: typing "chrome" lists the Google Chrome app before "Remove Google Chrome". A test over `kubaos.toml` holds both.

## Theme pipeline

- Wallpapers: the sets, one folder each, read-only in `/usr/share/kubaos/wallpapers/<set>/` (the flake input `kubaos-wallpapers`, SuplenC/kubaos-wallpapers, with each set's `CREDITS.md`), and the user's own in `~/Pictures/wallpapers/`, a real folder. `~/.config/kubaos/desktop/wallpapers/sets` (user layer, written by the install) names what the picker shows, one entry per line, `#` comments: a set's id for the whole set, `<set>/<file>` for one of its wallpapers (Kōbō writes a set whose wallpapers are all picked by its id, the rest one by one). Home activation seeds it with the sets on disk when it's missing, and `dot-theme` shows every set without it. A set a release adds shows up only once it's added there; a wallpaper a release adds to a set shows up when the set is listed by its id. The picker's folders are `dot-theme folders`: the chosen sets (whole or with a wallpaper picked) by name, then `yours`. `dot-theme wallpapers` lists what each folder shows, `folder<TAB>path` in order; the Quickshell picker and `next`/`prev` show only those. `dot-theme all-sets` rewrites the file with every set on disk, whole. `dot-theme show-set <set>` lists a set by its id, its single wallpapers dropped (a no-op without the file); `dot-theme hide-set <set>` drops its lines (writing every set first without the file) and refuses when no set on disk would be left. Both write through `sets.new` and a rename. The KubaOS Extension (`crates/kotodama-kubaos/src/wallpapers.rs`) watches the file and sends one Item a set on disk, with Show and Hide running those two. On first boot (no wallpaper yet) the wallpaper is `DEFAULT_WALLPAPER` when the picker shows it, else the first wallpaper of the first folder. A wallpaper is an image (jpg, jpeg, png, webp) or a video (mp4, webm, mkv, mov). A video's still is `<name>.poster.jpg` next to it, else `~/.local/state/theme/posters/<md5 of the path>.jpg`, which `dot-theme` cuts with ffmpeg when needed. Posters are never listed as wallpapers. `dot-theme` keeps paths under `/usr/share/kubaos/wallpapers` as given (it does not resolve the link into the store), so `wallpaper` and `colors.json` name that path. A wallpaper still named by its old `~/Pictures/wallpapers/<set>/` path moves to the same file under `/usr/share` on `apply`.
- Scheme: matugen `scheme-fidelity`, set once in `scripts/dot-theme` (`SCHEME`). First boot with no state uses `DEFAULT_WALLPAPER` (`shinjuku/kubaos-neon-sign.jpg`), and so does `apply` when the wallpaper in `wallpaper` is gone: a deleted file, or a live scene (`ukiyo:<id>`) from a release that shipped them. On that last one `apply` also stops and disables a leftover `ukiyo.service`.
- Command: `dot-theme` (owned by theme).
  - `dot-theme set <file>`: set wallpaper and regenerate colors. For a video matugen reads the poster, then `dot-theme` writes the video's path as `wallpaper` in `colors.json`, `hypr.lua` and `nvim.lua`
  - `dot-theme next` / `dot-theme prev`: next/previous wallpaper (stills and videos) in the current folder
  - `dot-theme folder <name>` (one of `dot-theme folders`) and `dot-theme toggle-folder` (cycles them)
  - `dot-theme wallpapers` (what the picker shows) and `dot-theme all-sets` (every set again, whole)
  - `dot-theme show-set <set>` / `dot-theme hide-set <set>`: one set into the picker, whole, or out of it; the last set stays
  - `dot-theme apply`: regenerate from the current wallpaper (used at login). Skips matugen and the reloads when the wallpaper (path, mtime, size; for a video also its poster's), the scheme, the mode, the matugen binary and the content of `config/matugen/config.toml`, `config/matugen/templates/*` and the oh-my-posh template all match the last successful run, and every output file exists. The record is `~/.local/state/theme/.stamp`, written after each successful run. `dot-theme apply --force` always regenerates; `set`, `next`, `prev`, `folder` and `toggle-folder` always do.
  - `dot-theme current`: print current wallpaper (absolute path)
- Generated output (never committed) goes to `~/.local/state/theme/`:

Do not disturb (`services/Notifs.qml`, `services/dnd.js`): on by hand until turned off, or by itself while Hyprland says a screen is shared (its `screencast` events counted, so it ends with the last of several shares) or a window on a shown workspace is really fullscreen (the client list's `fullscreen` mode 2, read again on each `fullscreen` event; a maximised window is mode 1 and doesn't count). Turned off during a share or a fullscreen window, it stays off until every reason has ended. While it is on, new notifications go to the panel without a popup, a critical one apart (urgency 2), however it was turned on. Its state is `$XDG_RUNTIME_DIR/kubaos-dnd.json`, `{"on", "manual", "reason"}`, written at the shell's start and on every change; a restarted shell takes `manual` back from it. Opening the notifications panel is seeing every popup (`services/popups.js`): they leave as it opens, critical ones too, and don't come back; a notification that arrives while it is open is listed there and doesn't pop up, then or after; a transient one seen there goes once the panel has gone. A notification's card never runs an action on a click: its main button runs the `default` action (named by its text, "Open" when it has none), or the first action when there is no `default`, and the other actions follow as text buttons, leaving out one with the main button's name. The panel, the peek and the popups show the notifications of one app as a group (`modules/notifications/CardGroup.qml`), grouped by `appName`, else `desktopEntry`: the panel per section, the popups at most five groups. A group's newest card stands for it: its dismiss, its actions and Mark read take every notification in it, and as a popup its time running out hides them all; a newer one taking the card starts its time again. Opened, each card stands for its own. A notification is unread until one of its actions is run, it is marked read, or listed in the notifications panel when that closes; the bar's bell shows while there is one or Do not disturb is on (crossed out), or always with `alwaysShowBell` in `U/desktop/quickshell/settings.json`.

Moving wallpapers (`services/Motion.qml`): a video decodes on a screen only when the mode allows it (`always`, or `ac` and UPower says not on battery), the session isn't locked, there has been input within `Settings.screenOffAfter` seconds (600, hypridle's DPMS timeout), and that monitor's active workspace has no fullscreen window. Otherwise the poster shows and the decoder is released. The lock screen plays the wallpaper if it's a video, else `Settings.lockLoop` (`""`, the blurred still), under the same rules minus the lock. One decoder per screen.

Screen recording state: `scripts/dot-hypr-record` writes `$XDG_RUNTIME_DIR/dot-record.json`, replaced atomically on every change: `{"state": "idle"|"recording"|"replay", "mode": "region"|"window"|"output"|"", "pid": <recorder pid>|null, "file": "<mp4 or replay dir>", "backend": "gsr"|"wf-recorder", "started": <unix seconds>}`. Quickshell watches it (`services/Recorder.qml`, `FileView` + `watchChanges`) and creates it as `{"state":"idle"}` when missing. A state other than `idle` whose pid is dead counts as idle; the script repairs it on its next run. Recordings go to `~/Videos/Recordings/` (`$DOT_RECORD_DIR`), screenshots to `~/Pictures/Screenshots/`; satty saves `<name>-annotated.png` next to the original.

Screen capture: gpu-screen-recorder (Nix) records through KMS. Its helper `gsr-kms-server` needs `CAP_SYS_ADMIN`, which a file in the Nix store can't carry, so `system/65-recorder.sh` copies the helper of KubaOS's nixpkgs build (`KUBAOS_DIR`, `system/lib.sh`) to `/usr/local/libexec/dotfiles/gsr-kms-server` (root:<user> 0750, `cap_sys_admin+ep`, GC root `/nix/var/nix/gcroots/dotfiles-gpu-screen-recorder`) and links `/run/wrappers/bin/gsr-kms-server` to it (`/etc/tmpfiles.d/dotfiles-gsr.conf`); nixpkgs' gsr wrapper looks there first. `system/relink.sh` re-runs it on every `kubaos update` and `kubaos rollback`, because gsr and its helper must be the same version. Without it gsr asks for the password through polkit.

PAM: the lock screen runs PAM conversations in parallel: `/etc/pam.d/qs-lock` (password, `pam_unix`), `/etc/pam.d/qs-lock-u2f` (FIDO2 security key, `pam_u2f` with `userverification=1 pinverification=0`: an enrolled finger, never a PIN; `Settings.u2f`, on; only when `/etc/u2f_mappings` has a line for the user) and `/etc/pam.d/qs-lock-fingerprint` (`pam_fprintd`, `Settings.fingerprint`, off). They live in `system/files/pam.d/`; `system/50-hyprland.sh` installs `qs-lock` and `qs-lock-fingerprint`, `system/70-bitwarden.sh` installs `qs-lock-u2f`. Quickshell links Nix's libpam, so `pam_unix.so` resolves to Nix's module; `system/` links `/run/wrappers/bin/unix_chkpwd` to Ubuntu's helper (tmpfiles.d), and the fingerprint file loads nixpkgs' `pam_fprintd.so` from the root-owned link `/usr/local/lib/security/pam_fprintd.so`. `system/60-nix.sh` and `system/relink.sh` build `fprintd` from KubaOS's nixpkgs (`--inputs-from $KUBAOS_DIR`), point the link at its store path and pin that path with the GC root `/nix/var/nix/gcroots/dotfiles-pam-fprintd` (`link_pam_fprintd` in `system/lib.sh`). `qs-lock-u2f` does the same with nixpkgs' `pam_u2f` (`/usr/local/lib/security/pam_u2f.so`, GC root `dotfiles-pam-u2f`, `link_pam_u2f`, created by `system/70-bitwarden.sh`, relinked by `system/relink.sh`). Nothing under `$HOME` is on the PAM load path. Ubuntu's modules by absolute path do not load under Nix's libpam. hypridle's `|| hyprlock` is the fallback locker.

Security key outside the lock screen: `system/70-bitwarden.sh` adds two lines, `auth sufficient pam_u2f.so authfile=/etc/u2f_mappings cue nouserok userverification=1 pinverification=0 [cue_prompt=Touch the fingerprint sensor]` and the same with `userverification=0 pinverification=1` (PIN fallback), above `@include common-auth` in `/etc/pam.d/sudo`, `sudo-i` and `polkit-1` (Ubuntu's module, Ubuntu's libpam), plus a `polkit-agent-helper@.service` drop-in that lets the helper see `/dev/hidraw*`. `/etc/u2f_mappings` is root:root 0644 and only `dot-u2f-enroll` (through sudo) writes it. The password always stays below as the fallback.

Polkit: the in-shell agent is off by default (`Settings.polkitAgent: false`) and Hyprland starts `hyprpolkitagent` (`POLKIT_AGENT = "hyprpolkitagent"` in `config/hypr/autostart.lua`). Flip both together.

Volume and brightness keys are bound in Hyprland directly to `wpctl` and `brightnessctl`. Quickshell shows the OSD by watching PipeWire and the backlight itself.

Written by `kubaos bitwarden env pull` (and `kubaos bitwarden setup`), read by the script a project's `mise.toml` sources for the projects its `KUBAOS_BWENV` names (`~/.local/share/kubaos/bwenv.sh`, generated by `home/secrets.nix`; Project pins, "The migration", has the lines) through `kubaos bitwarden env export <p>`, NUL-separated `NAME=VALUE` records. ## Hyprland conventions

- Session start: tty1 autologin (getty drop-in) -> zsh login shell -> `~/.zprofile` (home-manager) sources `system/files/hyprland-autostart.zsh` as its last step, which execs `start-hyprland` (shipped with the hyprland package; no uwsm). `~/.config/hypr/no-autostart` disables it.
- Graphical session: without uwsm nothing activates `graphical-session.target`, and xdg-desktop-portal (`Requisite=graphical-session.target`) refuses to start. `config/hypr/autostart.lua` imports the session environment, then starts `hyprland-session.target` (defined in `home/desktop.nix`, `BindsTo=graphical-session.target`).
- Leaving the session: every way out stops `graphical-session.target` and waits for it (at most 15 s) before Hyprland goes, so the portals, the polkit agent and Ghostty stop while Hyprland still answers them. The power menu runs `dot-session leave logout|reboot|poweroff` (then `loginctl terminate-session`, `systemctl reboot` or `poweroff`); the fallback exit bind (`config/hypr/fallback.lua`) does the same inline and then `hyprctl dispatch 'hl.dsp.exit()'`. `hyprland.shutdown` stops the target with `--no-block` for every other exit, never waiting on Hyprland's own clients. Bounds on top: `xdg-desktop-portal-hyprland` and `hyprpolkitagent` have `TimeoutStopSec=5s` (user drop-ins, `home/desktop.nix`), and the system and user managers `DefaultTimeoutStopSec=10s` (`system/files/systemd/{system,user}.conf.d`).
- Shutdown splash: Plymouth's `plymouth-{poweroff,reboot,halt,kexec}.service` start after `user.slice` has stopped, so plymouthd gets the screen once Hyprland has let go of it, and `kubaos-shutdown-splash.service` holds the final poweroff or reboot until 2 s after the splash shows (the sign's switch-off is about 1.7 s), skipped when no plymouthd runs. `install_shutdown_splash` in `system/lib.sh` (run by `25-boot.sh` and the `shutdown-splash` migration).
- Boot: nothing on the way to `graphical.target` waits for the network. `NetworkManager-wait-online` is disabled, and Docker starts on first use through `docker.socket` (`docker.service` and `containerd.service` are not enabled; containers with a restart policy start with it, not at boot; `TimeoutStopSec=20s` so dockerd can stop them). `setvtrgb` is masked. `install_fast_shutdown_boot` in `system/lib.sh` (run by `20-base.sh`, Docker's half by `40-apps.sh`, and the `fast-shutdown-boot` migration).
- inotify: each user may hold 1024 inotify instances and 524288 watches (`/etc/sysctl.d/60-kubaos-inotify.conf`), where the kernel allows 128 instances and a watch count scaled to the RAM: Quickshell, the Command menu's Extensions, KubaOS's services, editors and a workspace's tests each hold their own. `install_inotify_limits` in `system/lib.sh` (run by `20-base.sh`, and the `inotify-limits` migration) installs it and applies it at once.
- Swap: an 8 GiB swap file (`/swap/swapfile`, in its own `@swap` subvolume) behind zswap, which keeps swapped pages compressed with zstd in up to 20 % of the RAM and writes the ones that stay cold on to the file. Ubuntu's kernel builds zswap in and leaves it off; `/etc/tmpfiles.d/kubaos-zswap.conf` turns it on at every boot, setting the compressor before enabling it. `install_zswap` in `system/lib.sh` (run by `20-base.sh`, and the `zswap` migration) installs it and applies it at once. There is no zram, and systemd-oomd stays off: Hyprland's apps are not in per-app scopes, so oomd would kill the whole session. The Command menu's RAM answer shows the swap used and what zswap holds in how much RAM (`Zswapped` and `Zswap` in `/proc/meminfo`).
- Panels and windows: only the frame reserves space (exclusive zones from `config/quickshell/modules/frame/Exclusions.qml`: bar 36 px, 8 px elsewhere). Panels, popups and the OSD live in the frame layer with no exclusive zone and float over windows; opening one never resizes a window. Window corners: `gaps_out = 8`, `border_size = 2`, `rounding = 14` (Hyprland rounds the border's outer edge at rounding + border = 16 = frame radius 24 - gap 8, so the corners are concentric; 24 is the surface radius, `docs/DESIGN.md`).
- Primary terminal `ghostty`, fallback terminal `foot`. The Command menu is `kotodama toggle`, fallback `fuzzel`. Fallback binds always exist and never depend on Quickshell or Nix GPU wiring:
  - `SUPER+Return` ghostty, `SUPER+ALT+Return` foot
- Ghostty runs one background instance, the user unit `app-com.mitchellh.ghostty.service` (`home/terminal.nix`: Ghostty's own unit and D-Bus file, kept running with no window, never restarted by a switch). `SUPER+Return` and the `tui()` binds ask it for a window with `ghostty +new-window --working-directory="$HOME" [-e CMD]`; D-Bus starts the unit if it isn't running, and when the request fails the bind starts a Ghostty of its own. The config keeps `gtk-single-instance = detect`, so a launch with arguments (`-e`, `--working-directory`, Nautilus's "Open in Ghostty", Kotodama's terminal actions) is a process of its own. The windows get systemd --user's environment from when the unit started, which `autostart.lua` fills from Hyprland's first.
- Terminal greeting: a new Ghostty window's interactive zsh runs `fastfetch --config ~/.config/fastfetch/greeting.jsonc` (a short module list) and exports `KUBAOS_GREETING=0`, so shells started below it skip it. Never under `$TMUX`, `$NVIM`, `$SSH_CONNECTION`/`$SSH_TTY`, in `zsh -c`, or when the output isn't a terminal. Off while `~/.config/kubaos/terminal/zsh/no-greeting` exists (`dot-greeting on|off|status|show`, the Command menu's "Terminal greeting on/off") or `KUBAOS_GREETING=0` is set.
- zsh start-up: the init scripts of oh-my-posh, fzf, atuin, mise and zoxide and the completion dump are cached in `~/.cache/kubaos/zsh` (`home/shell.nix`), named after the tool's store path, so an update writes new ones. oh-my-zsh stays for its `git` plugin and libraries, without its security audit; compinit trusts the dump and rebuilds it daily, or when `$fpath` changes.
  - `SUPER+Space` the Command menu (`kotodama toggle || pkill -x fuzzel || fuzzel`: fuzzel when no menu answers), `SUPER+ALT+Space` fuzzel
- `SUPER+F1` opens the Command menu on Kotodama's Shortcuts View (`kotodama open --view hyprland/shortcuts`), which lists every bind by its `description`.
- Window focus on `SUPER+hjkl`, screen focus on `SUPER+arrows`, move window `SUPER+SHIFT+hjkl`, resize `SUPER+CTRL+hjkl`, workspaces `SUPER+1..0`, move to workspace `SUPER+SHIFT+1..0` (`+ALT` without following), next/previous workspace `SUPER+Tab` and `SUPER+CTRL+arrows`, next/previous workspace group `SUPER+CTRL+ALT+arrows`, group windows `SUPER+ALT+Tab`. The rest ported from Omarchy 4. Every bind has a `description`, its title in the Command menu's search (`[extensions.hyprland] in_search = true` in `config/kotodama/kubaos.toml`).
- Monitors: every screen at its preferred mode, placed by Hyprland and scaled for its density (`config/hypr/monitors.lua`), with the lid rule for `eDP-1`. A layout of one's own (positions, refresh rates, scales) goes in the user layer's `hyprland.lua`, matched by description; `config/hypr/README.md`, "Your screens", shows how. Every size (Quickshell tokens, terminal and UI fonts) is tuned once for Full HD density, about 1920 logical pixels across, which a screen's scale brings it to.
- Workspaces per screen: each has its own 1-10, a block of ten Hyprland ids (the laptop panel 1-10, the next 11-20), owned by a desk position, never by the screen or its connector (`config/hypr/workspaces.lua`, #131). The positions are the laptop panel and the externals counted 1, 2 and on from the left by Hyprland's layout (top to bottom at the same x), recomputed once the layout has held still for 250 ms after a screen arrives, goes or the layout changes (Hyprland reports a screen before it arranges it, and a dock's screens come and go one at a time), and never on a window event; whatever screen stands at a position shows its group, with no pairing to set up, so a desk needs its screens placed in the order they stand (user layer `hl.monitor` lines; auto placement follows connector order). The group of a position no screen holds waits, under its own numbers, on the primary screen (the laptop panel, else the external Hyprland numbered first) if it has windows, and goes to the next screen that takes the position; a position never seen gets a fresh block. When the positions shift, each group moves to the screen now at its position; no workspace is renumbered, since the bar's Quickshell keeps a workspace's first id. Each group keeps its first workspace and one after its last with windows as Hyprland persistent rules, bound to its screen. The bar shows each group apart, in block order: the screen's own first, then the waiting groups. Next and previous (binds, swipe, the bar's wheel) walk the groups in that order: every workspace the bar shows, one new empty workspace after a group's last, then the next group's first; a group's first steps back to the previous group's last. `SUPER+1..0` address the focused group. The user can pin screens to positions, which are then the workspace groups' numbers (`U/desktop/workspaces/groups.toml`, "Defaults and the user layer"): a pinned screen stands at its group's number whatever the layout, and the unpinned externals are counted from the left over the numbers left. The state is `~/.local/state/kubaos/hypr/workspace-screens` (`block<TAB>connector<TAB>position<TAB>screen` per position ever seen, and `<TAB>name` when its group has a name, `position` `panel` or `1`, `2` and on, the connector empty while no screen holds it, `screen` the description of the one there now or last; the panel's row stays while the panel stands at a group's position), which the bar reads for connector to block (`config/quickshell/services/Hypr.qml`) and the KubaOS Extension for its desk Items (`crates/kotodama-kubaos/src/desk.rs`). A file keyed by screen (`block<TAB>connector<TAB>identity`, an optional fourth column `x`) is migrated on the first reconcile: the externals plugged in keep their blocks at the positions they stand at, the others' blocks take the positions 1, 2 and on by last-known `x`, then block, up to the first position a plugged-in screen holds, and any left over wait with no position, so no window or id moves. A file naming a position twice, two positions with one block, or a screen at a position and again waiting at another is repaired on load (the first row, the plugged-in screen's row, and the held position win; a waiting row of a screen standing elsewhere goes once its block is empty). The file is written whole, by rename, after the workspaces have moved. The actions run over the socket too: `hyprctl dispatch 'dot.workspaces.focus(3)'`, and `dot.workspaces.go_to_position("1")` focuses a position's screen, or its waiting group. `dot-hypr-workspaces` runs `dot-hypr-lid sync` on every monitor hotplug.
- Keyboard layouts: the user's, `layouts` in `~/.config/kubaos/desktop/keyboard/keyboard.toml`, written only by `kubaos keyboard` (`kubaos_core::keyboard`), which the Command menu's keyboard Items and the control center's Keyboard tile and tab run; `config/hypr/input.lua` reads them, and `hyprctl reload` applies a change at once, with no privilege asked. Until the user has a list they are the ones in `/etc/default/keyboard`, which the install writes; the `keyboard-layouts` user migration and `kubaos keyboard seed` copy them over. `/etc/default/keyboard` is the system's: the console and the initramfs's disk passphrase prompt type with it, and Hyprland takes its model and options. It follows the user's default alone: when the default changes, `kubaos keyboard` writes it through `pkexec /usr/local/libexec/kubaos-keyboard-write` (`system/files/keyboard/`, polkit action `org.kubaos.keyboard.set`), which then runs `setupcon --save-only`, a udev change for input devices and `update-initramfs -u` in the background. Not through localed: Ubuntu's systemd ships a D-Bus policy (`org.freedesktop.locale1.read-only.conf`) that refuses `SetX11Keyboard` to everyone, root included, and Debian's localed no longer writes `/etc/default/keyboard`. `system/files/polkit/50-kubaos-keyboard.rules` lets an active local user in the `sudo` group through without a password, and anyone else gets the session agent's prompt. When that fails the user's layouts have changed all the same; everything pkexec said is logged on a line of its own, then the sentence the tab shows says the console keeps the old default and why (polkit refused it, no polkit agent was running to ask for the password, the prompt was dismissed, the helper isn't installed, or the helper's own words). With no terminal, as from the tab and the menu, pkexec runs with `--disable-internal-agent`, so only the session's agent asks. The tile switches to the next layout; its tab makes one the default, moves, removes or adds one from every layout and variant xkb knows. Those are the Items of the "Add a keyboard layout" Kotodama app (`crates/kotodama-kubaos/layouts/manifest.toml`, Extension `kubaos-layouts`, word `layout`, the same binary as the KubaOS Extension in its `layouts` mode), each layout not in use one Item that runs `kubaos keyboard add`. The tab's "Add a language…" (`config/quickshell/modules/controlcenter/KeyboardAddView.qml`) is a second Front end of the Daemon: its own `KotodamaSearch` runs the app's entry Item, searches inside the app and draws the Results. It never sends `shown`, answers `close` at once, and hands a `toggle` or `open` the Daemon routes to it on to the Command menu (`config/quickshell/services/MenuRequests.qml`). Searches over lists in the shell go through Kotodama this way, never a filter of their own.
- Mac-style accents on Left Alt: keyd (`/etc/keyd/kubaos.conf`, from `system/files/keyd/kubaos.conf`) makes Left Alt a layer that is Alt for every key but e, `, u, i and n. Those latch a mark; the next letter is sent as a dead key on a spare keycode, then the letter's own key, and Space as the mark alone on another. The `kubaos:mac-accents` XKB option (`/etc/xkb/rules/evdev` including the system's rules, and `/etc/xkb/symbols/kubaos`) gives the spare keycodes their symbols in every layout, and `config/hypr/input.lua` adds it to the file's options, never replacing them. Both files are generated from `crates/kubaos-core/src/keyboard/accents.rs`, and a test keeps them equal to it. The cheat sheet is a submap of described binds nothing enters (`config/hypr/accents.lua`), so the Shortcuts View lists it.
- Lock command everywhere: `loginctl lock-session`. hypridle's `lock_cmd` runs `qs ipc call session lock || hyprlock`.
- The shell's supervisor: Hyprland's autostart runs `dot-session shell` (a plain `qs` when Nix's scripts are missing), which runs `qs --no-color` with its output in the journal (`journalctl --user -t quickshell`, the supervisor's own lines among them) and starts it again whenever it exits non-zero: at once after a run of 10 s or more, else after 1 s, doubling to 30 s while it keeps dying as it starts. A `qs kill` (exit 0) stops it for good, and so does the end of the session (the compositor's `$WAYLAND_DISPLAY` socket gone). One supervisor a session (`$XDG_RUNTIME_DIR/dot-session-shell-supervisor.lock`); a second exits 1. Quickshell's own crash handler restarts a shell that crashes on a signal after its first 10 s, in the same process tree, so the supervisor sees the rest: a lost Wayland connection, on which Qt calls `_exit` with no crash report (a dock's screens dropping out while locked), a crash as it starts, a kill.
- The lock across a shell restart: the shell keeps `$XDG_RUNTIME_DIR/kubaos-session-lock` saying `locked` while it is locked and empty while not (`config/quickshell/services/Session.qml`), and a shell that starts while it says `locked` locks at once. Hyprland's `misc.allow_session_lock_restore` (`config/hypr/looks.lua`) hands the new shell the session lock its predecessor held, so a shell that dies while locked comes back to its lock screen, and the screen never unlocks on its own. The file goes with the login.
- Idle (`crates/kubaos-idle`, #155): by default lock 5 min, DPMS off 10 min, suspend 30 min only on battery; plugged in, never auto-suspend. The user's times, each on battery and plugged in, are in `~/.config/kubaos/desktop/idle/idle.toml` (see "Defaults and the user layer"). hypridle's `general` block and the sources are `config/hypr/hypridle.conf`; its listeners are `~/.local/state/kubaos/idle/hypridle.conf`, which `kubaos-idle` writes at every change, at login (`config/hypr/autostart.lua` starts hypridle through `kubaos-idle session`, the session's only hypridle: `system/50-hyprland.sh` masks Ubuntu's packaged `hypridle.service` for every user) and at every switch (`home/idle.nix`), before the user's own `hypridle.conf`. A wait the same on both power sources is one listener; two waits are a listener each, with `condition_cmd` `! dot-hypr-on-ac` or `dot-hypr-on-ac` and `condition_retry = 60`, so a power change while idle takes effect within a minute. A change restarts hypridle in the session: `hyprctl dispatch 'hl.dsp.exec_cmd([[dot-session start-idle]])'`, which starts it too when it isn't running. Nothing in KubaOS stops hypridle any more.
- Keep awake: a logind `idle` inhibitor (`systemd-inhibit --what=idle` around `kubaos-idle awake hold`, the transient user unit `kubaos-keep-awake`), which hypridle honours, for a while, until turned off (`SUPER+CTRL+I`, the Command menu), or until the battery is at a level (`kubaos-idle awake until 20%`, 1 % to 99 %; "Keep awake for…" in the Command menu takes `keep awake 25%`). It doesn't touch the lid: closing it does what the setting says (below), and after a resume it is still on if its time isn't up. Keep awake with the lid closed (`kubaos-idle awake lid on|DURATION|LEVEL`; the Command menu's "Keep awake with the lid closed", "Keep awake with the lid closed until the battery is at 20 %", and "Keep awake with the lid closed for…", which takes `keep-awake-lid 2h` or `keep-awake-lid 25%`) also runs the lid's holder (below), and closing the lid does nothing, on battery and plugged in. hypridle keeps running, so `before_sleep_cmd` still locks before a suspend. It ends on its own, and with the Hyprland it was started in; a level ends it once `/sys/class/power_supply` says the machine is on battery at that level or below (the machine's batteries combined, by energy when all report it), read every 5 s, and plugged in never. A Keep awake for a while or until turned off never ends for the battery. Asked for a level the battery is already at or below, on battery, it refuses. Its state is `$XDG_RUNTIME_DIR/kubaos-keep-awake.json` (`{"active", "until", "battery", "lid"}`, `battery` the level in percent, 0 or missing for none, `lid` whether it holds the lid, missing for false), which the bar's `IdleIndicator` watches; its tooltip says when the lid is held.
- Scheduled actions: "Lock in…/at…", "Suspend in…/at…", "Shut down in…/at…" and "Reboot in…/at…" (`kubaos-idle schedule ACTION in|at …`) act once, idle or not, through systemd user transient timers on the calendar with fixed names: `kubaos-scheduled-action` runs `kubaos-idle schedule fire`, and `kubaos-scheduled-warn-1m` and `-warn-10s` show heads-up toasts with a Cancel action (`notify-send --action`). The action runs in the Hyprland session through `hyprctl -i <instance> dispatch 'hl.dsp.exec_cmd(...)'`, as a keybind's would: `loginctl lock-session`, `systemctl suspend` (hypridle's `before_sleep_cmd` locks first), `dot-session leave poweroff|reboot` (so `graphical-session.target` stops cleanly). Shut down and reboot ask to confirm in the menu. One action at a time, the lock included: a new one replaces the old and its toast says what it replaced; "Cancel scheduled action" (id `lock-cancel`) stops them. A heads-up or a fire acts only while the state still names its action and time, so a stale Cancel never cancels its replacement. Keep awake doesn't hold any of them back. The state is `$XDG_RUNTIME_DIR/kubaos-scheduled.json` (`{"at", "action"}`); the bar counts down with the action's icon (lock, suspend, power, restart).
- Lid: logind's drop-in (`system/files/logind.conf.d/lid.conf`) suspends on lid close only on battery and ignores it plugged in or docked; it stays the fallback whenever no session holds the lid. When the user's lid setting differs (`lid` in `idle.toml`: suspend, lock or nothing, on battery and plugged in), or a Keep awake holds the lid, `kubaos-idle` runs a `handle-lid-switch` inhibitor (the transient user unit `kubaos-lid-hold`), and Hyprland's lid bind runs `kubaos-idle lid closed`, which does what the setting says, and nothing when logind's `Docked` is true or a Keep awake holds the lid. The holder rechecks a closed lid every 5 s as logind does (a laptop closed plugged in then unplugged suspends after 30 s awake; a lid closed when a lid-holding Keep awake ends gets the setting's action the same way), and exits when its Hyprland is gone, or once the setting is logind's again and no Keep awake holds the lid with the lid open.
- The panel under the lid (`dot-hypr-lid`): with the lid closed and another monitor active, `eDP-1` is disabled through the flag file `$XDG_RUNTIME_DIR/dot-hypr/laptop-panel-off`, which `monitors.lua` reads; as the only monitor it is powered off with DPMS, so the session keeps its output and windows, and `laptop-panel-dark` beside it records that. Opening the lid lights it, before anything that can fail. `dot-hypr-lid sync` re-evaluates at login and on every monitor added or removed, and hypridle's `after_sleep_cmd` and screens-off `on-resume` run it right after lighting the screens, so a closed lid stays dark and an open one stays lit. `misc:key_press_enables_dpms` and `misc:mouse_move_enables_dpms` stay on: input lights the panel under a closed lid too, the way back if the lid's opening is ever missed.

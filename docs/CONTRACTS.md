# Contracts between the parts of KubaOS

Every part of KubaOS is built against these interfaces. If you need to change one, update this file in the same commit.

Reference hardware: the TUXEDO InfinityBook Pro 14 Gen10 (AMD), the machine every release is tested on. Its drivers are the optional apt group `tuxedo`. Ubuntu Server 26.04 LTS minimal, Hyprland 0.56+ (from `ppa:cppiber/hyprland`, Lua config), Quickshell pinned to a tagged release via Nix, standalone home-manager (flake). Full context: `docs/PLAN.md`.

## Repo location and ownership

- On an installed machine, KubaOS is the root-owned checkout `/usr/share/kubaos`, on a local `release` branch that only a KubaOS update moves, with `origin` on GitHub. `/etc/gitconfig` lists it in `safe.directory`, so Nix reads it as the user. Nothing runs from a user-writable copy, and no Nix code names the checkout's path.
- Each user switches their own **user flake**, `~/.config/kubaos/home/` (`flake.nix`, `flake.lock`, `home.nix`), which the install writes from `user-flake/`. It has its own `nixpkgs` input and takes KubaOS as `git+file:///usr/share/kubaos?ref=refs/heads/release`, with no `follows`. The username and host are literals in it. After the install it's the user's: an update never writes it, except `flake.lock` when the user runs `nix flake update`, which `kubaos update` does, and a user migration ("Updates and migrations").
- KubaOS's flake exports `lib.mkHome { pkgs, username, modules }`, `homeModules.default` (`home/`) and `packages.<system>`, the curated set (`home/curated.nix`), built from KubaOS's own nixpkgs, plus `packages.<system>.cache`, a link to every output of the curated set but the debug ones, which the binary cache workflow builds ("The binary cache"). `mkHome` takes ordinary packages from `pkgs` (the user's nixpkgs) and gives the modules the curated set as the `kubaosPkgs` argument, plus KubaOS's whole package set as `kubaosPkgs.nixpkgs` for the GPU driver bundle. home-manager is KubaOS's pin. A package belongs in the curated set when it's built from source outside nixpkgs, loaded into a curated process, given privileges by `system/`, or driven by a curated program through an interface that changes between its releases (kdeconnect-kde); everything else comes from `pkgs`.
- **KubaOS's own crates in the curated set** (`kubaos`, `kobo`, `kotodama-kubaos`, `kubaos-files`, `-automount`, `-phone`, `-bluetooth`, `-clock`, `-sysmon`) build with crane (`crates/workspace.nix`, the `crane` flake input, which Kotodama's follows). Their dependencies build in two derivations, one for Kōbō (iced and wgpu, which nothing else uses) and one for the command-line tools, which change only with `Cargo.lock` and the crates' manifests; every package builds on its group's, compiling only KubaOS's code. A package's source is its crate, the workspace crates it depends on (read from the manifests) and the files they embed (`install/firstboot` for `kubaos-core`), plus every crate's `Cargo.toml`; so a release rebuilds only the packages whose crates changed. Their tests don't run in that build, on the user's machine: `cargo test --workspace` (`just test`) runs them. A new crate in the curated set goes in a group of `shipped` in `crates/workspace.nix`, so its dependencies are prebuilt. `/etc/nix/nix.conf` has `max-jobs = auto` (`system/60-nix.sh`, and the `parallel-builds` system migration on machines installed before it), so the daemon builds the packages side by side; `cores` keeps its default, every core for each build, which measured faster than a cap (`nix_parallel_builds` in `system/lib.sh`).
- **The binary cache** is the public Cachix cache `kuba-os` (`https://kuba-os.cachix.org`, key `kuba-os.cachix.org-1:BAhDPs8FW+W0SaOzsx7yS9sZmcb6ZjdLc09hBeKXIE0=`, signed by Cachix). On every push to `main`, `.github/workflows/cache.yml` builds `packages.<system>.cache` for `x86_64-linux` (`ubuntu-latest`) and `aarch64-linux` (`ubuntu-24.04-arm`) and runs `cachix push kuba-os` on it: its runtime closure, minus what cache.nixos.org has, which leaves KubaOS's crates, Kotodama, Quickshell's wrapper and the orange Colloid icon theme (about 240 MiB of NAR per architecture when all of it is new). Build-time paths, such as the crates' dependency builds, aren't pushed. Because `mkHome` takes the curated set from KubaOS's own lock whatever the user's nixpkgs, those are the exact store paths a machine's switch asks for. `/etc/nix/nix.conf` names the cache with `extra-substituters` and `extra-trusted-public-keys` (`nix_binary_cache` in `system/lib.sh`, run by `system/60-nix.sh` and by the `binary-cache` system migration on machines installed before it; `install/image/Dockerfile` and `test/Dockerfile` write the same lines). No user is in `trusted-users` and nothing runs `cachix use`: a trusted user is effectively root. A path the cache doesn't have yet, while CI is still building a push, builds on the machine as it would without the cache. The repo secret `CACHIX_AUTH_TOKEN` is the write token.
- KubaOS's flake also has `homeConfigurations."kuba@tuxedo"` and `"kuba@vm"`, for the payload build's user (`install/image/build` `PAYLOAD_USER`) and the test harness. They're `mkHome` with KubaOS's own nixpkgs.
- Hostnames: `tuxedo` (laptop, x86_64) and `vm` (UTM test VM, aarch64). Flake outputs are `<user>@<host>`, so plain `home-manager switch --flake ~/.config/kubaos/home` picks the right one.
- Flakes only see files git knows about: in a KubaOS clone, `git add` new files under `config/`, `scripts/`, `home/` before `home-manager switch` (no commit needed). `~/.config/kubaos/home` is a plain directory (a `path:` flake), unless you put it under git yourself.

## Defaults and the user layer (home/links.nix, scripts/dot-config)

KubaOS ships defaults. The user extends or overrides them in a layer of their own, and an update never overwrites it. An update can add new defaults and fix bugs in ours, and that's all.

- **Defaults** are `config/<app>/`. `links.nix` copies `config/` into the store once (`kubaos-defaults`) and links each file read-only into `~/.config/<app>/`, which is a real directory, so apps can still write their own files next to ours. `links.nix` finds the files with `builtins.readDir`, so a new file or app needs no Nix change. An update replaces this layer whole. Editing `config/` takes a `home-manager switch`. The shipped tree is also at `~/.local/share/kubaos/defaults`, for reading.
- **The user layer** is `~/.config/kubaos/<group>/<app>/`, grouped by area: `desktop/` (hypr, quickshell, cursor, clock, keyboard, sysmon, idle, power, files, wallpapers, phone, network, workspaces), `terminal/` (ghostty, foot, tmux, zsh, fastfetch), `editor/` (nvim), `tools/` (git, lazygit, yazi, bat, bacon, fuzzel) and `menu/` (kotodama), beside the user flake in `home/`. Inside an app's folder the file names are the app's own. The defaults load it last, so anything set there wins. Updates never write to a file in it. `dot-config apply`, which every `home-manager switch` runs (the install's included), creates each missing file from `user-layer/<group>/<app>/`. Each one opens with the settings people change most, commented out, each with its default and why you might change it, then a link to the app's full docs. Deleting a file brings it back on the next apply.
- **Where each app's folder is** is written once per language: `home/user-layer.nix` (Nix, and through the layer file's `app NAME PATH` lines, `dot-config` and the shell scripts, which ask `dot-config path APP`), `crates/kubaos-user-layer` (Rust), `config/hypr/user_layer.lua` (Hyprland), `config/quickshell/settings/UserLayer.qml` (Quickshell, the apps it reads) and `config/nvim/lua/config/user.lua` (Neovim's own folder). A file include in an app's config, which has no variables, names its grouped path literally; the harness checks each one exists after a switch. An eval-time assertion in `home/links.nix` and a test in `crates/kubaos-user-layer` keep `user-layer/` and the tables in step.
- **The maps.** `~/.config/kubaos/README.md` says where to go to change what, and each group's `README.md` lists its folders. They are links to the release's copies (`~/.local/share/kubaos/skel`), so they stay current; `dot-config apply` makes one only where there's nothing, and a README of the user's own is kept. The Command menu's "Settings folder" and "Settings: Desktop", "Terminal", "Editor", "Tools" and "Menu" open them in Files (`dot-config open [GROUP]`).
- **Moving from the flat layout.** Releases before the groups kept each app's folder at `~/.config/kubaos/<app>/`. `dot-config apply` moves those into their groups before it creates a missing file, so a new example never takes the place of the user's file (`dot-config relocate` does the move alone; the `grouped-user-layer` user migration runs it again). A folder whose group has none moves whole. Otherwise it moves file by file: the same file in both places is kept once, an untouched example gives way to the user's file, and when the user edited both, the grouped one stays and the flat one goes beside it as `<file>.old` (`.old.2` and so on), reported on stderr. Nothing is deleted but empty folders. In a user layer that is a git clone, the moves show as renames; nothing is committed. There's no fallback: nothing reads the flat paths after the move.
- When a default changes, users who never overrode it get the new value. Users who did keep theirs. In an entry file, the user layer's include stays the last line, below every default.
- A migration may change a user file only if it adds to the file and doesn't rewrite it, is safe to run more than once, backs the file up first, and skips any setting the user has changed. It may create a user file that doesn't exist.

### The running session after a switch (home/session.nix, scripts/dot-session)

A switch writes no file: it points the links in `~/.config` at new store files. Programs that read their config once at start keep the old defaults, and Hyprland, which watches its files for writes, doesn't notice either. So every generation records, in `kubaos-session` next to its `activate`, the store paths each of these parts starts from: its directory or file in `config/`, plus the package where KubaOS pins one. Home activation (`reloadSession`, after the user units and `dot-config apply`) compares the old generation's record with the new one's and runs `dot-session apply` for the parts that changed:

| Part | Record | On a change |
|---|---|---|
| Hyprland | `config/hypr/` without `hypridle.conf`, `hyprlock.conf`, `README.md` | `hyprctl -i <instance> reload` |
| Quickshell | `config/quickshell/`, `kubaosPkgs.quickshell` (which carries Kotodama's QML module) | Hyprland execs `dot-session restart-shell`: it waits while `qs ipc call session locked` says `true`, then `qs kill` and `exec qs`. When no Quickshell of the default config runs, nothing starts. Two restarts waiting at once start one shell |
| hypridle | `config/hypr/hypridle.conf` | Hyprland execs `dot-session restart-idle`: when hypridle runs, it is stopped and started again. One stopped by hand stays stopped. Activation writes the idle settings' listeners (`kubaos-idle write`, `home/idle.nix`) before this runs |
| Ghostty | `config/ghostty/` | `SIGUSR2` to the user's Ghostty processes |
| tmux | `config/tmux/` | `tmux source-file` when a server runs |

- The Hyprland instances are `hyprctl instances` in `$XDG_RUNTIME_DIR` (`/run/user/<uid>` when unset), so it works from a terminal in the session, from `kubaos update`'s switch unit and over ssh, all as the desktop user. With no Hyprland running (a tty, ssh with nobody logged in), the Hyprland, Quickshell and hypridle parts do nothing.
- A first activation (the installer's, a new home) has no old generation and does nothing. A part a generation has no record of counts as changed when the other has one, so the first switch onto a generation with records restarts everything that runs once.
- It never fails a switch: `dot-session apply` exits 0, and a failed reload or restart is only a missing line in the output.
- Left alone: the Kotodama Daemon (it follows its config links into the store, and its systemd unit is restarted by the switch's sd-switch when the package changes), hyprlock (starts afresh at each lock), Hyprland's own package (the VM's, from Nix: a new one needs a new login), `dot-hypr-workspaces` (a running script keeps its old copy until the next login), and Neovim and the other terminal apps (they read their config when they start).

## The state directory, Suites and switch jobs (home/state.nix, home/suites.nix, kubaos-core)

What the `kubaos` CLI, the Command menu and Kōbō install is declared in files the tool owns, never in Nix code (`docs/adr/0002-suites.md`).

- **The state directory** is `~/.config/kubaos/home/kubaos.d/`, inside the user flake: `packages.toml` and `suites/<name>.toml`. Any of them may hold `packages = ["ripgrep", "python3Packages.black"]`, attribute paths into the user's `pkgs`; the home installs the union. A Suite file's other keys (options, version) belong to the Suite framework. `kubaos package add|remove` rewrites `packages.toml` whole, sorted, under the lock `~/.local/state/kubaos/kubaos.d.lock`, through a temporary file and a rename. A Suite's install writes its file and its removal deletes it.
- **Git.** When the user flake is in a git work tree, Nix copies it from git's index, so a file git doesn't know isn't in the flake. Every write into `kubaos.d/` (`kubaos package`, `kubaos suite`, `kubaos package restore`) ends with `git add --intent-to-add -- kubaos.d`, which lists new files without staging their content, and `git rm --cached` of the files it deleted. Nothing is committed, and a changed file's staged content stays as the user left it (`kubaos_core::state::StateDir::sync_git`). A flake that isn't in a work tree is left alone.
- **Wiring.** `home.nix` sets `kubaos.stateDir = ./kubaos.d;` (`user-flake/home.nix` has it). `home/state.nix` reads the directory with `builtins.readDir` and `builtins.fromTOML` when the path exists, and does nothing otherwise. On an older `home.nix`, `kubaos package add|remove` and `kubaos suite add|configure|remove` add the line above its closing `}`, after copying the file to `~/.local/state/kubaos/backups/home.nix.bak` (or `.1`, `.2`, …). The backup lives outside the user flake, so it never becomes part of the flake's source in the Nix store. It skips a file that already sets it, and refuses one whose last line isn't a lone `}`, asking the user to add the line by hand (`kubaos_core::state::migrate`).
- **Rollback.** Each generation links its copy of the directory to `~/.local/share/kubaos/kubaos.d`, so `<generation>/home-files/.local/share/kubaos/kubaos.d` is the directory it was built from. `kubaos package restore <generation>` puts that copy back, and empties the directory for a generation that had none. `kubaos rollback` doesn't need it: an update never changes the directory, so a rollback puts back the `flake.lock` the update saved and switches.
- **Switch jobs.** Every switch is a job in `~/.local/state/kubaos/jobs/`: `<id>.json` (`id`; `state`, one of `queued`, `running`, `succeeded`, `failed`; `queued_at`, `started_at`, `finished_at` in Unix milliseconds; `error`) and `<id>.log`, the switch's output. Ids sort by queue time. Submitting writes the job, then starts `systemd-run --user --unit=kubaos-switch-<id> --collect kubaos job work`, passing on `PATH`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `NIX_PATH`, `LANG` and `LOCALE_ARCHIVE`. A worker takes `switch.lock` (`flock`) in that folder and runs every queued job, oldest first, each a `home-manager switch -b hm-backup --flake ~/.config/kubaos/home`, until none is left. A job still `running` when a worker gets the lock lost its worker, and is marked `failed`. A job records its unit as `unit` (none for `--foreground`); a job still `queued` whose unit is no longer active (`systemctl --user show -p ActiveState`), while no worker holds the lock, will never run (its program failed to start, say), and following it or `kubaos job list` marks it `failed`. So two switches never run at once, none is lost, and none waits forever. A front end follows a job by reading the two files (`kubaos_core::switch::Queue::follow`); `kubaos job follow <id>` prints the log as it grows. `--foreground` runs the queue in the calling process instead, for a session without a user manager (the test harness).

### Suites

A Suite (`docs/adr/0002-suites.md`) has two halves. Its metadata is a `kubaos_core::suites::Suite` in `crates/kubaos-core/src/suites/catalog.rs`: name, title, description, versions (the default first), extras, toolchain source (`Nix`, or an upstream manager such as rustup), cache folders under the home, user-layer files it seeds, its scaffolders, and the words that mark a user-layer file as mentioning it. Its Nix module is `home/suites/<name>.nix`, which `home/suites.nix` imports and which does nothing until `kubaos.suites.<name>` is set. A new Suite is one catalog entry plus one module.

- **The file.** `kubaos suite add` writes `kubaos.d/suites/<name>.toml`: a header comment, `version` and `extras`. `configure` rewrites it, `remove` deletes it, each under the state directory's edit lock, and each is followed by a switch. `home/state.nix` turns each file into `kubaos.suites.<name> = { version; extras; }`. A file with a name the catalog doesn't know still installs its `packages`.
- **What the module may declare:** packages, `home.sessionVariables`, `home.sessionPath`, its toolchain per version for Project pins (`kubaos.suiteToolchains`, below), and editor settings in the Defaults through `kubaos.nvim.suiteSpecs`, a list of lazy.nvim specs as Lua expressions (a LazyVim language extra is `''{ import = "lazyvim.plugins.extras.lang.go" }''`). `home/suites.nix` writes them to `~/.config/nvim/lua/kubaos/suites.lua`, which `config/nvim/lua/config/lazy.lua` loads after KubaOS's extras and before the user layer's `plugins/*.lua`, so the user's settings win.
- **The user layer.** A Suite never writes to a user-layer file that exists, a dangling link included. On `add` and `configure` it creates each of its seeds that is missing, with a comment on how it's loaded and a commented example, as `dot-config apply` does.
- **Removal** takes away everything the module declared, at the next switch. Caches are sized first and kept; `--purge-caches` deletes them (a cache inside the Projects root, or holding it, is never one). The user-layer files that mention the Suite (as a whole word, ignoring case; not `kubaos.d/`, `.git/`, links, or files over 1 MiB) are listed and left alone. Projects are never touched.
- **Scaffolding.** `kubaos suite new <name> <project>` runs a scaffolder of an installed Suite in the Projects root, with `{path}` and `{name}` filled in. It refuses a project folder that exists. The Projects root is `~/Projects` by default; `KUBAOS_PROJECTS` moves it (an absolute path, or one relative to the home; `crates/kubaos-core/src/state.rs`, `PROJECTS_VAR`), best set in the user flake as `home.sessionVariables.KUBAOS_PROJECTS`. The Command menu's project folders are its own setting (`folders` in `menu/kotodama/user.toml`), so a moved root goes there too. `kubaos suite list --json` and `kubaos suite show <name> --json` give a menu the "New <Suite> project" actions of each installed Suite.
- **The test Suite**, `test`, is in the catalog only in builds with the `test-suite` feature (the harness's); its module is `home/suites/test.nix`. Its toolchains (below) are declared only while it is installed, so a real home has no entries for it.

### Project pins (home/pins.nix, config/direnv/lib/suite.sh, kubaos-core pins)

A Project pin is a line in a folder's `.envrc`, `use suite <name> <version>` (`docs/adr/0002-suites.md`). It puts that version of the Suite's toolchain on PATH, ahead of the installed one, in the folder and below it; leaving the folder gives the installed one back, as direnv unloads it.

- **Toolchains.** Each Suite module declares `kubaos.suiteToolchains.<name>.<version>`, a package per version in the catalog, whether the Suite is installed or not, so a folder can pin a version the home doesn't have, of a Suite the home doesn't have. Its `bin/` (`lib.getBin`) is what goes on PATH. `home/pins.nix` writes one entry per version, `~/.local/share/kubaos/toolchains/<name>/<version>`: the derivation as `<drv>!<output>`, then the output path. The derivation's string context is the `.drv` file alone (`builtins.unsafeDiscardOutputDependency`) and the output path's is dropped, so a switch keeps the `.drv` files alive and builds nothing; the test Suite's entry keeps 2.4 MiB of `.drv` files and sources, most of it nixpkgs' bootstrap, which every entry shares.
- **The direnv function.** `config/direnv/lib/suite.sh`, linked to `~/.config/direnv/lib/` with the rest of `config/`, defines `use_suite`. It watches the entry, missing or not, so a switch that adds it or moves the version to a new build reloads every shell in the folder. It reads the entry; if the output isn't in the store, or isn't the one the folder's GC root points at, it runs `nix-store --realise <drv>!<output> --add-root <.direnv>/suites/<name>/<version>`, which substitutes it from the binary cache or builds it, once, and deletes the Suite's other roots in that folder, so a re-pinned version can be collected. Nix names the link `<version>-<output>` for any output but `out` (`3-bin` for a `bin` output), and that is the name compared. Then `PATH_add <output>/bin`. A name or version with no entry is an error naming the Suite's versions, and changes nothing.
- **Which pin applies.** direnv loads only the nearest `.envrc` above the current folder. A nested `.envrc` keeps the pins above it only with `source_up` (or `source_up_if_exists`), which loads the nearest `.envrc` above its own folder at that line (a `source_up` of another file, such as `source_up_if_exists .envrc.secrets`, doesn't); within what is loaded, the last pin of a Suite wins, so a pin after `source_up` overrides the one above. `kubaos_core::pins::Pins::resolve` reads the files the same way, split into words as the shell would (quotes removed, `#` ends the line), without running them: a pin inside an `if` counts as if it ran.
- **`kubaos pin <suite> <version> [folder]`** checks the version against the catalog, replaces the folder's `.envrc` line for the Suite in place, keeping its trailing comment, or appends one, creating the file when missing, and runs `direnv allow` on it. A new file in a folder below another `.envrc` starts with `source_up`, so the folder keeps what that one sets. A linked `.envrc` is written where it points, and a file keeps its mode, set before the text goes in. `kubaos unpin <suite> [folder]` removes the folder's own line for the Suite and its GC roots in the folder's `.direnv/suites/<suite>/` (and the folders that leaves empty), deletes the file when only blank lines and a bare `source_up` or `source_up_if_exists` are left, and allows it again otherwise; with no line there, it names the `.envrc` whose pin applies. Both edit only a lone, top-level line: a file that pins the Suite twice (an `if` and its `else`), or a pin line that is indented or between an `if`, `for`, `while`, `until`, `case`, `select` or `{` and its end, is refused with the line's number and left for the user to edit (`PinError::Tangled`). The folder is the current one by default, and may start with `~` (the Command menu passes it on as typed); a relative one, `..` included, is taken from the shell's logical `$PWD` and worked out from the text, links unresolved, as direnv walks it.
- **`kubaos pins [folder]`** lists the pins in effect, each with its `.envrc`, the installed version, and whether its toolchain is in the store, will be fetched on first use, or has no entry in the home; and the pins above that a nested `.envrc` without `source_up` hides. `kubaos pins --all` lists every pin in an `.envrc` under the Projects root, 4 folders deep at most, skipping hidden folders, links and `node_modules`, `target`, `vendor`, `dist`, `build`. Both take `--json`: `pins FOLDER --json` prints one object, `folder`, `envrc`, `pins` and `hidden`, and `pins --all --json` an array of pins (`suite`, `version`, `envrc`, `known`, `installed`, `installed_version`, `toolchain`: `in-store`, `on-first-use` or `missing`). A path that isn't UTF-8 has its bad bytes replaced.
- **Portable projects.** A pin needs KubaOS. A project shared with people who don't run it pins its toolchain in its own `flake.nix` and `use flake` instead; nix-direnv, which KubaOS enables, serves that too.

## Updates and migrations (kubaos-core update, kubaos update)

- **Records.** `/etc/kubaos/channel` is `stable` or `edge`; `kubaos channel` writes it. `/var/lib/kubaos/release` is `key=value` lines: `version`, `codename`, `commit`, `channel`, `date` (UTC). The install writes both: edge unless `/usr/share/kubaos-keys/allowed_signers` exists and a `v*` tag verified by it points at the installed commit. Without a record, `kubaos update` reads `release`'s `VERSION` and `CODENAME` and takes edge unless a verified tag is there. `/var/lib/kubaos/update-history` has one line per update, tab-separated: date, from commit, from version, to commit, to version, the saved lock (`~/.local/state/kubaos/locks/<unix time>.lock`, or empty). `kubaos rollback` undoes the last line and drops it.
- **The `kubaos` command** comes with the release: `home/curated.nix` builds it (`crates/kubaos-cli/package.nix`) and `home/updates.nix` installs it in every home, so each switch puts the release's build at `~/.nix-profile/bin/kubaos`. `/usr/bin/kubaos` is a launcher (`install/firstboot/kubaos-launcher`) that runs that one, and the install's own copy, `/usr/lib/kubaos/kubaos`, when the home has none (root, a home not switched yet). The daily check runs the generation's store path; the switch jobs' units run the binary that submitted them, which is the home's whenever it was started through the launcher or PATH. An update keeps running the binary it started with; the next one runs the new build. The system migration `kubaos-launcher` puts the launcher on machines installed before it.
- **Kōbō's setup mode** comes with the release the same way: `home/curated.nix` builds `kobo` (`crates/kubaos-kobo/package.nix`, its windowing and GPU libraries added to the runpath) and `home/setup.nix` installs it, at `~/.nix-profile/bin/kobo`. `/usr/bin/kubaos-setup` (`install/firstboot/kubaos-setup`), which the first-boot unit, the desktop entry and the Command menu's setup Items run, runs that one, and the install's own `/usr/bin/kobo` when the home has none. `/usr/bin/kobo` stays the build the live ISO carried: the installer runs it in `cage` before any Nix profile exists. The system migration `kobo-launcher` rewrites `/usr/bin/kubaos-setup` and `kubaos-setup.service` on machines installed before it, where they exist.
- **The release policy** (`kubaos_core::update::policy`): one seam, `Policy::pick(installed, refs)`, picks the update and the upgrade from a `Refs` (`GitRefs` after a fetch, `RemoteRefs` from `git ls-remote` for the daily check). Edge takes `origin/main`'s head, which `git verify-commit` must accept against `allowed_signers` when that file exists. Stable takes the newest `v<semver>` tag of the installed series that `git verify-tag` accepts, as the update, and the newest of the next series as the upgrade. Signatures are SSH (`gpg.ssh.allowedSignersFile`). A different release scheme replaces this module only.
- **Migrations.** `migrations/system/` and `migrations/user/` hold `<unix time>-<slug>.sh` (`just migration system|user <slug>` writes one). They change config, never only packages: an apt package goes in the package manifest ("The package manifest"), which every update applies. An update runs the new release's pending ones in name order, each under `bash -euo pipefail`, from the checkout, with `KUBAOS_DIR`: system ones as root after apt, the Hyprland pin and the package manifest, before the user flake's update; user ones as the user after the switch, with `KUBAOS_USER_FLAKE` and `KUBAOS_BACKUPS` too. `migrations/lib.sh` has `kubaos_backup FILE`. A migration that succeeds leaves a marker named after it in `/var/lib/kubaos/migrations/` or `~/.local/state/kubaos/migrations/`; one that fails stops the update and runs again on the next. The install writes markers for every migration of the installed release. A rollback keeps the markers: migrations only go forward.
- **The Hyprland pin.** On amd64, when the release's `system/files/apt/preferences.d/kubaos-hyprland` differs from `/etc/apt/preferences.d/kubaos-hyprland`, an update unholds the held stack (`system/lib.sh`'s `HYPR_HOLD_RE`), installs the pinned versions, holds the stack again, and only then writes the pin.
- **What a run reports** (`kubaos_core::update::event`). `kubaos update`, `upgrade`, `rollback`, `update --check` and `packages enable|disable` send `UpdateEvent`s to a `Sink`, and the CLI only shows them: a live view of the phases on a terminal, plain lines without escape codes elsewhere (`NO_COLOR` drops the colours of the live view), and with `--json` one event per line on stdout, an object tagged by `type` (`started`, `phase_started`, `step`, `progress`, `output`, `note`, `warning`, `preview`, `prompt`, `answered`, `phase_finished`, `available`, `summary`, `declined`, `failed`). A front end shows the same events. A `prompt` of kind `confirm` is answered with a line on stdin (empty or `y` is yes, end of input is no); one of kind `password` is `sudo -v` reading the terminal, so a front end without one passes `-y` and keeps sudo's credentials fresh itself. The phases are `checking`, `fetching`, `verifying`, `reviewing`, `snapshot`, `system_packages`, `release`, `hyprland`, `manifest`, `system_migrations`, `inputs`, `home`, `user_migrations`; each ends `done`, `skipped` or `failed`, and only those that run are sent. The `summary` holds from and to, the channel, the changes, the package count, `apt` (what the `manifest` phase installed and removed, one `{group, installed, removed}` a group), the Nix inputs, the migrations run, what the session reloaded (the switch's `dot-session:` lines), whether a re-login or reboot is needed, the command that undoes it and the log. The `preview`, before anything changes, holds the same `apt` with what the `manifest` phase will install (no removals: those are known only once apt has simulated them).
- **The run's log.** Every program's output goes to `~/.local/state/kubaos/update/<UTC date>T<time>-<command>.log`, each line with its seconds since the start, each command as a `$` line; the last 10 logs are kept. The check writes none. A failed step's event carries its last 20 lines of output and the log's path.
- **No terminal input.** Programs run with stdin closed, migrations included: a migration can't ask. apt runs with `DEBIAN_FRONTEND=noninteractive` and `--force-confdef --force-confold`, so a changed config file under `/etc` is kept and the package's new one is left beside it as `.dpkg-dist`. sudo's password is asked before a step that needs root (or runs sudo itself, as `system/relink.sh` does) only when sudo's cached credentials have run out, with the live view cleared.
- **The daily check.** The user timer `kubaos-update-check.timer` (`home/updates.nix`) runs `kubaos update --check`, which writes `~/.local/state/kubaos/update-available`: `update=`, `update-commit=`, `upgrade=`, `upgrade-commit=`, `upgrade-codename=`, `apt-security=` and `apt-security-packages=` lines, the file empty when nothing waits. Each version or commit is notified once (`~/.local/state/kubaos/notified`); each pending apt security package is notified once too, as `apt-security name=version`, and a check notifies only when the pending set gains a package not notified yet. The apt keys of packages no longer pending are dropped on every check, so the file stays as small as the pending set. The bar (`config/quickshell/services/Updates.qml`, `modules/bar/UpdateIndicator.qml`) and the KubaOS Extension (`crates/kotodama-kubaos/src/updates.rs`) watch the file: the bar's marker shows for `update`, `upgrade` or `apt-security`, and a click runs `kubaos update` unless only `upgrade` waits; the Extension's "Update KubaOS" Item adds the pending security count to its subtitle. An update empties it. The check takes the update's lock (`update.lock`) from counting to writing, and leaves the file alone when an update holds it, so a finished update's cleared count is never written back.
- **Pending apt security updates.** The check counts them without root. Ubuntu's own list refresh is retired (below), so the system's lists change only when `kubaos update` runs; the check therefore keeps lists of its own in `~/.local/state/kubaos/apt` (`kubaos_core::update::security`): `apt-get update` as the user with `Dir::State` and `Dir::Cache` moved there (sources, dpkg's status and the auto-installed marks stay the system's), then `apt-get -s upgrade --with-new-pkgs`, the same simulation the update's preview runs, counting each `Inst` line whose origins include a `-security` pocket. A candidate that comes from `-updates` alone is checked with `apt-cache policy` (one call for all of them): when a `-security` version newer than the installed one exists, the candidate carries that fix and counts. The package caches are off (`Dir::Cache::pkgcache=` and `srcpkgcache=` empty) and only English descriptions are fetched (`Acquire::Languages=none`); measured on the laptop, the folder is about 100 MiB (all of it lists, against about 250 MiB with the caches), and the simulation takes about 1 s. It never takes the dpkg lock or runs apt as root, and the folder can be deleted. `apt-get update` runs with `--error-on=any`, so a list that failed to download fails the refresh (plain `apt-get update` exits 0 with a `W: Failed to fetch`); when the refresh or apt fails the check warns and keeps the last count. The check costs one list download a day, as `apt-daily` did. What installs them is `kubaos update`: `apt-get upgrade --with-new-pkgs` takes every pocket in the sources, `-security` and `-updates` alike, and `--with-new-pkgs` brings a new kernel image and its metapackage; the summary says when a reboot is needed.
- **Ubuntu's own updaters are retired** (`retire_ubuntu_updaters` in `system/lib.sh`, run by `system/10-strip.sh` and the `retire-ubuntu-updaters` system migration): nothing starts apt unless `kubaos update` runs it. `apt-daily.timer`, `apt-daily-upgrade.timer`, `unattended-upgrades.service` and the `apt-daily` and `apt-daily-upgrade` services are stopped, disabled and masked (`unattended-upgrades.service` is not stopped while `/var/run/unattended-upgrades.lock` is held, since the stop would SIGTERM the running upgrade and wait for it, up to 30 minutes; it is still disabled and masked; the `apt-daily` services are never stopped, a running one finishes), so a package upgrade can't enable them again; `/etc/apt/apt.conf.d/99kubaos-no-periodic` (`system/files/apt/apt.conf.d/`) sets `APT::Periodic::{Enable,Update-Package-Lists,Download-Upgradeable-Packages,Unattended-Upgrade,AutocleanInterval,CleanInterval}` to 0, and sorts after Ubuntu's `20auto-upgrades`. The `unattended-upgrades` package is out of the package manifest (the `upgrades` group is gone), so an update removes it once it is recorded as installed and nothing depends on it. Ubuntu's other leftovers, checked on the laptop and decided one by one:
  - **Kept**: `fwupd` and `fwupd-refresh.timer` (it downloads LVFS metadata and installs nothing; firmware updates need it), `fstrim.timer` (SSD), `dpkg-db-backup.timer` (a daily copy of dpkg's database, cheap and useful after a crash).
  - **Already off or absent**: `motd-news.timer` and the `apt-news` and `esm-cache` services (`system/10-strip.sh` disables or masks them; the ESM line of the login motd has its exec bit off), `man-db.timer` and `update-notifier` (not installed).
  - **Left alone**: the Ubuntu Pro client's `ua-timer.timer`, `ubuntu-advantage.service` and `ua-reboot-cmds.service`, which are enabled but inert on a machine with no Pro subscription (their conditions fail, no timer is scheduled), `e2scrub_all.timer` (it finds no ext4 volume on a btrfs machine and exits at once), and the `85-fwupd` and `50-motd-news` login-motd scripts, which print a line at a console login and fetch nothing now.


## The package manifest (system/packages.toml, kubaos-core apt)

- **The manifest.** `system/packages.toml` lists every apt package KubaOS installs, in `[group.<name>]` tables: `summary`, `packages`, and optionally `arch` (the one architecture it is for), `repo` (a `[repo.<name>]`: `key_url`, `fingerprint`, `keyring`, with the sources file in `system/files/apt/sources.list.d/<name>.sources`, `@ARCH@` filled in), `hold = true` (apt-mark hold), `if_available = true` (a package with no install candidate is skipped quietly), `optional = "on"|"off"` (the user may turn it off or on; the value is its default) and `when_on`/`when_off` (the script, with its arguments, that sets up or takes down what the group needs beyond packages). The file keeps to tables, strings without escapes, booleans and string arrays: `system/manifest.sh` reads it with awk, `kubaos_core::apt::manifest` with serde, and a test holds the two to the same reading of the release's file. A group is **active** when it is for this architecture and on.
- **The choices.** `/etc/kubaos/apt-groups`, `<group>=on|off` lines, holds what the user decided; a group without a line follows its default. The scripts' flags write it (`40-apps.sh --no-docker`/`--no-chrome`, `70-bitwarden.sh --no-u2f`/`--remove-u2f`, `75-yubikey.sh --piv`/`--no-piv`, `30-hardware.sh`'s tuxedo part), and so does `kubaos packages enable|disable <group>`. The scripts take their defaults from it.
- **The record.** `/var/lib/kubaos/apt-installed`, `<package><TAB><group>` lines: each package an install script or an update installed because a group listed it and the machine lacked it. A package that was there first is never in it.
- **Install.** The system scripts install their groups with `group_install` (`system/manifest.sh`, sourced by `lib.sh`), which sets up a group's vendor repo, installs with `--no-install-recommends`, holds a held group and records what it installed. Their non-package work stays in the scripts. Outside the manifest: the kernel headers of the running kernel (`30-hardware.sh`), `make` and grub-btrfs when it isn't packaged (`20-base.sh`), and the Bitwarden desktop `.deb` (`70-bitwarden.sh`).
- **Update.** Every `kubaos update`, packages-only too, runs the `manifest` phase against the checked-out release's manifest, after the Hyprland pin and before the system migrations: `system/apt-repo.sh` (as root) for the vendor repos of the groups with packages to install; `apt-get install` of the active groups' missing packages that have a candidate (one without is a warning, or nothing for an `if_available` group); `apt-mark hold` of the held groups' packages; and `apt-get remove` of each recorded package no group lists any more, after `apt-get -s remove` shows it takes nothing else along; one that would is kept, with a warning. A group that is off loses nothing in an update.
- **Turning a group on or off.** `kubaos packages enable <group>` records `on`, installs the group's packages and runs its `when_on` script; `disable` records `off`, runs `when_off` (for `u2f`, `70-bitwarden.sh --remove-u2f`, so PAM never names a module that is gone), then removes the group's recorded packages that no active group lists; one it didn't install (a machine from before the record) stays, named in a warning with the `apt remove` that takes it. A failed script puts the old choice back. Both run as a run of `UpdateEvent`s (command `packages`), under the update lock, with a log.
- **Status.** `kubaos packages status` lists each group, active or not and why, with each package's state (`installed`, `held`, `missing`, `unavailable`, `skipped` for an inactive group's missing one) and version, and the `extra` packages: recorded, installed, and listed by no group. `--json` writes the same as one object: `arch`, `groups` (`name`, `summary`, `active`, `inactive`, `optional`, `packages`: `name`, `group`, `state`, `version`, `kubaos`), `extra`.
- **Adding a package.** Put it in its group of `system/packages.toml`; the install and the next update install it. No migration.

## Other links (home/links.nix)

- Every file in `scripts/` is linked from the store (`kubaos-scripts`) to `~/.local/bin/<name>`, like the defaults. `~/.zprofile` sources the tty1 autostart snippet (`system/files/hyprland-autostart.zsh`) from the store. Scripts are executable, start with `#!/usr/bin/env bash` (or another env shebang), use `set -euo pipefail`, and are prefixed `dot-`.
- **Never** manage a path under `config/` with a `programs.<x>` option that writes the same file (for example `programs.tmux.extraConfig` or `programs.ghostty.settings`). Install the package with `home.packages` or `programs.<x>.enable` only if that option writes nothing under the linked path. If Nix needs to hand a store path to a config (tmux plugins, for example), write it to a generated file outside the app's dir, such as `~/.config/tmux-nix/plugins.conf` via `xdg.configFile."tmux-nix/plugins.conf"`, and have the config `source` it if it exists.

The matugen colours reach Files through `~/.config/gtk-4.0/gtk.css` (`home/theme.nix`), which libadwaita reads at start.

A command that fails says so through `notify-send`. Bulk rename is Nautilus's own (`F2` on a selection).

- **yazi.** `kubaos-files open [PATH|URI]...` runs `ghostty -e yazi -- <entries>`, in a systemd scope of its own (`kotodama_extension::launch`). A path, `~`, or a `file://` URI on this machine (no host, `localhost` or the host name), percent-escapes undone; a path that doesn't exist becomes its nearest folder that does. No entry is the home folder. yazi opens a folder inside it and a file in its folder with the file hovered; several entries are tabs. It prints `<n> moved` and notifies. The setting is the file `~/.config/kubaos/desktop/files/tidy-downloads`: `tidy on` writes it, `tidy off` removes it, off by default. ## Removable drives (home/automount.nix, crates/kubaos-automount)

- The user unit `kubaos-automount.service` (`WantedBy=default.target`) runs `kubaos-automount watch`, a udisks2 client on the system bus (zbus). It reads udisks2's objects at start and follows `InterfacesAdded`, `InterfacesRemoved` and `PropertiesChanged`. A block device is mounted (`Filesystem.Mount`, `auth.no_user_interaction`, so udisks2's polkit rules for the active session decide) when it has a filesystem, isn't mounted, isn't `HintIgnore`, isn't in fstab or crypttab, and its drive is `Removable` and not `HintSystem`. A LUKS device isn't unlocked: a notification, "<name> is encrypted", opens Files, whose sidebar asks for the passphrase, and the cleartext device that gives is never mounted by the service. Drives present at start are mounted too.
- **Setting.** `~/.config/kubaos/desktop/files/no-automount` turns mounting off (`kubaos-automount off` writes it, `on` removes it); the service reads it on each new device, so it takes effect at once. Eject keeps working.
- **Notifications** (`org.freedesktop.Notifications`, the shell's server): "<name> is ready" with the actions Open (also the click; `nautilus --new-window <mount point>`), Import photos when the mount point holds a `DCIM` folder (case-insensitive), and Eject.
- **Drives file.** `$XDG_RUNTIME_DIR/kubaos-drives`, rewritten atomically on each change: a line per mounted removable drive, its udisks2 drive object path, its name (the label, else vendor and model, else the device file) and its mount points, separated by tabs (a tab or newline in a name becomes a space; a mount point with one is left out). The unit deletes it when the service stops. The KubaOS Extension watches it and sends an "Eject <name>" Item a line, id `drive:<last part of the object path>`, which runs `kubaos-automount eject <object path>`.
- **Eject.** `kubaos-automount eject TARGET` (a drive object path, a block device path, a device file or a mount point) unmounts every filesystem on the drive, locks its unlocked LUKS devices, then powers the drive off (`Drive.PowerOff`), or ejects it (`Drive.Eject`) when it can't be powered off. A busy filesystem leaves the drive mounted with "<name> is still in use". It notifies how it went; exit 1 puts the reason on stderr.
- **Import.** `kubaos-automount import FOLDER` copies the photos and videos under FOLDER's `DCIM` (or FOLDER itself without one; hidden entries and symlinks skipped) into `<XDG pictures folder>/<year>/<month>/`, by EXIF `DateTimeOriginal`, else `DateTime`, else the file's mtime in UTC. A file whose name and size are already in that month's folder is skipped; another file of the same name is copied as `<name> (n).<ext>`. Each copy is written under a temporary name, given the source's mtime, then renamed. The source is only read. It prints and notifies `<copied> copied, <already> already there, <failed> failed`; exit 1 when any failed.
- Exit 2 is a usage error for every command.

## Bluetooth pairing (home/bluetooth.nix, crates/kubaos-bluetooth)

- bluetoothd asks a pairing agent (`org.bluez.Agent1`) for every code a pairing needs. With none registered it pairs as `NoInputNoOutput`, so a keyboard that wants its passkey typed never pairs, and while a `Pair` hangs, bluetoothd keeps discovery suspended. The user unit `kubaos-bluetooth.service` (`Type=dbus`, `WantedBy=default.target`) runs `kubaos-bluetooth agent`, which registers `/org/kubaos/bluetooth/agent` with capability `KeyboardDisplay` and makes it the default agent (`RequestDefaultAgent`), again each time `org.bluez` reappears on the system bus. Ubuntu's `/etc/dbus-1/system.d/bluetooth.conf` (BlueZ's own) already lets any user call `org.bluez` and lets bluetoothd call `org.bluez.Agent1`; nothing in `system/` changes it.
- **Requests.** `DisplayPasskey` and `DisplayPinCode` show the code ("Type this on <device>, then Enter", with the digits typed so far) until bluetoothd's `Cancel` or the end of the pairing. `RequestConfirmation` and `RequestAuthorization` ask Pair or Cancel; `RequestAuthorization` for the device being paired from the shell is allowed without asking. `RequestPasskey` (six digits) and `RequestPinCode` (1 to 16 letters or digits) ask for input; anything else is `org.bluez.Error.Rejected`. `AuthorizeService` is allowed for a trusted device and the one being paired, rejected otherwise. A prompt nobody answers in 50 s is `org.bluez.Error.Canceled`, under bluetoothd's own 60 s limit. A new request replaces the open prompt.
- **State.** The agent writes `$XDG_RUNTIME_DIR/kubaos-bluetooth.json`, replaced atomically on every change: `{"agent": <registered with bluetoothd>, "prompt": {"id", "kind": "display-passkey"|"display-pin-code"|"confirm"|"authorize"|"passkey"|"pin-code", "device": <object path>, "name", "code": <six digits or the PIN>|null, "entered": <digits typed>|null}|null, "pairing": [<object paths>], "errors": {<object path>: <short reason>}}`. The unit deletes it when the agent stops. `config/quickshell/services/Bt.qml` watches it (`FileView` + `watchChanges`); no file means no agent.
- **Commands.** The shell calls the agent's session-bus service `org.kubaos.Bluetooth` (`/org/kubaos/Bluetooth`, `org.kubaos.Bluetooth1`) through `kubaos-bluetooth pair DEVICE`, `cancel DEVICE`, `answer ID yes|no [VALUE]` and `scan on|off ADAPTER` (BlueZ object paths). Exit 2 is a usage error; exit 1 puts the reason on stderr as one line, which the tab shows.
- **Pairing.** `pair` calls `Device1.Pair` and returns at once. After 90 s it calls `CancelPairing` and fails as "Timed out". A pairing that succeeds (or finds the device already paired) sets `Trusted` and calls `Connect`. One that fails keeps its reason under the device for 30 s (BlueZ's `TemporaryTimeout`), then the agent removes the device unless it got paired meanwhile, since `Pair` makes a device permanent in BlueZ before it tries. `cancel` calls `CancelPairing`; when bluetoothd has no pairing to cancel, the agent ends its own as "Cancelled". Every call to bluetoothd times out after 2 minutes.
- **Scanning.** bluetoothd keeps one discovery session per D-Bus connection and answers a second `StartDiscovery` from it with `InProgress`, even while it has that session suspended and shows `Discovering` false. `scan on` therefore calls `StopDiscovery` then `StartDiscovery`, on the agent's connection; `scan off` stops it. The scan button shows `Adapter1.Discovering`. `NotReady` from bluetoothd reads "Bluetooth isn't responding. Restart it: sudo systemctl restart bluetooth"; KubaOS doesn't restart bluetoothd itself, as that needs root.
- **The tab.** A new prompt opens the control center on the Bluetooth tab. Enter or a click on a device that is pairing cancels it; on a paired one it connects or disconnects through Quickshell.Bluetooth. An adapter that is off shows a power button (`Adapter1.Powered`, as the quick tile); if it is still off 4 s later, the tab says to restart bluetoothd. An rfkill-blocked adapter (`BluetoothAdapterState.Blocked`) says `rfkill unblock bluetooth`.

## Phone link (home/phone.nix, crates/kubaos-phone)

- **Opt-in.** KDE Connect (`kdeconnect-kde`, curated) ships with KubaOS, but kdeconnectd runs only while `~/.config/kubaos/desktop/phone/phone-link` exists. The user unit `kubaos-phone.service` (`Type=dbus`, `BusName=org.kde.kdeconnect`, `PartOf` and `WantedBy=graphical-session.target`) runs kdeconnectd from the store with `ConditionPathExists` on that file, so a login starts it exactly when the link was left on. KDE Connect's package isn't in the profile: its D-Bus activation file and its XDG autostart entry are nowhere the bus or a session looks, so nothing starts kdeconnectd behind the flag. The flag is in the user layer and not in `kubaos.d`: it takes effect at once, needs no switch, and the user layer is where the other on/off switches live (`files/no-automount`, `files/tidy-downloads`).
- **Commands.** `kubaos-phone on` writes the flag, then `systemctl --user start kubaos-phone.service`, and waits up to 10 s for `org.kde.kdeconnect` on the session bus; `off` removes the flag, then stops the unit. `status [--json]` prints `{"on", "running", "name", "addresses", "devices": [{"id", "name", "kind", "paired", "reachable", "wants_to_pair", "verification_key", "battery": {"charge", "charging"}|null}]}`; while the link is off it reads nothing from the bus and `name` is the host name. `accept DEVICE` accepts a pairing request, and only from a device asking (`isPairRequestedByPeer`). `send-clipboard`, `send-file PATH` (`~` expanded; a `file://` URL with everything outside the unreserved set escaped), `ring` and `unpair` take an optional phone, by id or name in any case, else the paired one in reach. Exit 2 is a usage error; exit 1 puts the reason and what to do on stderr. Every command but `status` notifies how it went (`notify-send`, app name Phone), since the menu runs them with no terminal.
- **The bus.** `kubaos-phone` and Kōbō call kdeconnectd through `busctl --user --auto-start=no --json=short`: `org.kde.kdeconnect.daemon` on `/modules/kdeconnect` (`announcedName`, `devices(false, false)`), the properties of `org.kde.kdeconnect.device` on `/modules/kdeconnect/devices/<id>` (`acceptPairing`, `unpair`), and the plugins below it (`/clipboard` `sendClipboard`, `/share` `shareUrl`, `/findmyphone` `ring`, `/battery` `charge` and `isCharging`). A device id is letters, digits and underscores, or it is refused. The laptop's addresses come from `ip -j -4 addr show scope global`, leaving out `docker*`, `br-*`, `veth*` and `virbr*`. Checked against kdeconnectd 26.04 (the curated one) and 26.08.
- **Plugins.** A device keeps only `kdeconnect_clipboard`, `_share`, `_ping`, `_battery`, `_findmyphone`, `_findthisdevice` and `_connectivity_report` (`kubaos_phone::phone::LINK_PLUGINS`), plus the names listed one a line in `~/.config/kubaos/desktop/phone/plugins` (blank lines and `#` comments skipped). `kubaos-phone restrict` turns every other plugin a device supports off (`isPluginEnabled`, `setPluginEnabled`, which kdeconnectd keeps in the device's config), for every device it knows, paired or asking; it never turns one on, so a plugin the user switched off stays off. It runs in `on`, before and after `accept`, and as the unit's `ExecStartPost`, so plugins a later KDE Connect adds are off from its first start; a failure there stops the unit. A pairing accepted from KDE Connect's own notification instead of the card is restricted at the next start.
- **The card.** Kōbō's "Your phone" card (docs/INSTALL-INTERNALS.md, "First boot") goes through the same library in process (`kubaos_core::setup::Sys::phone`).
- **Firewall.** KubaOS turns no firewall on. With one, KDE Connect needs TCP and UDP 1714-1764 and mDNS (UDP 5353) open on the local network.

## System monitor (home/sysmon.nix, crates/kubaos-sysmon)

- **Engine.** `kubaos-sysmon serve`, started by the shell (`config/quickshell/services/Sysmon.qml`) for its life and restarted with a backoff, reads `/proc` and `/sys` itself; no process is spawned per sample. It writes a line of JSON a sample on stdout, `{"type":"sample","t":<ms>,"detail":<bool>,"cpu","memory","gpus","disks","io","snapshots","net","battery","fans","top","uptime","kernel"}` (camelCase keys, `null` or `[]` where the machine has no such sensor), and `{"type":"alert","id","title","body","action","actionLabel"}` when an alert fires.
- **Pace.** The shell sends `{"id":n,"op":"mode","mode":"pill"|"quiet"|"popup"|"paused"}`: a light sample every 2 s for the pill (every 10 s, `quiet`, while a power stop holds background work back), a detailed one (per core, clock, fans, address, disk traffic, the top five processes) every second while the popup is open, none while the session is locked or with the pill hidden and alerts off. Out of a pause the counters start afresh. Requests on stdin, each answered with its `id`: `process` (`pid`: name, command, user, state, parent, threads, memory, start), `signal` (`pid`, `signal` `term` or `kill`; init and the monitor itself refused), `settings`, `set` (`key`, `value`). A failed one gets `{"id","error"}`.
- **Stream file.** Each sample also goes to `$XDG_RUNTIME_DIR/kubaos-sysmon.json`, replaced atomically. The KubaOS Extension answers `cpu`, `ram`/`memory` and `battery` from it while it is under 10 s old, else reads `/proc` and `/sys` itself, so the pill, the popup and the menu show one reading.
- **Alerts** (on by default): CPU over its temperature for 30 s, memory over its threshold for 10 s (naming the process holding the most), a watched disk over its threshold, the battery drawing over its threshold for 30 s while discharging. Each fires once while its condition holds, and again only once it has cleared and 10 min have passed; the shell shows it as a notification whose button runs `qs ipc call sysmon act <action>`. In the pill's pace the processes are scanned only while a CPU, memory or battery condition holds, so the alert can name the busiest.
- **Sources.** CPU temperature from hwmon (`k10temp` Tctl, `zenpower`, `coretemp` package, else a thermal zone); fans from every hwmon `fan*_input`, so TUXEDO's drivers show where they expose them; amdgpu's `gpu_busy_percent`, `mem_info_vram_*` and hwmon; a discrete GPU that is runtime-suspended is listed as asleep and not read, since reading it would wake it. NVIDIA's usage needs `nvidia-smi`, so only its presence and power state show. Disks are `/`, `/home` on its own device and anything under `/media` or `/run/media`; Btrfs snapshot space comes from qgroups in sysfs and is unknown without quotas.
- **Processes from the menu.** `kill NAME` and `end NAME` list the processes whose name holds NAME, one result a name; End and Kill both ask first, then signal every process of that exact name, scanned again.
- **Commands.** `kubaos-sysmon sample` (one detailed sample as JSON), `settings` (JSON), `set KEY VALUE` (`pill`/`alerts` `on|off|toggle`, `style`, `metrics` as words, `cpu-temp`, `ram`, `disk`, `battery-draw`). Exit 2 is a usage error.

## Power stops (home/power.nix, crates/kubaos-power)

- **The stops.** Super Saver, Power Saver, Balanced, Performance and Max Performance, in that order on the slider. power-profiles-daemon stays the one profile switch other tools see: Super Saver and Power Saver sit on its `power-saver`, Balanced on `balanced`, Performance and Max Performance on `performance`. `kubaos_power::plan::Plan::for_stop` is the one place a stop becomes its settings, the CPU scheduler among them (`Scheduler::Kernel`, or `Scheduler::Lavd` in the stop's mode when `scheduler = "lavd"`; "The CPU scheduler" below); `docs/USING.md`, "Power", has the table. ppd owns the rows it sets on its profile and sets again on every power change (EPP, `balance_power` on battery and `balance_performance` plugged in for Balanced; per-policy boost; the minimum clock; the platform profile); the service writes the rest after it, so its values are the last word: every policy's `scaling_max_freq`, amdgpu's `power_dpm_force_performance_level`, `panel_power_savings` of each connected `eDP` connector, `/sys/module/pcie_aspm/parameters/policy`, each USB device's `power/control`, `iw` power saving on each Wi-Fi interface, and the charge limit (TUXEDO's `charging_profile`, else `charge_control_end_threshold`). A knob the machine lacks is skipped, and `status` says so.
- **Service.** `kubaos-power serve`, the user unit `kubaos-power.service` (WantedBy and PartOf `graphical-session.target`), follows ppd's `ActiveProfile` and UPower's `OnBattery` and display device `Percentage` on the system bus, and answers one line a connection on `$XDG_RUNTIME_DIR/kubaos-power.sock` (`set STOP`, `undo`, `reload`, and `retry-scheduler`, a `reload` that also lets a LAVD systemd gave up on start again; `ok …` or `error …` back). `kubaos-power set STOP` (and `kubaos power set`) speak it; with no service, `set` changes ppd's profile alone. It replaces `$XDG_RUNTIME_DIR/kubaos-power.json` whole on every change, `{"stop","index","title","source","dropped_from","quiet","pid","refused"}`, which the shell watches (`services/Power.qml`: the slider, the bar's icon, the system monitor's `quiet` pace). Both files go when the unit stops.
- **Which stop.** Each power source remembers the stop last picked on it, battery and plugged in apart, in `~/.local/state/kubaos/power/stops.json` (`{"battery","ac","last":{"source","stop"},"dropped_from","undone"}`); before any pick, battery is Power Saver and plugged in Balanced. A plug or unplug counts once `OnBattery` has held for 3 s (a bouncing dock switches nothing), and moves to the new source's stop with a low-urgency toast. A ppd profile set from outside lands on the stop named like it, as the current source's pick, or on the source's own stop when the profile is that stop's (Super Saver's `power-saver`). A profile a program holds (ppd's `ActiveProfileHolds`, GameMode's) is followed but never remembered, and its end, ppd going back to the profile before it, returns to the source's own stop. At its start the service keeps the stop it left, when the source is the same and ppd's profile still fits it, follows ppd when it no longer does (changed while nothing watched), and takes the source's stop on the other source. The low-battery drop: at `low_battery` % or under, on battery, above the drop's stop, the stop drops there with a toast whose Undo (`kubaos-power undo`) goes back to the remembered stop; the drop is never the battery's pick, plugging in ends it, and after an Undo, or a pick made under the level, no drop comes until the next unplug. `kubaos_power::control` decides all of it, tested with fakes. The service also follows udev's GPU, screen and USB events (`udevadm monitor`) and ppd's profile changes, and once they have been quiet for a second (5 s at most after the first) writes whatever the stop lacks again: Max Performance's GPU `high`, which ppd's `amdgpu_dpm` action puts back to `auto` on a screen's arrival, and a newly plugged device's autosuspend. The runtime file names the service's `pid`; the shell checks `/proc/<pid>/comm`, so the file of a service killed outright isn't taken for a running one.
- **Root.** The writes go through `/usr/local/libexec/kubaos-power-write` (`system/files/power/`), run as `pkexec --disable-internal-agent` with only the knobs that differ, as `knob=value` arguments: `cpu-max=KHZ|max`, `gpu-dpm=CARD:LEVEL`, `panel-power=CONNECTOR:0-4`, `aspm=POLICY`, `usb=DEVICE:auto|on`, `wifi=INTERFACE:on|off`, `charge-profile=PROFILE`, `charge-end=BATTERY:PERCENT`, `scheduler=powersave[:CPUS]|autopilot|performance|off|reset` ("The CPU scheduler" below). It checks each name and value against its own patterns and that the device exists, writes only what differs, never sets `auto` on a device with a HID, smart card or audio interface or Yubico's vendor id, and goes on past a knob that fails, an unreadable file included, naming it on stdout as `failed KNOB=VALUE` (exit 1 then, 2 for a usage error). The service leaves a refused knob alone until the stop or the settings change, and `kubaos power status` says which the kernel refused. The stops keep printers, CDC network adapters and Realtek's USB Ethernet (docks' r8152) awake too. pkexec is `/usr/bin/pkexec`. polkit action `org.kubaos.power.write` (`org.kubaos.power.policy`, `auth_admin_keep`); `50-kubaos-power.rules` lets a local, active member of `sudo` or `admin` through without a password, as the keyboard's rule does: polkit counts the user manager's processes in the user's display session (`sd_uid_get_display`), and with no agent to ask, pkexec would refuse without one. `install_power_helper` (`system/lib.sh`) installs them from `system/30-hardware.sh` and the `power-helper` system migration, with `/etc/modprobe.d/kubaos-amdgpu.conf` (`amdgpu freesync_video=1`; `update-initramfs -u -k all` while the initramfs of any kernel in `/lib/modules` lacks it, so a failed rebuild is tried again), and on the first install and in the migration only (`install_power_helper --actions`), ppd's `amdgpu_dpm` action on and its `amdgpu_panel_power` action off: that one rewrites `panel_power_savings` at every battery percent, and the stops own it.
- **The CPU scheduler.** Off by default (`scheduler = "kernel"`): Linux's EEVDF. With `scheduler = "lavd"`, scx_lavd (nixpkgs' `scx.rustscheds` 1.1.2, only its `scx_lavd` copied out as the curated `scx-lavd`, `home/curated.nix`) runs as root from the system unit `kubaos-scx.service` (`system/files/systemd/`), `ExecStart=/usr/local/libexec/kubaos-scx-lavd $LAVD_ARGS` with `EnvironmentFile=/var/lib/kubaos/scx-lavd.env`, `Restart=on-failure`, `RestartSec=2`, `StartLimitBurst=3` in `StartLimitIntervalSec=5min`, conditioned on `/sys/kernel/sched_ext` and the env file. No `scx_loader`. Modes by stop: Super Saver `--powersave --cpu-pref-order …` (the CPUs from slowest core to fastest by `amd_pstate_highest_perf`, else ACPI CPPC's `highest_perf`, each core's threads side by side: `4,16,5,17,…,11,23,0,12,…,3,15` on the HX 370; plain `--powersave` where the cores are all alike), Power Saver `--powersave`, Balanced `--autopilot`, Performance and Max Performance `--performance`. LAVD's own powersave order sorts by last-level cache before capacity without an energy model, which would start on the Zen 5 cores; its `--autopower` follows ppd's three profiles, with no autopilot and no core order, so a mode change is a restart, EEVDF running for that moment. The helper's `scheduler=MODE[:CPUS]` checks the mode, that CPUS (powersave only) are distinct CPUs that exist, that `/sys/kernel/sched_ext` and the binary are there; writes the env file (`KUBAOS_SCHEDULER=` the value, `LAVD_ARGS=` the command line; mode 0644, the service reads it back) when it differs; enables the unit; and starts it, or restarts it when the mode changed, after `reset-failed` so that starts asked for never count towards the start limit; a unit waiting to restart after a crash (`SubState=auto-restart`) is left alone when the mode is the same, so stops during a crash loop never grant it fresh restarts. A unit systemd gave up on (`failed`) is never started: its new mode is kept and the knob fails until `scheduler=reset` (`reset-failed`). `scheduler=off` removes the env file, then `disable --now`s the unit and resets a failure. The service sends `scheduler=` only at a stop or a settings change, last, never on a recheck: `off` while the env file names a mode or LAVD runs, the stop's mode when sched_ext and the binary are there and LAVD doesn't run or runs another mode, preceded by `reset` after `retry-scheduler`. "LAVD runs" is `/sys/kernel/sched_ext/state` `enabled` with `root/ops` starting `lavd`. The kernel ejects a BPF scheduler that errors or stalls and goes back to EEVDF by itself; scx_lavd then exits with an error (or a signal kills it) and the unit restarts it. The service `Subscribe`s to systemd on the system bus and follows the unit's `PropertiesChanged` (`LoadState`, `ActiveState`, `SubState`, `Result`, `NRestarts`), and while LAVD is on toasts the moment the unit enters `auto-restart` (normal urgency; it promises no restart, since the crash that reaches the start limit enters `auto-restart` too) or `failed` (critical), and logs it; a unit found that way at the service's start is said too. A clean exit (SysRq-S) is no fallback and stays stopped until the next stop. `install_scx` (`system/lib.sh`, from `system/60-nix.sh` and `system/relink.sh`, so every update and rollback) builds `.#scx-lavd`, pins it with the GC root `/nix/var/nix/gcroots/dotfiles-scx-lavd`, links `/usr/local/libexec/kubaos-scx-lavd` to it, installs the unit (`daemon-reload` when it changed) and restarts a running LAVD on a new build or unit file, after `reset-failed`; it never enables the unit. The `sched-ext-lavd` system migration reinstalls the helper. Secure Boot: Ubuntu's kernel has `CONFIG_SCHED_CLASS_EXT=y` and BTF, and lockdown `integrity` restricts no BPF feature scx_lavd uses, so nothing is signed.
- **The laptop panel.** The service writes `refresh=60|native` and `vrr=0|1` to `$XDG_RUNTIME_DIR/kubaos-power/panel` and runs `hyprctl -i <instance> eval 'dot.power_panel()'`; `hyprland.lua` runs it after the user layer at every config load, so a reload keeps the stop. **VRR** goes through the global `misc:vrr` (`hl.config`), never the panel's rule: Hyprland 0.56 leaves a running screen alone when its new rule differs only in `vrr` (`CMonitorRule::compare` doesn't read it), while `misc:vrr`'s refresh runs `ensureVRR` on every screen, an adaptive-sync commit with no modeset. So `config/hypr/monitors.lua` gives the panel (`eDP-1`) a rule of its own with no `vrr`, and wraps `hl.monitor` to give every other output's rule `vrr = 0` unless the user's names one: the stops never reach an external screen, and `misc:vrr` belongs to them. Without the service's file the panel starts with VRR. A Hyprland whose screens were set up before these rules keeps `misc:vrr` off until it starts again (its first config load, before any screen, leaves `$XDG_RUNTIME_DIR/kubaos-power-vrr-<instance>`). **The rate** goes through the panel's own rule, which `hl.monitor` merges into by output name: `dot.power_panel()` sets only `mode`, the rule's size at 60 or the config's own mode back, so position, scale and the rest stay. 60 Hz is asked for only when `/sys/module/amdgpu/parameters/freesync_video` is on, where amdgpu's FreeSync video mode keeps the native timing and stretches the vertical blank, so the switch is seamless; without it Super Saver keeps the native rate with VRR, and `status` says the 60 Hz waits for a reboot. A panel the lid turned off stays off.
- **Background work.** The saver stops hold the file indexer paused through `localsearch inhibit sleep infinity` in the transient user unit `kubaos-power-quiet` (stopped to resume, and with the service), and the system monitor samples the pill every 10 s.
- **Commands.** `kubaos power` runs `kubaos-power`: `set STOP`, `undo`, `status` (every row, what the stop wants and what the machine says now, `✗` where they differ, and what this machine lacks), `measure [--seconds N]` (default 120: the battery's average draw sampled every second from `/sys/class/power_supply`, and the top ten interrupt lines and processes by wakeups per second, from `/proc/interrupts` and each process's context switches; saved in `~/.local/state/kubaos/power/measure/<time>-<stop>.txt`), `panel-power-saving on|off`, `charge-limit 80|90|100`, `low-battery power-saver|super-saver|off|PERCENT`, `panel STOP 60hz|vrr|native`, `apply`, `scheduler [status]` (which CPU scheduler runs and why, the mode in this stop, the unit's state and scx_lavd's last `Error:` line this boot from its journal, read with the `adm` or `systemd-journal` group), `scheduler on|off` (writes `scheduler`, then `retry-scheduler` or `reload`). `status` has a "CPU scheduler" row with the same why. Exit 1 is a refusal, 2 a usage error.
- **Command menu.** An Item a stop (`super-saver`, `power-saver`, `balanced`, `performance`, `max-performance`, the middle three the old toggles' ids), the Extension's own "Power: what this stop does" (`power-status`, the rows as a List View), "Undo the low-battery drop", the low-battery drop's three stops and level, panel power saving on and off, the charge limit at 80, 90 and 100 %, "Measure power draw" (for 2 minutes, or as long as typed), and "CPU scheduler: LAVD on" and "CPU scheduler: LAVD off" (`cpu-scheduler-lavd-on`, `cpu-scheduler-lavd-off`), in `config/kotodama/kubaos.toml`; and the Extension's "CPU scheduler: status" (`cpu-scheduler-status`, the report as a List View: what runs with why under it, then a row a detail).

## Proxy (home/proxy.nix, crates/kubaos-proxy)

- **The profile.** `~/.config/kubaos/desktop/network/proxy.toml` (seeded from `user-layer/desktop/network/proxy.toml`, every part commented out): `[tunnel]` `conf` (the `.conf` beside it without its keys, `kubaos-proxy import` writes it and this key), `kill_switch` (default true) and `vault_item` (default `kubaos-proxy`); `[dns]` `servers` and `domains`; `[http]` `proxy` (`http://` or `https://`, a host and a port, nothing else: no user, password or path), `pac` (`http(s)://`, no quotes, backslashes or spaces) and `no_proxy` (always led by `localhost`, `127.0.0.1`, `::1`); `[ca]` `file` (PEM, at most 64 KiB). An unknown key, a value outside its pattern, or `[dns]` without a tunnel refuses the whole profile; no file is no part. The `.conf`'s `DNS =` addresses and names count as `[dns]` servers and domains. A full tunnel is any peer whose `AllowedIPs` has `0.0.0.0/0` or `::/0`.
- **On and off.** `kubaos-proxy on` puts the parts up in this order and `off` takes them down in the other: the tunnel; the root helper's parts; the session's variables; GNOME's proxy; Docker's client proxy; git's. A part that fails takes every part before it (and itself) away again, so the Proxy is wholly on or off; `off` that fails to take a part away puts the ones it took down back. What is up is `~/.local/state/kubaos-proxy/applied` (a part a line), written after each part, so it outlives a crash or a reboot. A part is written there before it goes up. Taking a part away removes whatever of it KubaOS put there, whatever the profile says now, and puts back what the user had ("The session" below). The session lock is `$XDG_RUNTIME_DIR/kubaos-proxy/lock`; `$XDG_RUNTIME_DIR/kubaos-proxy/wanted` exists while the user wants it on.
- **The tunnel.** A NetworkManager WireGuard connection made at every `on` through `AddAndActivateConnection2` with `persist=volatile`: id `kubaos-proxy`, interface `wg-kubaos`, `autoconnect=false`, `permissions=user:$USER`, `wireguard.fwmark=0x6b6f`, the `.conf`'s addresses, MTU, listen port and peers (endpoint, allowed IPs, keepalive). An endpoint's name is resolved by `kubaos-proxy`, and NetworkManager is given the address, kept in `~/.local/state/kubaos-proxy/endpoints` (`HOST PORT ADDRESS` lines): with the kill switch up (a tunnel coming back, a second `on`) the kept address goes first, with no lookup; a name that doesn't resolve uses it too. The private key and each preshared key are in the call with flags `1` (agent-owned): NetworkManager keeps them for the activation, saves them nowhere, and deletes the connection when it goes down. The work DNS rides on it: `dns-data` per family and `dns-search` as routing domains (`~corp.example.com`), which NetworkManager hands to systemd-resolved for `wg-kubaos` alone; a full tunnel with servers adds `~.` and `dns-priority=-50`, so every name goes to the work servers. NetworkManager drops it when the machine sleeps.
- **Keys.** `kubaos-proxy import FILE` puts `PrivateKey` and each `PresharedKey` in the vault (a secure note named by `vault_item`, hidden fields `private-key` and `preshared-key <peer public key>`, created or edited through `bw create|edit item` with the item on stdin) and in the GNOME keyring (`secret-tool`, attributes `service=kubaos-proxy key=private-key`, and `key=preshared-key peer=<public key>`), then writes the `.conf` without them as `wireguard.conf` and sets `conf` in `proxy.toml` (`toml_edit`, comments kept). `on` reads the keys from the keyring; `kubaos-proxy pull` copies them from the vault to the keyring again. A key is on stdin, never in argv; the session goes in bw's environment alone.
- **Root.** `/usr/local/libexec/kubaos-proxy-write` (`system/files/proxy/`), as `pkexec --disable-internal-agent` (action `org.kubaos.proxy.write`, rule `50-kubaos-proxy.rules`: an admin at the machine, local and active, needs no password), installed by `install_proxy_helper` (`system/lib.sh`) from `20-base.sh` and the `proxy-helper` migration. Its arguments, in the order `on` gives them: `killswitch=on` (nftables `table inet kubaos_proxy`: output and forward reject everything but `lo`, `wg-kubaos`, packets marked `0x6b6f`, DHCP, IPv6 neighbour discovery, and the container bridges `docker0`, `virbr0`, `br-*`, `veth*`; no DNS lookup goes out beside the tunnel; only for a full tunnel with `kill_switch`), `ca=-` (one PEM certificate on stdin, read and written back by `openssl x509`: `/usr/local/share/ca-certificates/kubaos-proxy/company.crt` and `update-ca-certificates`, which Nix's `/etc/ssl/certs/ca-certificates.crt` follows, Chrome's `CACertificates` in `/etc/opt/chrome/policies/managed/kubaos-proxy-ca.json`, and a running Docker daemon restarted, as it reads its roots once), `apt=URL` (`/etc/apt/apt.conf.d/80kubaos-proxy`), `docker=URL|NO_PROXY` and `nix=URL|NO_PROXY` (`/etc/systemd/system/{docker,nix-daemon}.service.d/kubaos-proxy.conf`, then `daemon-reload` and `try-restart`; a unit that isn't installed is left alone), `chrome=proxy|URL|NO_PROXY` or `chrome=pac|URL` (`ProxySettings` in `kubaos-proxy.json` beside the CA's), each `PART=off`, and `off` (every part, past one that fails). It checks every value against its own pattern before any part goes, writes only its own files whole, and stops at the first part that fails; `done PART=VALUE` on stdout names each one done. A file whose part failed after it was written (a daemon that wouldn't restart, a trust store that wouldn't update) goes again, so the next run writes it anew. It ignores SIGPIPE, so a caller that stops reading never stops it half way. `stats` prints `wg show wg-kubaos latest-handshakes`. Exit 1 when a part failed, 2 for a usage error, 3 when a value isn't pinned. `KUBAOS_PROXY_ROOT` points it at a fake `/` for the tests (`crates/kubaos-proxy/tests/helper.rs`); pkexec clears it.
- **Pins.** A trusted root and a proxy see all of the machine's traffic, so the passwordless helper puts in place only what an admin pinned in `/etc/kubaos/proxy-pins` (root's, 0644: `ca=` the CA's SHA-256 fingerprint or `none`, `proxy=` URL or `none`, `no_proxy=`, `pac=` URL or `none`); a CA, proxy, `no_proxy` or PAC file that differs exits 3 and changes nothing. The killswitch, every `PART=off`, `off` and `stats` need no pin. `/usr/local/libexec/kubaos-proxy-pin`, the same script by another name, writes the pins (`ca=-|none proxy=URL|none no-proxy=LIST pac=URL|none`, all four, the CA on stdin) under the action `org.kubaos.proxy.pin`, `auth_admin` with no rule: the password every time. `on` pins when the write helper says exit 3, which asks for the password once, then applies again; a profile that keeps its values never asks again.
- **The session.** `systemctl --user set-environment` (and `unset-environment` at `off`) of `http_proxy`, `https_proxy`, `no_proxy` and their capitals, for units started after; the values the user manager had before (`show-environment`) are kept in `$XDG_RUNTIME_DIR/kubaos-proxy/env-before` and set again at `off`. The same as `export` lines in `$XDG_RUNTIME_DIR/kubaos-proxy/env`, which zsh sources at start (`home/shell.nix`, order 1890). GNOME: `org.gnome.system.proxy` `mode` `manual` with `http` and `https` `host`/`port` and `ignore-hosts`, or `auto` with `autoconfig-url` for a PAC file; the seven keys as `gsettings get` had them first are kept in `~/.local/state/kubaos-proxy/gnome-before` and set back at `off`, the mode last. Docker's client: `proxies.default` (`httpProxy`, `httpsProxy`, `noProxy`) merged into `$DOCKER_CONFIG/config.json` (else `~/.docker/config.json`), its mode kept; `~/.local/state/kubaos-proxy/docker-proxies.json` keeps `{"ours","before"}`, and `off` puts `before` back (or removes the key) only while the one there is still `ours`. git: `[http] proxy` in `~/.local/state/kubaos-proxy/proxy.gitconfig`, which `config/git/config` includes.
- **Service.** `kubaos-proxy serve`, the user unit `kubaos-proxy.service` (WantedBy and PartOf `graphical-session.target`), reconciles at its start, after logind's `PrepareForSleep(false)` once NetworkManager is connected again (at most 60 s), and when NetworkManager's `ActiveConnections` change (a burst settles 2 s first), so a tunnel dropped while the machine is awake comes back too: not wanted (a login starts so), whatever `applied` lists and an active tunnel go; wanted, a part not up or a dropped tunnel goes up again with the rest. A tunnel that can't come back takes everything down but the kill switch, when it was up: the Proxy stays wanted, a notification says that "Proxy off" lifts it, and a change of network tries again, at most once in 30 s after a failure (`kubaos_proxy::watch`). Without a kill switch, everything goes and so does the wish. It logs through `log` on stderr, with the journal's priority prefixes.
- **Status.** `kubaos-proxy status [--json] [--live]`; `--json` is `{"configured","wanted","on","busy","parts","tunnel":{"full","killSwitch","endpoint","up","handshake","rxBytes","txBytes"}|null,"dnsServers","dnsDomains","proxy","pac","ca","warnings","problem"}`. `--live` adds the handshake (through the helper's `stats`) and `/sys/class/net/wg-kubaos/statistics`. Every `on`, `off` and reconcile replaces `$XDG_RUNTIME_DIR/kubaos-proxy.json` whole with the status not live, `busy` true while it works; `services/Proxy.qml` watches it. `kubaos proxy` runs `kubaos-proxy`. Exit 2 is a usage error; exit 1 says why on stderr, and `on` and `off` notify it (`notify-send`, app name Proxy).
- **Command menu.** "Proxy on", "Proxy off", "Import WireGuard config…" (in a terminal, for bw's prompt) and "Open proxy settings" (`proxy-on`, `proxy-off`, `proxy-import`, `proxy-settings`) in `config/kotodama/kubaos.toml`, and the Extension's own "Proxy status" (`proxy-status`, the rows as a List View, read live).
- **Shell.** The control center's Proxy tile (shown once the profile has a part) switches it; its arrow opens the detail, which, while it shows and the tunnel is up, reads `/sys/class/net/wg-kubaos/statistics` every 5 s (the bytes moved, and when the tunnel last received), and the handshake through `status --json --live` (pkexec) as it opens and then once a minute. The bar's `ProxyIndicator` shows while it is on.

## Theme pipeline

- Wallpapers: the sets, one folder each, read-only in `/usr/share/kubaos/wallpapers/<set>/` (the flake input `kubaos-wallpapers`, SuplenC/kubaos-wallpapers, with each set's `CREDITS.md`), and the user's own in `~/Pictures/wallpapers/`, a real folder. `~/.config/kubaos/desktop/wallpapers/sets` (user layer, written by the install) names what the picker shows, one entry per line, `#` comments: a set's id for the whole set, `<set>/<file>` for one of its wallpapers (Kōbō writes a set whose wallpapers are all picked by its id, the rest one by one). Home activation seeds it with the sets on disk when it's missing, and `dot-theme` shows every set without it. A set a release adds shows up only once it's added there; a wallpaper a release adds to a set shows up when the set is listed by its id. The picker's folders are `dot-theme folders`: the chosen sets (whole or with a wallpaper picked) by name, then `yours`. `dot-theme wallpapers` lists what each folder shows, `folder<TAB>path` in order; the Quickshell picker and `next`/`prev` show only those. `dot-theme all-sets` rewrites the file with every set on disk, whole. `dot-theme show-set <set>` lists a set by its id, its single wallpapers dropped (a no-op without the file); `dot-theme hide-set <set>` drops its lines (writing every set first without the file) and refuses when no set on disk would be left. Both write through `sets.new` and a rename. The KubaOS Extension (`crates/kotodama-kubaos/src/wallpapers.rs`) watches the file and sends one Item a set on disk, with Show and Hide running those two. On first boot (no wallpaper yet) the wallpaper is `DEFAULT_WALLPAPER` when the picker shows it, else the first wallpaper of the first folder. A wallpaper is an image (jpg, jpeg, png, webp) or a video (mp4, webm, mkv, mov). A video's still is `<name>.poster.jpg` next to it, else `~/.local/state/theme/posters/<md5 of the path>.jpg`, which `dot-theme` cuts with ffmpeg when needed. Posters are never listed as wallpapers. `dot-theme` keeps paths under `/usr/share/kubaos/wallpapers` as given (it does not resolve the link into the store), so `wallpaper` and `colors.json` name that path. - Scheme: matugen `scheme-fidelity`, set once in `scripts/dot-theme` (`SCHEME`). First boot with no state uses `DEFAULT_WALLPAPER` (`shinjuku/kubaos-neon-sign.jpg`), and so does `apply` when the wallpaper in `wallpaper` is gone: a deleted file, or a live scene (`ukiyo:<id>`) from a release that shipped them. On that last one `apply` also stops and disables a leftover `ukiyo.service`.
- Command: `dot-theme` (owned by theme).
  - `dot-theme set <file>`: set wallpaper and regenerate colors. For a video matugen reads the poster, then `dot-theme` writes the video's path as `wallpaper` in `colors.json`, `hypr.lua` and `nvim.lua`
  - `dot-theme next` / `dot-theme prev`: next/previous wallpaper (stills and videos) in the current folder
  - `dot-theme folder <name>` (one of `dot-theme folders`) and `dot-theme toggle-folder` (cycles them)
  - `dot-theme wallpapers` (what the picker shows) and `dot-theme all-sets` (every set again, whole)
  - `dot-theme show-set <set>` / `dot-theme hide-set <set>`: one set into the picker, whole, or out of it; the last set stays
  - `dot-theme apply`: regenerate from the current wallpaper (used at login). Skips matugen and the reloads when the wallpaper (path, mtime, size; for a video also its poster's), the scheme, the mode, the matugen binary and the content of `config/matugen/config.toml`, `config/matugen/templates/*` and the oh-my-posh template all match the last successful run, and every output file exists. The record is `~/.local/state/theme/.stamp`, written after each successful run. `dot-theme apply --force` always regenerates; `set`, `next`, `prev`, `folder` and `toggle-folder` always do.
  - `dot-theme current`: print current wallpaper (absolute path)

Moving wallpapers (`services/Motion.qml`): a video decodes on a screen only when the mode allows it (`always`, or `ac` and UPower says not on battery), the session isn't locked, there has been input within `Settings.screenOffAfter` seconds (600, hypridle's DPMS timeout), and that monitor's active workspace has no fullscreen window. Otherwise the poster shows and the decoder is released. The lock screen plays the wallpaper if it's a video, else `Settings.lockLoop` (`""`, the blurred still), under the same rules minus the lock. One decoder per screen.

Screen recording state: `scripts/dot-hypr-record` writes `$XDG_RUNTIME_DIR/dot-record.json`, replaced atomically on every change: `{"state": "idle"|"recording"|"replay", "mode": "region"|"window"|"output"|"", "pid": <recorder pid>|null, "file": "<mp4 or replay dir>", "backend": "gsr"|"wf-recorder", "started": <unix seconds>}`. Quickshell watches it (`services/Recorder.qml`, `FileView` + `watchChanges`) and creates it as `{"state":"idle"}` when missing. A state other than `idle` whose pid is dead counts as idle; the script repairs it on its next run. Recordings go to `~/Videos/Recordings/` (`$DOT_RECORD_DIR`), screenshots to `~/Pictures/Screenshots/`; satty saves `<name>-annotated.png` next to the original.

Screen capture: gpu-screen-recorder (Nix) records through KMS. Its helper `gsr-kms-server` needs `CAP_SYS_ADMIN`, which a file in the Nix store can't carry, so `system/65-recorder.sh` copies the helper of KubaOS's nixpkgs build (`KUBAOS_DIR`, `system/lib.sh`) to `/usr/local/libexec/dotfiles/gsr-kms-server` (root:<user> 0750, `cap_sys_admin+ep`, GC root `/nix/var/nix/gcroots/dotfiles-gpu-screen-recorder`) and links `/run/wrappers/bin/gsr-kms-server` to it (`/etc/tmpfiles.d/dotfiles-gsr.conf`); nixpkgs' gsr wrapper looks there first. `system/relink.sh` re-runs it on every `kubaos update` and `kubaos rollback`, because gsr and its helper must be the same version. Without it gsr asks for the password through polkit.

PAM: the lock screen runs PAM conversations in parallel: `/etc/pam.d/qs-lock` (password, `pam_unix`), `/etc/pam.d/qs-lock-u2f` (FIDO2 security key, `pam_u2f` with `userverification=1 pinverification=0`: an enrolled finger, never a PIN; `Settings.u2f`, on; only when `/etc/u2f_mappings` has a line for the user) and `/etc/pam.d/qs-lock-fingerprint` (`pam_fprintd`, `Settings.fingerprint`, off). They live in `system/files/pam.d/`; `system/50-hyprland.sh` installs `qs-lock` and `qs-lock-fingerprint`, `system/70-bitwarden.sh` installs `qs-lock-u2f`. Quickshell links Nix's libpam, so `pam_unix.so` resolves to Nix's module; `system/` links `/run/wrappers/bin/unix_chkpwd` to Ubuntu's helper (tmpfiles.d), and the fingerprint file loads nixpkgs' `pam_fprintd.so` from the root-owned link `/usr/local/lib/security/pam_fprintd.so`. `system/60-nix.sh` and `system/relink.sh` build `fprintd` from KubaOS's nixpkgs (`--inputs-from $KUBAOS_DIR`), point the link at its store path and pin that path with the GC root `/nix/var/nix/gcroots/dotfiles-pam-fprintd` (`link_pam_fprintd` in `system/lib.sh`). `qs-lock-u2f` does the same with nixpkgs' `pam_u2f` (`/usr/local/lib/security/pam_u2f.so`, GC root `dotfiles-pam-u2f`, `link_pam_u2f`, created by `system/70-bitwarden.sh`, relinked by `system/relink.sh`). Nothing under `$HOME` is on the PAM load path. Ubuntu's modules by absolute path do not load under Nix's libpam. hypridle's `|| hyprlock` is the fallback locker.

Security key outside the lock screen: `system/70-bitwarden.sh` adds two lines, `auth sufficient pam_u2f.so authfile=/etc/u2f_mappings cue nouserok userverification=1 pinverification=0 [cue_prompt=Touch the fingerprint sensor]` and the same with `userverification=0 pinverification=1` (PIN fallback), above `@include common-auth` in `/etc/pam.d/sudo`, `sudo-i` and `polkit-1` (Ubuntu's module, Ubuntu's libpam), plus a `polkit-agent-helper@.service` drop-in that lets the helper see `/dev/hidraw*`. `/etc/u2f_mappings` is root:root 0644 and only `dot-u2f-enroll` (through sudo) writes it. The password always stays below as the fallback.

Polkit: the in-shell agent is off by default (`Settings.polkitAgent: false`) and Hyprland starts `hyprpolkitagent` (`POLKIT_AGENT = "hyprpolkitagent"` in `config/hypr/autostart.lua`). Flip both together.

Volume and brightness keys are bound in Hyprland directly to `wpctl` and `brightnessctl`. Quickshell shows the OSD by watching PipeWire and the backlight itself.

## Secrets (docs/SECRETS.md)

- `SSH_AUTH_SOCK` is `~/.bitwarden-ssh-agent.sock` (Bitwarden desktop's agent) in the login shell (`home.sessionVariables`), hence Hyprland and its children, and in systemd --user (`systemd.user.sessionVariables`). `home/secrets.nix` masks Ubuntu's `ssh-agent.socket`/`.service` and `gcr-ssh-agent.socket`/`.service` for the user, so nothing else sets it. Hyprland's autostart starts `bitwarden`.

- git signing: `config/git/config` includes `~/.config/git-bitwarden/signing.gitconfig` (`user.signingKey`, `gpg.format = ssh`, `gpg.ssh.allowedSignersFile`, `commit.gpgSign`), generated by `kubaos bitwarden`. Missing include = unsigned commits.

Written by `kubaos bitwarden env pull` (and `kubaos bitwarden setup`), read by `use bwenv <p>` in `.envrc` (`~/.config/direnv/lib/bwenv.sh`, generated by `home/secrets.nix`) through `kubaos bitwarden env export <p>`, NUL-separated `NAME=VALUE` records. The service name keeps its dotfiles-era value: a new one would orphan every entry already stored.
- Vault names: the gh token comes from the item `gh-token` and a project's env from the folder `env/<p>`. Both are defaults: `KUBAOS_BW_GH_ITEM` names another item and `KUBAOS_BW_ENV_PREFIX` another prefix (`crates/kubaos-core/src/bitwarden/vault.rs`, `Names`), read by `kubaos bitwarden` and Kōbō; an empty value is the default.
- The Proxy's tunnel keys: the vault item `kubaos-proxy` (or the profile's `vault_item`), cached in the GNOME keyring with `service=kubaos-proxy`; "Proxy" above has the rest.

## Hyprland conventions

- Session start: tty1 autologin (getty drop-in) -> zsh login shell -> `~/.zprofile` (home-manager) sources `system/files/hyprland-autostart.zsh` as its last step, which execs `start-hyprland` (shipped with the hyprland package; no uwsm). `~/.config/hypr/no-autostart` disables it.
- Graphical session: without uwsm nothing activates `graphical-session.target`, and xdg-desktop-portal (`Requisite=graphical-session.target`) refuses to start. `config/hypr/autostart.lua` imports the session environment, then starts `hyprland-session.target` (defined in `home/desktop.nix`, `BindsTo=graphical-session.target`).
- Leaving the session: every way out stops `graphical-session.target` and waits for it (at most 15 s) before Hyprland goes, so the portals, the polkit agent and Ghostty stop while Hyprland still answers them. The power menu runs `dot-session leave logout|reboot|poweroff` (then `loginctl terminate-session`, `systemctl reboot` or `poweroff`); the fallback exit bind (`config/hypr/fallback.lua`) does the same inline and then `hyprctl dispatch 'hl.dsp.exit()'`. `hyprland.shutdown` stops the target with `--no-block` for every other exit, never waiting on Hyprland's own clients. Bounds on top: `xdg-desktop-portal-hyprland` and `hyprpolkitagent` have `TimeoutStopSec=5s` (user drop-ins, `home/desktop.nix`), and the system and user managers `DefaultTimeoutStopSec=10s` (`system/files/systemd/{system,user}.conf.d`).
- Shutdown splash: Plymouth's `plymouth-{poweroff,reboot,halt,kexec}.service` start after `user.slice` has stopped, so plymouthd gets the screen once Hyprland has let go of it, and `kubaos-shutdown-splash.service` holds the final poweroff or reboot until 2 s after the splash shows (the sign's switch-off is about 1.7 s), skipped when no plymouthd runs. `install_shutdown_splash` in `system/lib.sh` (run by `25-boot.sh` and the `shutdown-splash` migration).
- Boot: nothing on the way to `graphical.target` waits for the network. `NetworkManager-wait-online` is disabled, and Docker starts on first use through `docker.socket` (`docker.service` and `containerd.service` are not enabled; containers with a restart policy start with it, not at boot; `TimeoutStopSec=20s` so dockerd can stop them). `setvtrgb` is masked. `install_fast_shutdown_boot` in `system/lib.sh` (run by `20-base.sh`, Docker's half by `40-apps.sh`, and the `fast-shutdown-boot` migration).
- Panels and windows: only the frame reserves space (exclusive zones from `config/quickshell/modules/frame/Exclusions.qml`: bar 36 px, 8 px elsewhere). Panels, popups and the OSD live in the frame layer with no exclusive zone and float over windows; opening one never resizes a window. Window corners: `gaps_out = 8`, `border_size = 2`, `rounding = 14` (Hyprland rounds the border's outer edge at rounding + border = 16 = frame radius 24 - gap 8, so the corners are concentric; 24 is the surface radius, `docs/DESIGN.md`).
- Primary terminal `ghostty`, fallback terminal `foot`. The Command menu is `kotodama toggle`, fallback `fuzzel`. Fallback binds always exist and never depend on Quickshell or Nix GPU wiring:
  - `SUPER+Return` ghostty, `SUPER+ALT+Return` foot
- Ghostty runs one background instance, the user unit `app-com.mitchellh.ghostty.service` (`home/terminal.nix`: Ghostty's own unit and D-Bus file, kept running with no window, never restarted by a switch). `SUPER+Return` and the `tui()` binds ask it for a window with `ghostty +new-window --working-directory="$HOME" [-e CMD]`; D-Bus starts the unit if it isn't running, and when the request fails the bind starts a Ghostty of its own. The config keeps `gtk-single-instance = detect`, so a launch with arguments (`-e`, `--working-directory`, Nautilus's "Open in Ghostty", Kotodama's terminal actions) is a process of its own. The windows get systemd --user's environment from when the unit started, which `autostart.lua` fills from Hyprland's first.
- Terminal greeting: a new Ghostty window's interactive zsh runs `fastfetch --config ~/.config/fastfetch/greeting.jsonc` (a short module list) and exports `KUBAOS_GREETING=0`, so shells started below it skip it. Never under `$TMUX`, `$NVIM`, `$SSH_CONNECTION`/`$SSH_TTY`, in `zsh -c`, or when the output isn't a terminal. Off while `~/.config/kubaos/terminal/zsh/no-greeting` exists (`dot-greeting on|off|status|show`, the Command menu's "Terminal greeting on/off") or `KUBAOS_GREETING=0` is set.
- zsh start-up: the init scripts of oh-my-posh, fzf, atuin, direnv and zoxide and the completion dump are cached in `~/.cache/kubaos/zsh` (`home/shell.nix`), named after the tool's store path, so an update writes new ones. oh-my-zsh stays for its `git` plugin and libraries, without its security audit; compinit trusts the dump and rebuilds it daily, or when `$fpath` changes.
  - `SUPER+Space` the Command menu (`kotodama toggle || pkill -x fuzzel || fuzzel`: fuzzel when no menu answers), `SUPER+ALT+Space` fuzzel
- `SUPER+F1` opens the Command menu on Kotodama's Shortcuts View (`kotodama open --view hyprland/shortcuts`), which lists every bind by its `description`.
- Window focus on `SUPER+hjkl`, screen focus on `SUPER+arrows`, move window `SUPER+SHIFT+hjkl`, resize `SUPER+CTRL+hjkl`, workspaces `SUPER+1..0`, move to workspace `SUPER+SHIFT+1..0` (`+ALT` without following), next/previous workspace `SUPER+Tab` and `SUPER+CTRL+arrows`, next/previous workspace group `SUPER+CTRL+ALT+arrows`, group windows `SUPER+ALT+Tab`. The rest ported from Omarchy 4. Every bind has a `description`, its title in the Command menu's search (`[extensions.hyprland] in_search = true` in `config/kotodama/kubaos.toml`).
- Monitors: every screen at its preferred mode, placed by Hyprland and scaled for its density (`config/hypr/monitors.lua`), with the lid rule for `eDP-1`. A layout of one's own (positions, refresh rates, scales) goes in the user layer's `hyprland.lua`, matched by description; `config/hypr/README.md`, "Your screens", shows how. Every size (Quickshell tokens, terminal and UI fonts) is tuned once for Full HD density, about 1920 logical pixels across, which a screen's scale brings it to.
- Workspaces per screen: each has its own 1-10, a block of ten Hyprland ids (the laptop panel 1-10, the next 11-20), owned by a desk position, never by the screen or its connector (`config/hypr/workspaces.lua`, #131). The positions are the laptop panel and the externals counted 1, 2 and on from the left by Hyprland's layout (top to bottom at the same x), recomputed once the layout has held still for 250 ms after a screen arrives, goes or the layout changes (Hyprland reports a screen before it arranges it, and a dock's screens come and go one at a time), and never on a window event; whatever screen stands at a position shows its group, with no pairing to set up, so a desk needs its screens placed in the order they stand (user layer `hl.monitor` lines; auto placement follows connector order). The group of a position no screen holds waits, under its own numbers, on the primary screen (the laptop panel, else the external Hyprland numbered first) if it has windows, and goes to the next screen that takes the position; a position never seen gets a fresh block. When the positions shift, each group moves to the screen now at its position; no workspace is renumbered, since the bar's Quickshell keeps a workspace's first id. Each group keeps its first workspace and one after its last with windows as Hyprland persistent rules, bound to its screen. The bar shows each group apart, in block order: the screen's own first, then the waiting groups. Next and previous (binds, swipe, the bar's wheel) walk the groups in that order: every workspace the bar shows, one new empty workspace after a group's last, then the next group's first; a group's first steps back to the previous group's last. `SUPER+1..0` address the focused group. The user can pin screens to positions, which are then the workspace groups' numbers (`U/desktop/workspaces/groups.toml`, "Defaults and the user layer"): a pinned screen stands at its group's number whatever the layout, and the unpinned externals are counted from the left over the numbers left. The state is `~/.local/state/kubaos/hypr/workspace-screens` (`block<TAB>connector<TAB>position<TAB>screen` per position ever seen, and `<TAB>name` when its group has a name, `position` `panel` or `1`, `2` and on, the connector empty while no screen holds it, `screen` the description of the one there now or last; the panel's row stays while the panel stands at a group's position), which the bar reads for connector to block (`config/quickshell/services/Hypr.qml`) and the KubaOS Extension for its desk Items (`crates/kotodama-kubaos/src/desk.rs`). A file keyed by screen (`block<TAB>connector<TAB>identity`, an optional fourth column `x`) is migrated on the first reconcile: the externals plugged in keep their blocks at the positions they stand at, the others' blocks take the positions 1, 2 and on by last-known `x`, then block, up to the first position a plugged-in screen holds, and any left over wait with no position, so no window or id moves. A file naming a position twice, two positions with one block, or a screen at a position and again waiting at another is repaired on load (the first row, the plugged-in screen's row, and the held position win; a waiting row of a screen standing elsewhere goes once its block is empty). The file is written whole, by rename, after the workspaces have moved. The actions run over the socket too: `hyprctl dispatch 'dot.workspaces.focus(3)'`, and `dot.workspaces.go_to_position("1")` focuses a position's screen, or its waiting group. `dot-hypr-workspaces` runs `dot-hypr-lid sync` on every monitor hotplug.
- Keyboard layouts: the user's, `layouts` in `~/.config/kubaos/desktop/keyboard/keyboard.toml`, written only by `kubaos keyboard` (`kubaos_core::keyboard`), which the Command menu's keyboard Items and the control center's Keyboard tile and tab run; `config/hypr/input.lua` reads them, and `hyprctl reload` applies a change at once, with no privilege asked. Until the user has a list they are the ones in `/etc/default/keyboard`, which the install writes; the `keyboard-layouts` user migration and `kubaos keyboard seed` copy them over. `/etc/default/keyboard` is the system's: the console and the initramfs's disk passphrase prompt type with it, and Hyprland takes its model and options. It follows the user's default alone: when the default changes, `kubaos keyboard` writes it through `pkexec /usr/local/libexec/kubaos-keyboard-write` (`system/files/keyboard/`, polkit action `org.kubaos.keyboard.set`), which then runs `setupcon --save-only`, a udev change for input devices and `update-initramfs -u` in the background. Not through localed: Ubuntu's systemd ships a D-Bus policy (`org.freedesktop.locale1.read-only.conf`) that refuses `SetX11Keyboard` to everyone, root included, and Debian's localed no longer writes `/etc/default/keyboard`. `system/files/polkit/50-kubaos-keyboard.rules` lets an active local user in the `sudo` group through without a password, and anyone else gets the session agent's prompt. When that fails the user's layouts have changed all the same; everything pkexec said is logged on a line of its own, then the sentence the tab shows says the console keeps the old default and why (polkit refused it, no polkit agent was running to ask for the password, the prompt was dismissed, the helper isn't installed, or the helper's own words). With no terminal, as from the tab and the menu, pkexec runs with `--disable-internal-agent`, so only the session's agent asks. The tile switches to the next layout; its tab makes one the default, moves, removes or adds one from every layout and variant xkb knows. Those are the Items of the "Add a keyboard layout" Kotodama app (`crates/kotodama-kubaos/layouts/manifest.toml`, Extension `kubaos-layouts`, word `layout`, the same binary as the KubaOS Extension in its `layouts` mode), each layout not in use one Item that runs `kubaos keyboard add`. The tab's "Add a language…" (`config/quickshell/modules/controlcenter/KeyboardAddView.qml`) is a second Front end of the Daemon: its own `KotodamaSearch` runs the app's entry Item, searches inside the app and draws the Results. It never sends `shown`, answers `close` at once, and hands a `toggle` or `open` the Daemon routes to it on to the Command menu (`config/quickshell/services/MenuRequests.qml`). Searches over lists in the shell go through Kotodama this way, never a filter of their own.
- Mac-style accents on Left Alt: keyd (`/etc/keyd/kubaos.conf`, from `system/files/keyd/kubaos.conf`) makes Left Alt a layer that is Alt for every key but e, `, u, i and n. Those latch a mark; the next letter is sent as a dead key on a spare keycode, then the letter's own key, and Space as the mark alone on another. The `kubaos:mac-accents` XKB option (`/etc/xkb/rules/evdev` including the system's rules, and `/etc/xkb/symbols/kubaos`) gives the spare keycodes their symbols in every layout, and `config/hypr/input.lua` adds it to the file's options, never replacing them. Both files are generated from `crates/kubaos-core/src/keyboard/accents.rs`, and a test keeps them equal to it. The cheat sheet is a submap of described binds nothing enters (`config/hypr/accents.lua`), so the Shortcuts View lists it.
- Lock command everywhere: `loginctl lock-session`. hypridle's `lock_cmd` runs `qs ipc call session lock || hyprlock`.
- Idle (`crates/kubaos-idle`, #155): by default lock 5 min, DPMS off 10 min, suspend 30 min only on battery; plugged in, never auto-suspend. The user's times, each on battery and plugged in, are in `~/.config/kubaos/desktop/idle/idle.toml` (see "Defaults and the user layer"). hypridle's `general` block and the sources are `config/hypr/hypridle.conf`; its listeners are `~/.local/state/kubaos/idle/hypridle.conf`, which `kubaos-idle` writes at every change, at login (`config/hypr/autostart.lua` starts hypridle through `kubaos-idle session`) and at every switch (`home/idle.nix`), before the user's own `hypridle.conf`. A wait the same on both power sources is one listener; two waits are a listener each, with `condition_cmd` `! dot-hypr-on-ac` or `dot-hypr-on-ac` and `condition_retry = 60`, so a power change while idle takes effect within a minute. A change restarts hypridle in the session: `hyprctl dispatch 'hl.dsp.exec_cmd([[dot-session start-idle]])'`, which starts it too when it isn't running. Nothing in KubaOS stops hypridle any more.
- Keep awake: a logind `idle` inhibitor (`systemd-inhibit --what=idle` around `kubaos-idle awake hold`, the transient user unit `kubaos-keep-awake`), which hypridle honours, for a while or until turned off (`SUPER+CTRL+I`, the Command menu). hypridle keeps running, so `before_sleep_cmd` still locks before a suspend. It ends on its own, and with the Hyprland it was started in. Its state is `$XDG_RUNTIME_DIR/kubaos-keep-awake.json` (`{"active", "until"}`), which the bar's `IdleIndicator` watches.
- Scheduled actions: "Lock in…/at…", "Suspend in…/at…", "Shut down in…/at…" and "Reboot in…/at…" (`kubaos-idle schedule ACTION in|at …`) act once, idle or not, through systemd user transient timers on the calendar with fixed names: `kubaos-scheduled-action` runs `kubaos-idle schedule fire`, and `kubaos-scheduled-warn-1m` and `-warn-10s` show heads-up toasts with a Cancel action (`notify-send --action`). The action runs in the Hyprland session through `hyprctl -i <instance> dispatch 'hl.dsp.exec_cmd(...)'`, as a keybind's would: `loginctl lock-session`, `systemctl suspend` (hypridle's `before_sleep_cmd` locks first), `dot-session leave poweroff|reboot` (so `graphical-session.target` stops cleanly). Shut down and reboot ask to confirm in the menu. One action at a time, the lock included: a new one replaces the old and its toast says what it replaced; "Cancel scheduled action" (id `lock-cancel`) stops them. A heads-up or a fire acts only while the state still names its action and time, so a stale Cancel never cancels its replacement. Keep awake doesn't hold any of them back. The state is `$XDG_RUNTIME_DIR/kubaos-scheduled.json` (`{"at", "action"}`); the bar counts down with the action's icon (lock, suspend, power, restart).
- Lid: logind's drop-in (`system/files/logind.conf.d/lid.conf`) suspends on lid close only on battery and ignores it plugged in or docked; it stays the fallback whenever no session holds the lid. When the user's lid setting differs (`lid` in `idle.toml`: suspend, lock or nothing, on battery and plugged in), `kubaos-idle` runs a `handle-lid-switch` inhibitor (the transient user unit `kubaos-lid-hold`), and Hyprland's lid bind runs `kubaos-idle lid closed`, which does what the setting says, and nothing when logind's `Docked` is true. The holder rechecks a closed lid every 5 s as logind does (a laptop closed plugged in then unplugged suspends after 30 s awake), and exits when its Hyprland is gone or the setting is logind's again. Hyprland disables `eDP-1` on lid close with an external connected and enables it on open (`dot-hypr-lid`).

# 9. An app is a folder of typed actions with inverses, journaled

Status: accepted (2026-11-16). Kuba's decisions in #435 (part of #93). Amends ADR 0008: an app is a folder of actions instead of a source plus hooks, and whether it is installed is read from its journal.

## Context

ADR 0008 made an app one source (apt, nixpkgs or a pinned `.deb`) plus an opaque pair of shell functions: `system_hooks` in `system/lib.sh` for root and `user_hooks` in `apps/user-hooks.sh` for the user. Installing an app is usually a process, though: a package, a group, a unit, a setting, a vendor tool's own installer. With hooks, nothing knows what an app changed. Each hook's cleanup is written by hand (`remove_t3_service` is a hundred lines of it), a failure halfway leaves whatever the hook got to, a removal has to guess what was there before (`t3-code-linger-was-off` is such a guess written to disk), and two apps can write the same file without either noticing.

## Decision

**An install is a list of typed actions, each with its inverse, recorded in a per-app journal. The journal is the box.** A failed install rolls back to where it started, and removing an app undoes exactly what its install did. Nobody writes cleanup by hand.

### The folder

`apps/<id>/app.toml` is the app; files its actions use sit beside it (templates, scripts a `run` calls, a web app's icon). Adding an app is one folder. A file another project wrote (Penpot's logo, its compose stack) names its licence in its header comment, and the repository ships that licence's text in `LICENSES/`. The file says what the app is, then its actions in order:

```toml
name = "Docker"
category = "development"
tags = ["containers", "compose", "docker"]
summary = "Containers and Compose"
description = "Docker Engine is an open source containerization technology for building and containerizing your applications."
description_from = "https://docs.docker.com/engine/"
icon = "docker"

[[action]]
name = "Install Docker"
kind = "apt"
repo = "docker"
packages = ["docker-ce", "docker-ce-cli", "containerd.io"]

[[action]]
name = "Let you run docker without sudo"
kind = "group"
group = "docker"
```

Every app carries its description, all of it required and checked when the folder is read:

- `category`: one of `browsers`, `development`, `ai`, `communication`, `media`, `graphics`, `office`, `security`, `system`, `games`, which groups it with others (Kōbō's guided setup, `kubaos app list`). A new category is a decision for its PR, added here.
- `tags`: at least one word people search by ("browser", "containers", "passwords"), lowercase words, each once. They find the app while it isn't installed: they are keywords of its Install Item only, never of Remove.
- `summary`: one line of ours, in KubaOS's voice (`docs/BRAND.md`), saying what the app is.
- `description`: the app's own words, copied from its upstream (its AppStream metainfo, store listing or homepage) where the source's licence allows it, trimmed of lines that speak as the vendor; else a plain factual one of KubaOS's; `description_from`, the `https://` URL it came from, or `"kubaos"` for one KubaOS wrote.

`icon` stays optional. It is the icon theme's name for the app's icon (Colloid's, `icon = "docker"`), or, for an app the theme doesn't draw (Aider, a CLI tool with a logo of its own), an `.svg` of the folder named `<icon name>.svg`. The install then puts it in the theme: a step after the app's own install-stage actions, before a setup's, "Put <Name>'s icon in place", a `file` to `~/.local/share/icons/hicolor/scalable/apps/<icon name>.svg`, journaled with the picture's text as any `file` is, and taken away with the app. `hicolor` is the theme every theme falls back to, so a desktop entry naming the icon (a vendor's own, `Icon=<icon name>`) finds it whatever theme is on. The Command menu shows the folder's file by its path, so an app has its icon before it is installed. The picture names its licence in its header, as every picture of a folder does.

An app with setups (ADR 0008) lists them as `[setup.<id>]` with `name` and `summary`, and each setup's own actions as `[[setup.<id>.action]]`. An install of a setup runs the app's `[[action]]`s, then the setup's, as one list, the install stage's first and the configure stage's after them (below): a step is its 1-based place in that list, so the app's own install-stage actions, which come first, have the same steps in every setup. A `[[ready]]` (`check`, an argv run as the user in the app's folder with its words filled in, and `says`, the sentence when it fails), top level or in a setup, must pass before an install or a removal changes anything (T3 Code's "quit T3 Code first"), and only then: an install of a complete app every step of which stands (its journals record it word for word and its checks, from the user's side, say done) changes nothing, so it isn't asked, and an update checking T3 Code's service goes ahead while T3 Code is open.

Strings take `@USER@`, `@HOME@`, `@ARCH@` and `@VERSION@`, the version of the app's downloads: every `download` of an app, in any setup, has one `version`, which a release moves together, so the app's other actions name the version's folder by it too (a `symlink`'s `target`, a unit `file`'s `ExecStart`); a `symlink` or a template `file` naming it in an app with no download is refused as it resolves. A path is `~/…` (the home) or absolute; an absolute path an action writes is under `/etc/`, `/opt/` or `/usr/local/`. Templates (`from` with `template = true`) take the same words.

`keeps`, top level or in a setup, is what a removal leaves on purpose, said as it ends: the user's own data (Penpot's local designs).

### Dependencies

`requires = ["<id>", { id = "<id>", min = "<version>" }]`, top level or in a setup (an install in a setup requires the app's, then the setup's), names the apps installed first, in order. A dependent app's folder holds only its own part (LazyVim: its config and first plugin sync); the required app installs through its own folder, actions and journal, as if the user had added it.

- **The catalog check** refuses an id the catalog lacks, the app itself, an id twice, a `min` that isn't a dpkg version, a required app with setups (nothing could say which), and apps requiring each other in a circle, naming it ("agent → desk → agent").
- **The plan.** An install first works out its apps: what it requires, each after what that requires, every app once, then the app. A `min` is checked then, before anything runs, against the version the required app's source offers this machine: its first own package's, a `deb`'s or `download`'s pinned `version` (the installed one, for a `.deb` that updates itself), an `apt` package's installed version, else the one `apt-cache policy` says apt would install; compared as dpkg compares versions. A source that can't say (a `nix` package, apt not knowing the package yet) can't be shown to meet it, and is refused as well. An `apt` package from a vendor repository the machine hasn't added is such a case: apt knows its versions only from the repository's index, which comes with the repository, and adding it is a root step of the required app's install; reading the index before that would need root and the network while the plan is made, before the one prompt and before anything is meant to change, so a `min` on such an app waits until its repository is there (the app installed by itself first). The refusal reads: "it needs Neovim 0.11 or newer, and this machine would get 0.10.2-1".
- **The run.** The run holds the lock from the plan to its last app, so another run can't come between them. Each app of the plan is installed in turn, an `app` event naming it and its place ("Neovim, 1 of 2"); a required app the machine has with no journal is taken in first, owned when picked. One that fails rolls back its own steps, and the required apps this run installed are removed after it, newest first, so the machine is as before; one that was there stays.
- **Brought by.** Once every app of the plan stands, each required app the user hasn't picked records in its user journal's `brought_by` the apps of the plan that require it. It is state, never in the picks: the picks stay what the user asked for.
- **Switching setups.** An app the machine has in another setup is checked ready in both setups before anything runs, as the switch undoes the old setup's own steps (Penpot's window open on penpot.app keeps the switch to the local stack from deleting files under it). Once the app stands in its new setup, each app the old setup required and the new one doesn't forgets that the app brought it, and goes, as a removal of the app would take it, when nothing else installed brought it, no installed app requires it and the user hasn't picked it: switching Penpot from its local stack to penpot.app takes the Docker it brought, after the stack is down. One that can't be removed is a warning, and keeps the app in its `brought_by`, so the app's removal takes it.
- **Removing.** Removing an app an installed app requires (in the setup it is installed in) is refused before anything runs, naming it: "Neovim is needed by LazyVim: remove that first". Otherwise the app goes, then each app every one of whose `brought_by` is going (or no longer installed), which the picks don't have and no installed app staying requires, each after the apps that brought it, each its own `app` event. A required app the user picked, before or after it came, stays; one two apps brought goes with the last of them. An app staying loses the removed app from its `brought_by`. Once the app asked for is gone, a brought app that can't be removed is a warning naming `kubaos app remove <id>`, and the apps it brought stay: the removal asked for is done, so the picks keep it out.
- An app is **unavailable** on a machine when a step of its own, or of an app it requires through what those require, has nothing for its architecture: Penpot on arm64, as Google builds Chrome for amd64 alone. A `nix` step with `unfree = true` has nothing for a machine whose user's nixpkgs refuses unfree packages: its name in `packages.toml` would fail the home's switch, for every package, not only the app's.

### The configure stage

`stage = "configure"` on an action makes it part of the configure stage, which sets the app up the KubaOS way: its defaults in the user layer, never in the user's own files. Its steps come after every install-stage step, the app's then the setup's, and an install runs them as any other. A configure step runs as the user, and what it writes (a `file`, `symlink`, `output` or `download` path, a `setting`'s file) is in `~/.config/kubaos/<id>/`; a user `run` may be one (LazyVim's first plugin sync); the folder check refuses anything else. `kubaos app configure <id>` runs the stage alone again on an installed app: each configure step checked, one not done done (a default the user changed is put back), a failure undoing the steps this run added; it needs no password. An app whose journals record a step its folder has changed since (a release added or changed one, moving the steps' numbers) is refused until an install brings it up to date: "LazyVim changed with this release: kubaos update brings it up to date, then configure it". A removal undoes configure steps with the rest of the journal. The Command menu has "Configure <Name>" for an installed app whose setup has a configure stage.

### The vocabulary

Every action has a `name` ("Download the t3 tool"), the step the user sees. Each kind knows how to **do** itself, **check** whether it is done, and **undo** itself, and runs as root or as the user by its kind and paths, never by the author's say, except `run`. An action resolved for a machine (its words filled in, the files of the folder it names read in) is what the journal records and what an undo runs.

**`versions` is the app's build of a name.** A distribution may ship its own package under the name a vendor's repository has: Ubuntu's `firefox` is `1:1snap1`, a stand-in that installs the snap, whose epoch sorts above Mozilla's `160.0~build1`. `versions` is the pattern of the versions that are the app's (`*` any run of characters: `*~build*`); a package dpkg has at another version doesn't count as installed, the install replaces it, moved down if apt must, and a removal leaves a build outside the pattern, which the step never installed. Only the action's own packages may move down: the simulation names each package apt would move to a lower version (`Inst <package> [<old>] (<new> …)`, the new version sorting below the old), and one that isn't the action's is refused as a removal is. A user's pin of priority 1000 on a library, which apt would follow down, never goes silently through an install that allows downgrades for its own package.

**`run` is the one escape hatch**, for vendor tools (`t3 service install`). Its `check` and `undo` are mandatory: the author says how to tell it is done and how to take it back, or there is no `run`. Its argvs are a program on the fixed `PATH`, `./<script>` in the app's folder, or, as the user only, one under the home (`@HOME@/.local/bin/t3`): root never runs a program the user could change; `@HOME@` and the rest are filled in, nothing else is. It runs as the user, with their environment and `HOME`, unless `root = true`: then as root, with root's own environment (`HOME=/root`, the fixed `PATH`) and nothing of the user's (no `XDG_*`, no `PYTHON*`, `NPM_*` or `CURL_*`). A `./<script>` is read into the action as it resolves, so the journal holds the scripts the step ran: a check, a resume and an undo run those, from a fresh private folder that is their working directory, whatever the app's folder holds by then or after the app left the catalog. A script reads nothing else of the folder; a file it needs is an action of its own (a `file`). With `window` (the sentence of the step left to the person), it opens a window, so it runs only in a run that may open one (`kubaos app add` in a session with a display); in one that may not (`kubaos update`, or `kubaos app add` over SSH), it is skipped, its sentence becomes a note, and the install is complete all the same. It is the only place an author's command runs.

**Several downloads, one folder.** A `download` may unpack into another download's folder, its `to` a path in the other's: Ollama's AMD libraries are a second archive of its release whose every file is under `lib/ollama/rocm_v7_2/`, which the main archive doesn't have, unpacked there with `strip = 3`. It owns only what it adds (its folder, and the folders above it it made), so a removal, newest first, takes it, then the folder around it, and a setup switch takes it alone. The folder check refuses a step whose path is in a download's folder before that download: the download unpacks its folder whole, over whatever a step before it put there. Replacing the outer download (a new pin at the same path, or one a stopped run left) takes the inner one's files with it, and the inner step, which comes after, finds its path gone and downloads it again in the same run; a new version lands both in the new version's folder.

**A GPU's libraries are a setup, picked by the user.** Ollama's main archive carries the CPU builds, NVIDIA's CUDA 12 and 13 and Vulkan; AMD's ROCm is the second archive, a gigabyte more. The choices were nested downloads alone (every machine downloads ROCm, used by AMD's GPUs alone), a setup per GPU kind (`nvidia`, `amd`, `cpu`: the first and the last install the same archive, a choice that changes nothing), and nested downloads within setups. Ollama has two setups, `standard` (the main archive) and `amd` (with ROCm, unpacked into it): what a person picks is whether to download AMD's libraries. Nothing in the engine knows the machine's GPU, and a step that detected one would be a `run` whose answer changes with the hardware, under a journal that records what was done; the person knows their GPU, and a switch between the setups downloads or removes the ROCm folder alone. The steps after the ROCm download (the service's unit file and its start) are each setup's own, so the service starts with the libraries it will find.

**A download's pin is the journal's.** A file's content can be compared with its action, a download's can't: a tarball unpacked to a folder carries no sha256, and hashing a runtime on every run would be slow. So the journal says which pin a download is: its check is done only when the step that put `to` there recorded the pin the folder's action has now, and a release that changes the pin downloads it again, at a new path or over the old one. A `to` without `@VERSION@` is allowed, since a single program at a path others name (`~/.local/bin/tool`) has nowhere else to go; a folder a running program reads takes `@VERSION@`, so a new version lands beside the old one, which goes only once the new one stands (T3's runtime does). `self_updates` hands the download to the vendor's updater once it is there: a pin that moves never brings an older build back over a newer one the updater installed, so a `to` without `@VERSION@` is done while it is there, as a self-updating `deb` is done while dpkg has the package.

**A web app's window is named by Chrome, not by us.** On Wayland, Chrome names an `--app` window after the URL and the profile, `chrome-<host>_<path>-<profile directory>` (the file name of the desktop entry it would write for the app, a character a file name can't have and a space made `_`); `--class` sets only X11's `WM_CLASS` class, which an XWayland window would have, so a `StartupWMClass` of the class never matched the window. A `--user-data-dir` of its own makes the web app a browser process of its own, so its flags reach it whether or not the user's Chrome is open (a second launch with the same folder is handed to the running browser, flags and all), and a `--profile-directory` of `kubaos-web-<id>` makes the name the web app's alone: `chrome-design.penpot.app__-kubaos-web-penpot`, which `StartupWMClass` holds, so a launcher or a dock matches the window to its entry; no Hyprland rule names a web app's window. Read in Chromium 157's `browser_native_widget_aura_linux.cc` (`wayland_app_id = GetXdgAppIdForWebApp(app_name, profile_path)`, `app_name` the URL's host, `_` and path) and `web_app_shortcut_linux.cc`. Its own folder also keeps the web app's sign-ins apart from the user's browser; they are the user's data, so a removal keeps them, as it keeps Penpot's designs.

**A web app's icon is the theme's when the theme has one.** The icon theme, Colloid (`home/theme.nix`), is on every machine, so a `web_app` whose service it draws names the icon (`icon = "whatsapp"`): the desktop entry says `Icon=whatsapp` and nothing is copied. The icon follows the theme's updates, and the repository ships no copy of an icon under another licence (Colloid's are GPL-3.0, whose text a copy would have to carry). A name is the icon theme's form: letters, digits, `-`, `_` and `.`, starting with a letter or a digit, with no `.svg`, `.png` or `.xpm` at its end: an `.svg` names a file of the folder, and the theme's lookup reads any of the three as a file's. An `.svg` in the folder stays for a service no theme draws (Penpot), copied to the user's icons as before.

**Unfree is said by the folder.** Whether a nixpkgs package is unfree is its `meta.unfree`, which only an evaluation of the user's nixpkgs can read: seconds of `nix eval`, too slow for the menu's reading of the catalog. The `nix` action says it instead, `unfree = true` (Discord, Zoom), and availability reads the user's setting (`nixpkgs.toml`'s `allow_unfree`) beside the architecture. A `nix` package of one architecture says so as `apt`'s does, `arch = "amd64"`.

The set is sized to the six apps and Penpot (whose setups are a `web_app` and a compose stack) and stays small: a new kind is a decision for its PR, with do, check and undo written down here.

### What an action owns

**Never undo what the app didn't do.** Before an action does anything, its check runs. Done already is **found**: it is reported as done, and the journal records it as not owned, so a removal leaves it. A package that was installed, a group membership that existed, lingering that was on, a key that had the value: the app never takes them away. An action that changes part of a thing owns only that part: an `apt` action owns the packages it installed, not those it found; a `setting` owns the key, with its old value, never the file.

Each action records **claims**, one per thing it changed or found: `path:/…`, `dir:/…` (a folder it made for a path), `key:<file>#<key>`, `package:<name>`, `dep:<name>` (a package apt pulled in for the step's, always owned, kept by the step while it stands; one of another architecture than the machine's is `<name>:<arch>`, as apt names it), `nix:<name>`, `member:<group>:<user>`, `group:<name>`, `unit:<scope>:<name>`, `linger:<user>`, `run`, each owned or not. A claim another app's journal also holds is handed over when its owner is removed, not undone, with the owner's prior state: an `apt` package two apps need is removed with the second, not the first (a `dep:` passes to an app whose step found that `package:`), and a unit one app enabled and another found enabled goes back to disabled when the second of them goes, whichever order they go in.

**Who owns a path comes from the journals.** An action that would write a path another app's journal owns (the path itself, a folder above it or a path in it) is refused before anything runs, naming the owner ("~/.config/nvim belongs to AstroNvim"). A path that is there and that no journal owns, and whose check isn't done, is the user's own: the action refuses and names it, and never overwrites it. A path already as the action would leave it is found, not owned. There is no hand-written `conflicts` field. A `setting`'s key follows the same rule against other apps; changing the user's own key is what a `setting` is for, and its undo puts their value back.

### The journal

Each app has one journal a side: `~/.local/state/kubaos/apps/<id>/journal.toml` for its user actions, `/var/lib/kubaos/apps/<id>/journal.toml` (root's, readable by everyone, written by root only) for its root actions. It is state, never in the picks: it describes this machine.

```toml
app = "t3-code"
setup = "service"
# Every step of the install is done. The user journal says it for both.
complete = true

[[entry]]
step = 6
state = "done"
claims = [{ claim = "run", owned = true }]
action = { name = "Start the service", kind = "run", do = ["/home/kuba/.local/bin/t3", "service", "install"], … }
```

An entry holds the action as it was done, its words filled in, so a removal undoes what was done even after a release changed the folder, and its **prior state**: what the undo needs and nothing else (a key's old value, whether the unit was enabled, whether lingering was on).

**Write-ahead.** Before an action runs, its entry is written as `doing`, with its claims and prior state read from the machine; once it is done, `done`. Before an undo, it is written `undoing`, and it goes once the undo is done; so a run killed during an undo leaves an entry that is never taken as settled. The file is rewritten whole and renamed into place, so a run killed at any point leaves a journal that is either the old one or the new one.

**Failure.** The steps already done are undone, newest first, across both journals; the machine is as before and the error names the step ("Start the service: `t3 service install` exited with code 1"). For an install, "before" is before the install began: an app that wasn't complete (a fresh install, or one resumed after a stop) is rolled back whole and its journals go. An app that was complete undoes only the steps this run added (a release added one), and stays installed: a step this run did again or updated stays done, and the next run checks it.

**Remove.** The journal is undone, newest first, and its folders go. Data the user made (Docker's images, T3's projects and threads) is no action's, and stays. An undo that fails stops the removal there; the journal keeps what is left, and the next removal goes on from it.

**Every run checks every step.** The journal says what the app owns, never whether a step still holds: a run checks each step, whatever its entry. A step whose check says done is reported done (settled, or found when the journal has no entry for it); one whose check fails is done again, as `kubaos update` repairs an app the user broke, keeping what its entry owned and the prior state recorded before it first ran. A step whose entry is `doing` or `undoing` (a run stopped during it) is checked the same way. So a run stopped after step 2 of 4 reports 1–2 done and goes on from 3, and a step after one that changed is checked like any other (Docker's `docker.service` `enable = false` after a new Docker enabled it again).

**A changed step.** A step is changed when its entry's action, as recorded, isn't the folder's action at that step as resolved now, word for word. A changed step that acts on the same thing (the same kind on the same side and, for a kind whose thing has a name, the same name: a `deb`'s package, a `file`'s, `symlink`'s or `output`'s path, a `setting`'s file and key, a `unit`'s unit and scope, a `group`'s group, a `web_app`'s id; any `apt`, `nix`, `download`, `linger` or `run` is the same thing as another of its kind) is **updated in place**: the new action is done over the old one when its check fails (a `deb` or `apt` installs the new version over the old, a `file` is rewritten, a `download` of a new version is fetched to its new path, or over the old one at a `to` without `@VERSION@`), keeping ownership of everything both claim (and of the folders the old one made that the new one's path is in); then what only the old one owned is undone (a package dropped from an `apt` list, the old version's download folder). The entry keeps the old action with those claims as `replaced` until that undo is done, so a run stopped between them finishes it. A changed step that acts on another thing is undone first, then the new action is done. An app is never undone and done again whole.

**A declined password changes nothing**: the root half is started before the first step whenever the run may need it, so a run that needs root and doesn't get it stops before anything runs. A run needs root when a root step has no entry in root's journal that is settled and records the same action word for word, when such a step's check, run from the user's side, doesn't say done (a root `run`'s check runs only as root, so such a step always needs it), and when an app that isn't complete has root steps a failure would undo. An installed app whose root steps all check done installs without a prompt.

**Installed** is the user journal's `complete`, with something owned in either journal; a complete app that owns nothing is **found**, KubaOS's to leave, and has no Remove Item. An app with no journal whose own `apt` and `deb` packages dpkg has is installed when picked (taking it in makes it KubaOS's) and found when not. Reading it is two small files an app and the one dpkg query the status makes for the versions anyway, no check run, so the Command menu's status reads stay cheap.

**Querying ownership** reads every journal (one TOML file an app and side, a few hundred bytes each) into an index of claims; a dozen apps is a dozen small reads, so no second index is kept that could drift from the journals.

### What a machine had

An app the machine had before its journal (installed by an older release of KubaOS, the base apps the `base-apps-*` migrations handed over, an app added through `kubaos app add` before this, or one set up by hand) is **taken in**, running nothing but checks: by `kubaos app adopt`, which the user migration `apps-adopt` runs once, and before `kubaos app add|remove` and an update's install of an app with no journal. The rule:

- **Whether it is there.** An app with no journal on either side is there when every package step of its own actions (`apt`, `deb`, `nix`; every one of its own actions, for an app with none) checks done. A picked app is there in the setup the picks name: the user picked it, and a step of it that doesn't check done (a runtime the vendor's updater replaced, a unit the user stopped) is the next run's to do. Any other is there in the first setup, by id, whose own steps that open no window all check done (a window step, pairing, is the person's to do, and an update skips it anyway), else in the setup with no steps of its own; with neither, it isn't taken in. An app that isn't there stays without a journal.
- **What it records.** Its user journal is written `complete` in that setup, with an entry for each user step that checks done; a step that doesn't is left to the next run that checks it, as one the user undid is. Root's steps are recorded by root, through an `adopt` request (app, setup, and whether it is owned; root records its steps that check done, by the same rule), on the first run that starts root: until then the user journal's `root_adoption` says it is due. Taking an app in asks for no password, so the migration runs unattended, and the status reads it as installed from the start.
- **Whose it is.** A **picked** app is KubaOS's: the picks are written only by `kubaos app add` and by `base-apps-picked`, which picks a base app only where the release's install put it (its package group wasn't turned off). Each step of it that checks done is **owned**, with the prior state of a machine without the app: a unit neither enabled nor running, a settings key absent, the user not in the group. So its removal undoes it, as if the engine had installed it. A step whose path is there holding another text an older release wrote is owned too, and the next run brings it to this release's (Chrome's theme helper and units and Docker's drop-in, whose comments named the scripts that installed them then). An app one of whose steps has nothing for the machine's architecture isn't there. Never owned: a group itself (the package makes it), a package apt pulled in beside the app's (no journal knew it, so a removal leaves it), and lingering, unless KubaOS's older mark `<id>-linger-was-off` beside the journals says it was off before (the mark goes once a `linger` step is recorded, whose prior state replaces it). An app that **isn't picked** was put there by other means (a T3 Code service set up with `t3 up`, a Chrome installed while its group was off): every step is **found** and owns nothing, so it counts as found, and its removal forgets it and leaves the machine as it is, saying so; it asks for no password unless root has a record of what it found, which other apps' removals hand claims to and only root forgets.

Root takes the user's side's word for whether an app is owned: the word decides only what a later removal takes away, and that removal asks for the password, which already lets its holder remove those packages.

### Events

Each step is an event of the run's `UpdateEvent`s: `action` with the app, the step, of how many, its name and its state (`done`, `found`, `skipped`, `undoing`, `undone`, `failed`). A `step` event carries the name and a `progress` event the count (`done` of `total`, sent before each step and once at the end), an install's, a removal's and a configure's alike. An `app` event (`app`, `name`, `n`, `of`) starts each app of a run: an install's required apps first, a removal's brought apps after it, a configure's one. The Command menu's Job shows the step and its place among the app's, "Installing T3 Code" with "Start the service, 2 of 4", after the app and its place in the run when the run has more than one: "Installing LazyVim" with "Neovim (1 of 2): Install Neovim, 1 of 1"; its bar runs across the whole run.

### Root

**The root half is the `kubaos-apps` binary, not shell.** A root run starts one root process (`pkexec /usr/local/libexec/kubaos-apps serve` for `kubaos app`, through sudo inside `kubaos update`), one polkit prompt a run, which answers requests on its stdin, one JSON line each: `preflight` (an install's root steps checked against the root journals' claims), `step` (do one step of an app's setup) and `undo` (undo one step of the root journal). A request names an app id, a setup id and a step number, nothing else: the binary reads the action from the root-owned catalog (`/usr/share/kubaos/apps/<id>/app.toml`, refused unless the checkout, its `apps/` and `system/`, `system/apt-repo.sh`, and the app's folder and everything in it, at any depth, are root's, none a link, and no one else may write them), refuses a step whose action isn't root's (a user action, or a `run` without `root = true`), and undoes only what the root journal, which only root writes, recorded. An `adopt` request (app, setup, whether the app is owned) records root's steps of an app taken in, as above. It holds `/run/kubaos/apps.lock`, in a folder only root may write, while it serves, so only one run changes a machine at a time; the user's side holds `~/.local/state/kubaos/apps/.lock`.

Why a binary: the actions are Rust, typed and tested once; a shell root helper would have to implement the vocabulary a second time in the language least able to check it, which is how `kubaos-apps` grew to two hundred lines of manifest parsing in awk. The binary is small to audit because its surface is: its `main` takes `serve` and nothing else, and every request is three validated words; the actions it runs are the same code the tests prove. It is built with the release (`.#kubaos`, a second binary of `kubaos-cli`), linked from the Nix store into `/usr/local/libexec/` by root, as `install_scx` links `scx_lavd`, so neither the user nor their profile can change what pkexec runs.

**The local stack runs as root.** Docker's install adds the user to the `docker` group, and a session gets its groups at login, so a user's `docker compose` right after it is refused until the next login. The choices were a root `run`, `sg docker` (a shell string, run through `newgrp`'s password logic, the group still missing from every other process of the session) and the user's own `run` after a re-login (an install that can't finish in one go). Root needs no group and talks to the daemon as the group would; what the daemon starts is the same either way. So the compose file is root's (`/etc/kubaos/penpot/`, a `file` action: a stack the user could edit, run by root, would be root for anyone who can write it), and the `run` that brings it up and down is `root = true`, its scripts read from the root-owned catalog. Its check also runs as root, so every run that checks Penpot's local setup starts the root helper; an update holds sudo already.

**Started on its first use.** Docker starts through `docker.socket`, not at boot, and nothing would bring Penpot's containers back after a reboot until something asked Docker. `kubaos-penpot.socket` listens on `127.0.0.1:9001`, where the window connects (Chrome falls back to it from `::1`, and a machine with IPv6 off can still bind it); its first connection starts `kubaos-penpot.service`, which runs the app's `up` from the root-owned catalog, as the install does, so every image a start pulls is listed for the removal (starting Docker through its socket) and then `systemd-socket-proxyd 127.0.0.1:9002`, passing the window's connections on to the frontend. The proxy runs as a user of its own (`DynamicUser`), with no capabilities, the file system read-only and the homes hidden, no devices, only IP and Unix sockets and the system-service system calls; `up` alone runs with root's privileges (`ExecStartPre=+`), as it talks to Docker's daemon. Penpot's `PENPOT_PUBLIC_URI` is `http://localhost:9001`, the address the window has.

**Deleting the designs is the user's to ask, never a removal's.** A removal of Penpot's local setup keeps its volumes and says so (`keeps`). Deleting them is designed as an action of its own, which no removal runs: an app or setup declares its data as `[[data]]`, with `name` ("Penpot's local designs"), `check` (a root argv that exits 0 while the data is there: `docker volume inspect penpot_penpot_postgres_v15 penpot_penpot_assets`) and `delete` (the root argv that deletes it: `docker volume rm` of both, refused by Docker while a container uses them, so only once the stack is gone). `kubaos app forget-data <id>` runs `delete` through the root helper (a `data` request naming the app and the data's place, nothing else), asking first, the sentence exact and calm: "Penpot's local designs, the volumes penpot_penpot_postgres_v15 and penpot_penpot_assets, get deleted. There's no undo." The Command menu has "Delete Penpot's local designs" while `check` passes and the app isn't installed in that setup, confirmed first. It is not built yet: nothing but Penpot needs it.

What changes in behaviour: cleanup is complete, every time. Removing an app undoes everything its journal owns, even what something outside the catalog would have used: Chrome's theme helper, when Chrome's install made it, goes with Chrome even while a Chrome beta the user installed reads it too; a helper found there (left by an older install, which the base-apps migration kept) was never Chrome's, and stays; Docker's group membership and drop-in go with Docker unless another app's journal claims them; T3 Code's lingering is restored by the `linger` action's prior state instead of a mark file, and only if it was off. The vendor's `google-chrome.list` is turned off by the `apt` action's repository setup, as ADR 0008's one-way trust already does.

## Alternatives

- **A scripting language for installs** (shell functions as today, or a Lua or Rhai script an app). Every script needs its own cleanup, written by hand and tested by nobody, and what it changed is unknowable to anything but itself: no rollback, no ownership, no resume. A sandboxed language could limit what a script touches but still couldn't say how to undo it. The vocabulary trades expressiveness for knowing; `run` covers the rest, with its inverse declared.
- **Nix for everything.** Nix owns the home and a switch is atomic, but the six apps are mostly outside it: apt packages from vendor repositories, a vendor's `.deb` that updates itself, a polkit-era system unit, group membership, an Electron app's own settings file. A NixOS module would do it on NixOS; on Ubuntu, home-manager can't add a user to a group or install a `.deb`. `nix` stays one kind among the others.
- **btrfs snapshots** as the rollback. A snapshot of `@` rolls back everything on the machine, the user's own changes made meanwhile included, needs a reboot to restore, and says nothing about what an app owns, so a removal weeks later can't use it. KubaOS keeps its snapper snapshots for updates (ADR 0001); an app's box is its journal.
- **Containers or Flatpak.** A sandboxed app owns its files by construction, but the six apps are those that need the machine: Docker's daemon, Bitwarden's SSH agent and system-authentication unlock, Chrome's policies, Claude Code and T3 Code running the user's tools. ADR 0008 already excludes Flatpak.

## Consequences

- The engine, its journal and the `kubaos-apps` binary land first, proven on fixture apps. The six apps then move to `apps/<id>/`, with the binary linked as root (`install_apps_helper`, from `60-nix.sh` and `relink.sh`, after its polkit action, which installs without nix too) and `kubaos app` and `kubaos update` running the engine; `system_hooks`, `user_hooks`, `apps/user-hooks.sh`, `apps/user-helper`, the shell `kubaos-apps` and the apps' install functions in `system/lib.sh` go, and `apps-adopt` takes in what an installed machine has, as above.
- The update that brings the folders runs the `kubaos` it started with, which reads the catalog as manifests and finds none: its Apps phase warns that each pick has no app and installs nothing, and the next update, on the new `kubaos`, checks every picked app's steps.
- A `download` a vendor's own updater replaces (T3's runtime after `t3 update`) is `self_updates`: the newer version's folder stands for the pin the updater removed, so no run downloads the pin again.
- Dependencies (`requires`) and the configure stage land after the six apps, with Penpot as the first app that requires others. Each required app keeps its own journal, so `kubaos app show` lists what each owns, and "brought by" is the only state a dependency adds.
- Suites (#32) may share the vocabulary later: a Suite asked for a small, auditable set of privileged steps, which this is.
- The root journal is one a machine, not one a user: KubaOS is a one-person machine, and the root half acts for the user who asked.
